03 · 一轮怎样接着下一轮

文件工具已经读到了 return a - b。模型为什么下一轮知道这件事？因为宿主再次发起请求时，把调用和结果一起放进消息列表。

下面沿用加法修复任务。所有内容都是教学示意，工具结果结构有所简化，不是实际 MiniMax 请求抓包。

第一轮：还没有任何读取结果

发送的消息：

system: 工作区规则与行为约束
user: 修复加法函数的失败测试，不要修改测试文件

工具定义作为请求的另一部分发送，不是伪装成 user 消息。模型返回：

assistant:
  tool_calls = [{id: "read-1", name: "read_file", arguments: ...}]

此时先保存 assistant 消息，再执行工具。

第二轮：历史中多了一对请求与结果

system: 工作区规则与行为约束
user: 修复加法函数的失败测试，不要修改测试文件
assistant: 请求 read_file，id = read-1
 tool: 源码为 return a - b，tool_call_id = read-1

这里的缩进仅用于强调结果，真实角色名仍是 tool。它没有替换最初的任务，而是追加新的证据。模型于是可以请求运行测试；执行后再追加一对消息。

第三轮：模型同时看到目标和失败证据

system: 工作区规则与行为约束
user: 修复加法函数的失败测试，不要修改测试文件
assistant: 请求 read_file，id = read-1
 tool: 源码为 return a - b，tool_call_id = read-1
assistant: 请求 run_command，id = test-1
 tool: 目标测试失败，预期 5，实际 -1，tool_call_id = test-1

现在模型可以提出编辑请求。编辑、复测和差异检查继续遵循相同规则。若模型返回不含工具调用的最终文本，当前循环可以结束；文本是否可靠仍需看证据。

为什么要保留调用 ID

假如模型一次请求读取源码和测试，返回两份正文。如果没有对应关系，就容易混淆哪份结果回答了哪个请求。协议用调用 ID 建立配对，不靠正文顺序猜测。

因此，裁剪和压缩不能留下有请求无结果、或有结果无请求的残缺片段。单条工具消息也不应被改成用户消息：两者来源不同，含义不同。

动手核对

在交互会话完成一次读取后执行 /history。找到一条 assistant 工具调用及其对应的 tool 结果，检查调用 ID，并确认原始用户目标仍在历史里。再执行一次读取，观察历史增加了什么。

阅读 Agent._run 时，只追踪 history.append 和模型调用即可；流式、压缩和检查点逻辑留到后面。协议类型见 models.py。

自测：只把源码正文发给下一轮，不保留用户任务，会怎样？ 模型可能知道文件内容，却失去“修复什么”和“不要改测试”的约束。工具结果不能替代目标。
