05 · 怎样放心地修改代码

模型终于提出把 a - b 改为 a + b。这是一个合理建议，但程序仍不能直接相信它。先看几个独立问题：用户允许修改吗？文件是否已经变化？改错了能恢复吗？命令是否能访问不该访问的位置？

不同机制守住不同边界

机制 加法修复中的作用 不能替代什么
权限与确认 判断本次写入或命令能否执行 文件内容是否仍是刚读到的版本
文件版本检查 拒绝基于旧内容覆盖新修改 用户授权
编辑记录与撤销 保留可核对的旧内容，安全条件满足时恢复 任意命令副作用的回滚
命令沙箱 在已接入路径上约束进程访问 所有工具和远端服务的统一隔离
Git worktree 把任务文件修改与主工作目录分开 操作系统级进程或网络隔离

版本检查为什么必要

10:00 Agent 读取文件版本 A
10:01 同事保存版本 B
10:02 Agent 根据版本 A 请求编辑

若直接覆盖，版本 B 的修改可能丢失。此时应拒绝旧请求，重新读取和评估差异，而不是自动替用户决定保留哪一份。

恢复会话也存在同样的问题：历史里读过文件，不代表现在仍然有效。Fast Agent 加载历史时回到计划模式，并清除读取标记；它保留知识，不继承历史授权。

修改后还需要证据

对这个任务，检查目标测试从失败变成通过、源码差异符合预期、测试文件没有被改掉。退出码为 0、工具返回成功和模型说“完成”，分别只能说明对应步骤的状态，不能互相代替。

动手核对

在可丢弃的临时仓库中，先让 Agent 读取文件，再由你修改同一文件，随后要求它按旧内容编辑。观察它是否拒绝或重新读取。不要在重要工作文件上制造冲突。

详细操作：计划与执行、编辑撤销、命令沙箱。源码：file_tools.py、permissions.py。

自测：独立 worktree 中能否放心执行任意 shell 命令？ 不能。工作目录隔离不等于进程访问隔离，仍要遵守命令权限和适用沙箱边界。
