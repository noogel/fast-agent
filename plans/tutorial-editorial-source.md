# Agent 分层架构

这是一篇进阶回顾。[由浅入深理解 agent 阅读路线](deep-dive/index.md)先用具体问题解释决策、上下文和恢复，再回到本图。建议先完成 [从修复测试理解 Agent](start-with-a-task.md)，并阅读工具、循环和会话章节，再用本图整理已学功能。无需在入门时记住这些层名。

Fast Agent 是一个本地工程 Agent 教学项目。模型提出下一步，宿主程序保存消息、校验参数、检查权限、执行工具并回传结果。**模型输出工具调用，不等于工具已经执行。**

本页基于当前实现描述逻辑分层。源码暂时保持平铺的 Python 模块，避免为了目录外观大规模移动和破坏教程链接。图中六个横向层级表达职责与支撑关系，同层模块并列；右侧安全治理、可观测与控制是横切能力，底部是系统之外的服务依赖。这里没有执行顺序箭头，也不代表六个独立进程。实线框表示已有模块，橙色框提示受限能力（具体边界见下表），底部虚线框表示系统外依赖。

### 图应该怎样读

- **纵向看职责**：交互接入 → 任务编排 → 上下文与知识 → 能力适配 → 执行环境 → 存储基础设施。下层提供支撑，不要求每个请求逐层经过。
- **横向看组成**：同层模块是不同职责，例如模型适配、工具协议和扩展适配互不代表执行顺序。
- **侧边看横切能力**：权限、模式、沙箱、日志、预算和失败控制分布在多个模块中，不是流程末尾的一站。
- **边界外看依赖**：MiniMax 和 MCP 服务不属于本地 Agent 内核。图中持久用户交互指可恢复提问，持久提问已有独立记录与恢复入口，区别于即时 ask_user。

## 一次任务如何经过这些模块

1. 用户输入任务，CLI 把任务交给 Agent；`/save` 等本地命令直接进入管理入口。
2. Agent 加入用户消息；检查上下文占用，在安全边界执行必要压缩。
3. 模型网关收到历史和工具定义，返回文本或带 ID 的 tool calls。这里没有直接写文件。
4. Agent 保存 assistant 消息；注册表校验参数，ToolContext 和工具内部检查权限、规则、路径及版本。
5. 工具执行后返回 ToolResult。大结果先落盘，历史中保留有界结果和读取引用。
6. 对应 tool 消息带上原 tool_call_id，送入下一轮。只有模型结束、达到限额、失败暂停或取消才退出循环。
7. CLI 展示结果；测试输出、差异、日志和报告提供核对依据。模型宣称“完成”仍需这些证据支持。

教学时建议沿 `cli → Agent.run → model.complete → registry.execute → ToolResult → Message(tool)` 阅读，然后再展开上下文和工程工作流。扩展能力不应绕过这条权限和证据路径。

## 本次结构调整：执行与报告存储分离

此前 `delegation.py` 同时运行子任务并直接写运行文件。本次保留它的执行职责，新增 `DelegationReports` 负责格式校验、保存、分页列表和加载；底层文件操作继续复用 RuntimeStore。

`/delegate 任务` 创建报告，`/delegations [页码]` 每页列出 20 条摘要，`/delegation ID` 展示详细报告。两个查看命令不请求模型、不注入主会话、不重放工具；计划模式也能查看。列表按 ID 排序，最多扫描 1000 个候选文件；超限后用 ID 直接读取。损坏记录在列表中显示错误，不能把无效记录当作成功。

`completed=false` 必须保留；工具调用成功也不等于报告结论正确。保存主会话不会嵌入这些独立报告，报告的引用保护与回收规则见[存储回收](tutorial/46-storage-retention.md)。

## 已有能力的边界

- **工作区与回收**：清理证据包、Git 保护引用和审计清单无自动到期，不提供删除唯一恢复证据的命令；清理不保证总磁盘占用下降。
- **委派**：当前为只读、有界并发和协作取消；不强杀已发送的远端请求，不自动重跑未知任务。
- **扩展**：OAuth 支持预注册公共客户端，不含动态注册和客户端密钥认证；外部真实账户按本次要求不接入，不能称已验证。
- **上下文**：窗口估算不是精确 tokenizer，不自动发现供应商窗口；摘要可能丢失细节，Skill 校验不是文件系统快照。
- **工程工具**：LSP 工具不是编辑器插件；评测是限定任务集，不是任意大型仓库修复能力的证明。

图中橙色模块提示这些范围限制，不表示七项约定任务仍未实现。后续扩展应从具体新需求出发，不把已完成验收重新写成待办。

## docs/tutorial/01-model.md

# 01：先理解一次模型调用

模型本身只接收消息并生成回复。配置来自环境，适配器将我们的 Message 转换为 SDK 消息格式。

阅读 [config.py](../../src/fast_agent/config.py)、[models.py](../../src/fast_agent/models.py) 和 [providers.py](../../src/fast_agent/providers.py) 中的 OpenAIModel。重点观察：API Key 不出现在配置 repr 中；默认连接超时 10 秒、读取超时 60 秒，SDK 隐式重试关闭，宿主最多重试 2 次（详见第 11 章）；供应商异常转换成不含原始请求的提示。

在项目根、激活虚拟环境且配置真实模型后执行：

```bash
python examples/single_call.py
```

这一步没有 Agent 循环，也没有执行工具。`Model.complete(messages, tools)` 是我们定义的接口，OpenAIModel 和 MockModel 都实现它，因此后面可以替换模型而不改 Agent。

练习：修改示例中的用户问题，观察回复。没有密钥时使用 `fast-agent --mock --prompt 你好`，但模拟回复不是智能推理。


## docs/tutorial/02-tools.md

# 02：模型请求调用，程序真正执行

工具定义是发给模型的一份说明：名称、用途、参数 JSON Schema。模型返回 ToolCall，其中 id 用于关联结果、name 用于选择工具、arguments 是 JSON 字符串。

阅读 [tools.py](../../src/fast_agent/tools.py)。ToolRegistry.register 注册工具；schemas 导出模型可理解的定义；execute 解析参数、检查类型、调用 handler，最后生成 ToolResult。

参数错误不能直接让整个程序崩溃：返回 `ok=False` 和 error，模型下一步就可以根据错误调整。注册表仅实现项目使用的 JSON Schema 子集，不支持完整规范。

无需密钥，在项目根运行：

```bash
python examples/custom_tool.py
python -m pytest tests/test_tools.py -q
```

练习：把示例的 text 改成数字，观察类型校验；把工具名改为不存在的名称，观察错误结果。不要因为模型声称某项操作已执行就相信它，真正的执行发生在 handler。


## docs/tutorial/03-loop.md

# 03：把一次调用变成 Agent

阅读 [agent.py](../../src/fast_agent/agent.py) 的 Agent.run，这是项目最重要的部分。

1. 先把用户消息加入历史。
2. 带着历史和工具定义调用模型。
3. 将模型的 assistant 消息保存，再检查有没有工具调用。
4. 无工具调用则结束；有调用则执行，并把结果作为 tool 消息写回历史。
5. 再次调用模型，重复直到回答或达到上限。

工具结果必须携带原始 tool_call_id。一个回复包含多个工具时，顺序执行，每一个都必须回传结果。顺序执行方便观察，也避免文件修改之间相互竞争。

无需密钥运行：

```bash
fast-agent --demo
python -m pytest tests/test_agent.py -q
```

观察演示的四次模型调用：读取、编辑、复读、总结。它不是模型在后台偷偷运行代码，而是宿主程序按协议执行请求。

默认上限是每轮 10 次模型调用，不是 10 个工具；同一轮可以请求多个工具。达到上限时本轮标记未完成，最后一批工具结果仍被保存。练习：在测试里把 max_steps 改成 1，观察未完成状态。


## docs/tutorial/04-boundaries.md

# 04：工具执行边界

阅读 [file_tools.py](../../src/fast_agent/file_tools.py) 和 [command_tool.py](../../src/fast_agent/command_tool.py)。

文件路径先 resolve，再判断是否属于工作目录，所以 `../` 和指向外部的符号链接都被拒绝。读取只接受 UTF-8 普通文件；文件最大 1 MiB，单次返回最多 64 KiB，可按行读取。edit_file 要求 old 非空且唯一出现，避免误改多个位置。所有创建、覆盖和精确替换均展示差异并确认；已有文件必须先读取，并检查读取后是否发生变化。

命令工具接受 argv 数组，不拼接 shell 字符串。例如 `['python3', '-c', 'print(1)']`。shell=False 不代表系统沙箱：被执行程序仍可读写当前用户可访问的文件。

本章的同步命令在默认 confirm 策略下要求交互确认，批处理默认拒绝。第 10 章增加显式命令白名单和独立后台工具。命令超时后清理进程组；读取输出时只保存限额内的数据，继续排空多余数据，防止管道阻塞和内存无限增长。同步命令遗留的后台进程会被清理；需要跨终端存活的有界任务使用第 10 章的 start_command。

无需密钥运行边界测试：

```bash
python -m pytest tests/test_tools.py -q
```

练习：为不存在的文件、非 UTF-8 文件和重复匹配添加测试，观察它们如何变为模型可以理解的失败结果。路径检查不抵御同时发生的恶意符号链接替换，不要把本项目当安全隔离系统。


## docs/tutorial/05-conversation.md

# 05：多轮历史与可观察事件

阅读 [agent.py](../../src/fast_agent/agent.py) 的 history 和 emit，以及 [cli.py](../../src/fast_agent/cli.py) 的 show_event。

历史中保留 system、user、assistant 和 tool 四类消息。再次输入问题时，这些消息一起传给模型，所以它可以了解之前发生了什么。reset 会只留下系统消息，不回滚文件内容。

事件与历史的用途不同：历史用于模型上下文，事件用于向用户展示当前执行过程。model_start 表示开始调用；tool_start/tool_end 展示参数和结果；answer/error 记录结局。CLI 限制单个工具事件的展示长度，历史仍保留工具限额内的结果。

无需密钥运行：

```bash
fast-agent --mock
```

依次输入任意文本、`/reset`、`/exit`。模拟模型只说明自身用途；真实多轮推理需要接入真实模型。

执行期间 Ctrl+C 会补齐尚未完成调用的错误结果，防止下一轮发送无对应结果的工具请求。已执行的修改不自动撤销。现在可用 /save 和 /load 保存恢复，用 /trim 按整轮裁剪；超出配置预算时会自动摘要旧轮次，详见 [第九章](09-compaction-streaming.md)。详见 [第七章](07-context.md)。长对话仍可能超过模型上下文。

## docs/tutorial/07-context.md

# 07：保存、恢复与裁剪上下文

模型每次收到的请求都包含消息历史。本章先讲解 Python API 的内存历史和手动会话保存；当前 CLI 还会自动保存任务检查点，关闭终端后可恢复，详见第 10 章。会话保存把消息写到磁盘；恢复把它们重新加载到新的 Agent。这里没有训练模型，也没有自动重放工具。

## 亲自操作

```bash
fast-agent --mock --workspace /你的练习目录
```

依次输入：

```text
你好
/history
/context
/save first
/reset
/load first
/context
/trim 0
/exit
```

文件保存在工作目录的 `.fast-agent/sessions/first.json`。只保存版本、工作目录和消息，不保存 API 配置或密钥。消息本身可能包含用户输入和代码，因此文件权限为 600，本项目的该目录已加入 Git 忽略（在其他仓库使用时也应忽略 `.fast-agent/`）；不要把敏感内容随意发给模型或分享会话文件。

恢复后默认进入计划模式，历史中的执行同意不会成为当前授权。需要修改时在终端输入 `/execute`；启动权限为 read-only 时不能提升。详见 [第十二章](12-plan-execute.md)。

## 为什么不能直接删除前 N 条消息

一轮 user 消息后可能有多个 assistant 工具调用与 tool 结果。只保留最后几条可能让结果失去对应调用 ID，导致下次模型请求失败。

[sessions.py](../../src/fast_agent/sessions.py) 的 trim_history 按 user 开始的一整组消息裁剪，保留开头的 system 消息。`/trim 2` 保留最近两组，包括组内所有工具请求及结果；`/trim 0` 只保留系统消息。中断或请求失败的轮次可能尚未获得最终回复，但只要工具结果配对完整，也允许保存和恢复。

`/context` 分别显示轮数和完整回复轮数。JSON 字符数是可理解的粗略体积指标，不是模型 tokenizer 的精确 token 数，也没有计入工具定义。现在也支持自动摘要，详见 [第九章](09-compaction-streaming.md)。手动裁剪会遗忘早期目标；重要需求应重新告诉模型。文件中的既有保存不会随内存裁剪自动改变，需要再次 /save。

## 保存与恢复的正确性

保存先写同目录临时文件，flush 和 fsync 后再原子替换，写入失败不会破坏原会话。加载检查版本、工作目录、字段类型和每个工具调用的配对；所有检查通过才替换当前 history。工作目录不同则拒绝，防止恢复后把工具用于另一个项目。

同名 /save 会原子覆盖原会话。会话目录和文件拒绝符号链接；这仍不是抵御恶意并发文件系统修改的完整沙箱。

## 用真实模型验证跨进程恢复

配置好真实模型后，在项目根运行：

```bash
source .env
.venv/bin/python examples/real_session_demo.py
```

父进程生成一个随机目标标题。第一个独立进程把标题告诉模型，只读取 note.txt，然后保存会话并退出。第二个独立进程只收到工作目录，不收到目标标题；它通过 `restore_history` 加载历史进入计划模式，再由演示宿主显式 `set_mode("execute")`，重新读取文件建立当前修改指纹，再继续上一轮任务，编辑并复读文件。确认回调仅批准临时 note.txt 的修改。最后父进程核对随机标题、正文与工具顺序。

这个演示复用真正的 SessionStore、Agent 和模型接口；完成后清理临时文件。它同时证明：消息跨进程持久化、上下文恢复、工具调用 ID 的序列结构有效，以及恢复后的真实修改结果正确。


## docs/tutorial/08-repository.md

# 08：从工具演示到本地仓库开发

现在可以把 Fast Agent 指向一个代码仓库，完成“检索 → 阅读规则和源码 → 复现失败 → 确认修改 → 运行测试 → 检查差异”的流程。

```bash
source .env
.venv/bin/fast-agent --workspace /你的代码仓库 --max-steps 20
```

输入一个具体任务，例如：“定位并修复单元测试中的失败。先复现，再做最小修改，不要改测试，完成后运行测试并检查 Git 差异。”读取和检索直接执行；每次文件修改与任意命令执行都要求终端确认。

## 发现代码与分段读取

- `list_files(path?, limit?)`：列出文件，默认最多 100 项，最大 500。
- `search_code(query, path?, limit?)`：固定文本搜索，返回路径、行号和片段。不是正则表达式搜索。
- `read_file(path, start_line?, end_line?)`：行号从 1 开始，包含结束行。文件最多 1 MiB，每次返回内容最多 64 KiB；超限时要求缩小范围。

检索需要安装 ripgrep，例如 macOS 用 `brew install ripgrep`。工具通过 `rg --no-config --no-follow` 调用，避免用户配置隐式启用符号链接跟随或预处理程序。遵循忽略规则，同时排除 .git、.venv、venv、node_modules、.fast-agent、.idea、__pycache__ 和 .env*。搜索文件上限 1 MiB，进程输出上限 64 KiB，执行超时 10 秒；返回 truncated 时结果不完整。

列表/搜索默认排除凭据文件不代表通用密钥识别。用户明确请求 read_file 的其他文件仍可能含敏感信息，真实服务会收到工具返回的数据。

## AGENTS.md 如何进入上下文

[workspace.py](../../src/fast_agent/workspace.py) 将工作目录根的 AGENTS.md 放入系统消息；每轮任务前刷新。读取某文件时，还会将从工作目录到该文件父目录沿途的规则放入工具结果，越靠近目标文件的规则越具体。

新增文件前先调用 `read_instructions(path)`。存在适用规则时，write_file 会检查模型是否已读取这些规则。规则合计最多 64 KiB，拒绝规则文件符号链接。这里的根是用户指定的 --workspace，不会自行扫描它上方的私人目录。

规则内容是给模型的项目约定，不是权限沙箱。模型仍可能理解错误；真正修改和命令执行必须经用户确认。验证样本独立核对了“不可修改测试”和“保留接口、补中文注释”等规则的效果。

## 修改前后检查

[file_tools.py](../../src/fast_agent/file_tools.py) 在 read_file 时记录整份文件内容哈希及规则指纹。edit_file 和覆盖已有文件要求先读取：

1. 检查当前内容与读取记录一致，规则未改变。
2. 生成 unified diff，展示并请求确认；新建文件也需要确认。
3. 确认后再次检查内容与规则。
4. 在同目录写临时文件、保留原权限、flush/fsync 后原子替换。

如果外部编辑器修改了文件，操作拒绝覆盖，需重新读取。差异超过 64 KiB 时要求拆分修改。这个流程降低误覆盖风险，不提供针对恶意并发文件系统修改的锁或完整沙箱。

保存会话只保存消息，不保存读取指纹。恢复会话或 /reset 后，修改文件前必须重新读取，以当前磁盘内容为准。

## 运行测试与查看 Git

`run_command` 仍要求每次确认，接受 argv 数组，不使用 shell。工作目录限定不等于系统访问隔离；确认前要检查命令。该工具适合短任务，默认 10 秒、最大 60 秒，结束时清理同组后台进程。

`git_status` 和 `git_diff(path?, staged?)` 是无需确认的检查工具，范围限定在工作目录。Git 外部 diff、textconv、fsmonitor、clean 和 process 过滤器被禁用，避免检查操作执行仓库配置中的程序。禁用过滤器后看到的是原始工作区文本，使用 LFS/自定义过滤器的项目可能与日常 Git 展示不同。未跟踪文件只显示在 status，不会自动出现在 diff 中。

## 可重复的真实模型验证

```bash
source .env

```

脚本创建临时 Git 仓库，其中 add 错写成减法，两个 unittest 都失败。MiniMax 必须检索、读取规则、先运行失败测试，再修改源码、重新测试并查看 Git 差异。

演示的确认回调只批准该样本源码的修改和一条固定的 unittest 命令；不是全局自动批准。验证程序独立检查测试确实通过、测试文件未变、仅预期源码发生差异，并要求实际调用检索和 Git 工具。临时仓库自动清理，结果留在项目 `.fast-agent/validation/repository-demo.json`。

这是本地仓库开发基础版本：现已支持终端流式输出和自动摘要（第九章），仍缺少完整沙箱、长任务后台管理或生产级恢复保证，不等同于 Claude Code 的全部能力。

## docs/tutorial/09-compaction-streaming.md

# 09：自动压缩上下文与流式交互

Agent 的历史随着工具执行增长，等待完整回复也会让终端显得没有反应。本章分别解决历史体积和输出延迟，核心循环仍然是“请求模型 → 执行完整工具调用 → 回传结果”。

## 开始使用

```bash
source .env
.venv/bin/fast-agent --workspace /你的仓库 --max-steps 20
```

真实模型默认流式输出；模拟模型没有流式接口时自动回退普通输出。自动压缩默认阈值为 60000 个请求 JSON 字符，保留最近 2 轮原始对话。这不是模型的精确 token 数或服务端上下文上限。

```bash
# 更早触发压缩，并保留最近一轮（包括当前用户任务）
.venv/bin/fast-agent --context-chars 20000 --keep-rounds 1
# 关闭流式输出
.venv/bin/fast-agent --no-stream
# 关闭自动压缩，仍可使用 /trim
.venv/bin/fast-agent --context-chars 0
```

## 自动压缩发生在哪里

[agent.py](../../src/fast_agent/agent.py) 在每次任务模型调用前检查消息和工具定义的序列化字符数。超过预算时调用 [compaction.py](../../src/fast_agent/compaction.py)：

1. 按 user 消息划分轮次，保留最近 N 轮的所有消息，工具请求和结果不拆开。
2. 把更早的消息作为数据交给同一个真实模型，要求总结目标、约束、路径、关键数值、已完成验证和未完成事项。摘要调用不提供工具。
3. 检查摘要有内容、没有工具请求、长度合适，而且替换后确实缩小并满足预算。
4. 将原始完整会话备份到 `.fast-agent/sessions/auto-<随机编号>.json`。
5. 备份成功后才替换内存历史，显示压缩前后字符数和备份路径。

摘要以一组明确标注的 user/assistant 历史记录放在 system 之后。它不替换当前的系统规则；重复压缩时旧摘要一起参与重新整理，不无限堆叠。最近原始轮次仍按协议原样保留。/history 可以查看摘要，/save 和 /load 继续使用原有格式，不需要新会话格式。

摘要是有损信息整理，不保证逐字保留所有细节。需要找回原始事实时可用 `/load auto-编号` 恢复备份（加载不重放工具）；也可提高预算或关闭自动压缩。摘要可能遗漏信息，因此关键修改仍要重新读文件并验证结果。

## 为什么有时会停止而不是强行压缩

摘要调用失败、超长、请求工具、无效或备份失败时，当前轮次明确报错，原历史不被覆盖。不会无上限重试，也不会默默删除对话。

待摘要输入最多 100000 字符，摘要最多为预算的四分之一且不超过 8000 字符。如果最近保留轮次、系统规则或工具定义本身已经很大，仍可能无法满足预算；单个正在执行的轮次不会从中间拆开。这时需要更小的文件读取范围、提高预算、调整 --keep-rounds 或手动 /trim。

自动摘要会额外调用一次模型，增加耗时和费用；它不计入任务模型循环的 max-steps。每次任务模型调用前至多尝试一次压缩，失败会停止本轮。字符预算用于可理解的教学策略，不是对任意模型上下文大小的保证。

## 流式输出如何工作

[providers.py](../../src/fast_agent/providers.py) 的 complete_stream 给 Chat Completions 请求增加 `stream=True`。SDK 返回增量事件，交给 [streaming.py](../../src/fast_agent/streaming.py) 处理。

文本片段通过 text_delta 事件立即交给终端显示。一段可能是几个字或标点，不等于一个 token。最终回答不再重复打印。程序仅处理 content 文本字段；供应商把额外标签混入 content 时，它们也可能显示。

工具调用参数也可能分多段到达，例如：

```text
片段 1：index=0，id=call_A，name=read_file，arguments={"pa
片段 2：index=0，arguments=th":"note.txt"}
结束标记：finish_reason=tool_calls
```

程序按照 index 合并 id、名称和 arguments，等到正常完成标记，再校验调用 ID 和 JSON 参数。只有这些检查通过后，Agent 才执行工具。

连接中断、缺少结束标记、length/content_filter、无效参数等情况都会拒绝执行本次回复中的工具。已显示的部分文本可能不完整，终端会同时显示失败信息；不把半截回复加入历史。已经完成的前几次工具操作不会回滚。

Ctrl+C 会关闭当前流；如果发生在工具执行阶段，仍按原有机制补齐中断结果，保留可继续使用的消息结构。流式回复总量最多 1 MiB、最多 128 个工具调用，避免无界累积。

## 一次完整的真实模型验证

```bash
source .env
.venv/bin/python examples/real_context_stream_demo.py
```

演示使用三个独立进程：

1. 第一进程告诉模型一个随机目标标题及较长背景，保存会话。
2. 第二进程加载历史，不直接获得随机标题；较低预算触发真实模型摘要，随后以流式工具调用读取、修改、复读 note.txt，并保存压缩后的会话。
3. 第三进程加载压缩后的会话，要求只回答之前的标题，验证跨进程保留了关键信息。

父进程检查磁盘内容、工具顺序、多个真实文本增量、摘要事件、原始备份、不同 PID 和恢复后的标题。临时目录随后清理，报告留在 `.fast-agent/validation/context-stream-demo.json`。

这验证的是一次可重复的小型端到端场景，不代表摘要对所有长任务都无损。大型仓库仍应结合分段读取、测试和差异审查。

## 本次真实验证（2026-10-19）

MiniMax-M3 在三个独立进程中完成验证，总耗时 56.55 秒。请求字符数由 19475 降到 3722，备份原始会话 1 份；压缩后执行 read_file → edit_file → read_file，磁盘随机标题正确且正文未变。第三个进程恢复压缩后的会话，准确回答同一个随机标题。

三个阶段分别收到 40、111、12 个真实 content 增量，共 163 个；任务模型调用共 6 次，另有 1 次摘要调用。临时文件已清理，JSON 报告保留在项目 Git 忽略目录。自动化测试共 111 项通过，包含缺少结束标记、断流、截断、参数无效、摘要失败、重复压缩和 CLI 不重复输出。

后续 [第 16 章](16-active-compaction.md) 扩展了单次任务内部的压缩：在完整工具批次边界摘要较早结果，保留当前用户要求和最近一批原始证据。


## docs/tutorial/10-tasks-jobs-permissions.md

# 10：任务恢复、后台命令与权限

这一章把 Agent 循环扩展成可以中断、检查和继续的本地工作流程。模型负责提出下一步，宿主程序负责保存证据、执行权限和进程生命周期。

## 从会话到任务检查点

`/save` 保存的是会话。任务检查点额外记录本轮状态、操作结果是否确定，以及权限决策。CLI 默认启用，每次输入任务会显示一个 ID，并将检查点原子写入 `.fast-agent/tasks/`。Python API 通过 `Agent(..., checkpoints=True)` 开启。

一次调用的顺序是：

1. 将用户消息保存，然后请求模型。
2. 收到完整的工具调用，执行前保存检查点。
3. 执行工具，将带 `tool_call_id` 的结果追加到历史。
4. 再次保存，然后请求模型决定下一步。

磁盘快照始终是一组完整配对的消息：尚未执行的调用使用“未执行”结果占位，正在执行的修改使用“结果未知”占位。内存中的正常执行历史使用实际结果。这样即使进程直接退出，恢复后的消息仍符合模型协议。

```text
/tasks
/resume <任务ID>
/execute
继续检查结果并完成任务
```

也可以重新启动：

```bash
fast-agent --workspace /你的仓库 --resume <任务ID>
```

恢复只加载历史，不执行历史里的工具，并进入计划模式。可继续只读检查；需要修改时由用户输入 `/execute`，仍遵循启动权限。重新读取文件后才能编辑，之前的读取指纹不会恢复。已完成的操作结果告诉模型哪些步骤已经做过；程序不会自动重放旧调用，但不能保证模型永远不会提出新的重复操作，修改仍受权限控制。

## 为什么“结果未知”不能等同于失败

考虑：文件已经替换成功，但程序在保存工具结果之前退出。再次执行同一条追加命令可能重复写入。跨进程保存和外部副作用不在同一个事务里，所以这里不承诺“恰好执行一次”。

有未知结果时，整个工作目录的后续修改与命令都会被阻止；读取和检查仍可使用。新建任务、`/reset` 或 `/load` 不会解除阻止。人检查实际文件、Git 差异、命令日志后，显式记录处理结论：

```text
/resolve <任务ID> 已检查文件和测试日志，修改已完成，不需要重放
```

`/resolve` 是终端命令，不是模型工具。它不会撤销修改或执行命令，也不验证用户说明是否真实。工作目录内同时只允许一个启用检查点的 Agent 主循环；后台命令可以继续并发运行，因此仍要注意外部文件变化。

## 后台命令如何工作

`run_command` 保留原有同步语义，最大 60 秒。新工具为：

| 工具 | 作用 |
| --- | --- |
| `start_command(argv, timeout?)` | 启动独立执行器，立即返回 `job_id`；默认 300 秒，最多 3600 秒 |
| `poll_command(job_id, offset?, wait_seconds?)` | 返回状态、退出码、日志；单次最多 64 KiB，可等待最多 10 秒 |
| `cancel_command(job_id)` | 经确认写入取消请求，执行器终止命令进程组 |

终端查询不消耗模型请求：

```text
/jobs
/job <任务ID>
/job <任务ID> <next_offset>
/cancel <任务ID>
```

日志偏移以字节为单位；分块 UTF-8 边界可能显示替代字符。每个命令最多保存 1 MiB 日志，多余输出继续读取但不保存，`truncated=true` 表示丢弃发生。状态 `succeeded` 且 `returncode=0` 才表示命令成功；查询接口的 `ok=true` 仅表示查询成功。

关闭终端后独立执行器继续工作。它每半秒保存心跳；超过 10 秒无心跳会显示 `unknown`，不能据此重新启动命令。失联任务同样阻止后续修改；人工检查后使用 `/resolve-job <任务ID> <核实说明>` 解除阻止。核实记录不启动或终止命令。取消通过文件请求完成，不使用历史 PID 直接杀进程，避免误杀复用 PID 的其他程序。若执行器被强制杀死或机器重启，无法保证清理已脱离其控制的子进程，需人工检查。主动退出进程组的程序也不受普通进程组清理保证。

## 权限是本地决策

```bash
fast-agent --workspace /你的仓库 --permissions read-only
fast-agent --workspace /你的仓库 --permissions confirm
fast-agent --workspace /你的仓库 --permissions restricted --allow-commands /可信位置/commands.json
```

- `read-only`：允许内置读取、检索、Git 状态与后台查询；拒绝编辑、启动和模型发起的取消。用户输入 `/cancel` 是独立的显式取消请求。
- `confirm`：默认策略，文件修改展示差异后确认，命令逐次确认。非交互输入默认拒绝这些操作。
- `restricted`：精确匹配 `argv` 数组的命令自动获准，其余修改仍需交互确认；无交互时拒绝。不是命令前缀匹配。

白名单文件示例：

```json
{"commands": [["/绝对路径/python", "-m", "unittest", "discover", "-s", "tests"]]}
```

白名单在启动时由用户指定并读取，模型不能通过工具参数更改它。测试本身也能执行代码；精确参数匹配并不限制程序内部的行为。文件编辑仍保留原有差异确认和外部变化检查。注册自定义工具时默认按修改类处理，只有真正无副作用的工具才应声明 `effect='read'`。自定义修改工具也应在副作用之前调用 `context.authorize()`；只有能确定尚无副作用的校验错误才使用 `ToolInputError`，其余异常保守视为未知结果。文件编辑工具禁止修改 `.fast-agent` 运行记录和 `.git` 内部数据。

检查点内的 `audit` 保存批准/拒绝与目标，消息保存工具参数和结果；不复制 API 密钥或整个环境，但用户输入与工具输出本身仍可能含敏感内容。运行目录已被 Git 忽略，文件默认 0600。后台执行器不继承 `FAST_AGENT_API_KEY`，其他环境继承；同步命令仍继承环境。这些功能不是操作系统沙箱，也不防御同一用户恶意修改运行记录或并发替换符号链接。

## 对照代码阅读与验证

从 `agent.py` 的 `checkpoint()` 看写前记录，再看 `tasks.py` 的未知结果占位和 `resolve()`；`tools.py` 先检查只读/未知结果限制，具体编辑与命令通过 `ToolContext.authorize()` 作权限决策。`jobs.py` 创建句柄和查询记录，`job_worker.py` 独立管理命令生命周期。

```bash
source .env
python examples/real_reliability_demo.py
```

验证器只操作临时目录：真实模型读取并编辑文件、启动后台测试；宿主在启动结果已保存后模拟中断；第二个进程恢复并查询原任务，核对命令只执行一次；第三个进程启动并取消另一个任务。最终断言检查文件、退出码、测试日志、执行次数和进程 ID，不依赖模型的“完成”措辞。未知副作用和进程直接退出的路径另由离线自动测试覆盖。


## docs/tutorial/11-model-request-reliability.md

# 11：模型请求的超时、重试与执行边界

真实模型请求会遇到连接失败、限流和服务端临时故障。工程化 Agent 需要有界恢复，同时保证恢复网络请求时不会重新执行已经完成的文件修改或命令。本章在模型适配层实现这条边界。

## 配置与默认值

配置从当前进程环境读取，不扫描其他项目的凭据，也不自动加载 `.env`。

```bash
export FAST_AGENT_CONNECT_TIMEOUT=10
export FAST_AGENT_READ_TIMEOUT=60
export FAST_AGENT_MAX_RETRIES=2
fast-agent --workspace /你的仓库
```

| 变量 | 默认值 | 允许范围 | 含义 |
| --- | --- | --- | --- |
| `FAST_AGENT_CONNECT_TIMEOUT` | 10 秒 | 大于 0，最多 120 秒 | 连接超时，也用于写入和连接池等待 |
| `FAST_AGENT_READ_TIMEOUT` | 60 秒 | 大于 0，最多 600 秒 | 等待响应数据的读取超时 |
| `FAST_AGENT_MAX_RETRIES` | 2 | 0～5 的整数 | 初次请求之外的重试次数；0 表示禁用 |

读取超时不是整个任务的总时长限制。流式响应持续收到数据时，可以运行超过这个时长；`--max-steps` 仍限制 Agent 的决策步数。配置为 2 次重试意味着一次决策最多发出 3 次 HTTP 请求。非有限数、负数、零超时和超限配置会在启动时被拒绝。

Python API 也可以使用 `Config(..., connect_timeout=10, read_timeout=90, max_retries=1)`。正常构造模型时会把这些值传给 SDK；若显式注入已有 SDK client，则连接参数由该 client 的创建者负责。

## 哪些情况可以重试

`request_policy.py` 只接受明确的临时故障：

- SDK 连接失败、超时，以及流读取过程中尚未收到任何片段时的网络/远端协议传输异常。
- HTTP 429、500、502、503、504。

401/403、请求参数错误、其他 HTTP 状态、工具参数不合法、模型回复缺少结束标记等情况不自动重试。程序异常也不会因为碰巧有一个 `status_code` 字段就被当成网络故障。

默认按约 1、2、4、8、16 秒指数退避，并加入 0.8～1.2 倍随机抖动；单次等待不超过 30 秒。有效的 `Retry-After` 秒数或 HTTP 日期优先；服务要求等待超过 30 秒时直接结束本次请求，不提前请求。无效头部回退到有界退避。

终端会显示：

```text
[重试] 请求受限，请检查配额或稍后重试。 等待 2.0 秒，准备第 2/3 次请求
```

日志只包含本地生成的中文原因、次数和等待时间，不展示供应商原始错误、请求头或密钥。重试用尽时说明实际尝试次数。等待期间 Ctrl+C 可以中断。

SDK 自带重试被设为 0，由 Fast Agent 统一管理；否则两层重试可能相乘，次数和等待就难以理解。

## 流式回复一旦开始，就不能悄悄重来

假设屏幕已经显示“正在修改”，随后连接断开。重新生成可能输出另一段文本，甚至提出不同的工具参数。因此采用保守边界：**收到任何流式片段后，停止自动重试**。

“任何片段”包括文本、工具参数、角色、推理或用量片段，即使它尚未显示给用户。这也意味着某些看似没有文字的请求仍然不能自动重试。失败提示会说明已收到响应内容，当前响应中的工具没有执行。

只有完整、正常结束并通过校验的工具调用才会交给 Agent。失败流会关闭，部分文本不会作为完整 assistant 消息加入历史，部分工具调用不会执行。用户可检查状态后发起新的任务；程序不会拼接两次生成的工具参数。

## 为什么重试不会重放工具

看 `agent.py` 和 `providers.py` 的分工：

```text
Agent 请求模型
    ↓
模型适配器尝试 HTTP 请求，必要时重试同一份 messages/tools
    ↓
收到完整 ModelReply
    ↓
Agent 执行工具一次，保存 tool_call_id 对应结果和检查点
    ↓
下一次模型请求把工具结果一并发送
```

重试循环包围的是 `chat.completions.create` 和响应读取，不包围 `Agent.run`，也不调用 `ToolRegistry.execute`。如果工具已完成、下一次模型请求遇到 503，重发的是包含既有工具结果的消息，之前的工具不会再次执行。

重试模型请求仍可能重复产生服务端生成费用，因为客户端超时不能证明服务端没有处理请求。这里保证宿主程序不因重试而重放工具，不承诺模型服务端恰好处理一次，也不能阻止模型在后续完整回复中主动提出新的重复操作。

自动上下文摘要同样使用这个模型适配器，因此也遵循超时和重试策略。摘要失败时仍保留原历史；成功后的原始会话备份机制不变。

## 如何验证

离线故障注入与真实服务验证分开完成：

```bash
python -m pytest -q
source .env
python examples/real_repository_demo.py
python examples/real_context_stream_demo.py
```

自动测试使用真实 SDK 的内存 HTTP 传输，模拟首次 503、第二次正常 SSE，检查请求内容一致且文字只输出一次。其他用例覆盖认证拒绝、重试耗尽、连接失败、Retry-After、等待中断、流式片段后的失败，以及工具副作用只发生一次。

MiniMax 验证器不伪造服务故障。仓库验证器让模型检索代码、复现失败测试、修改源码、重跑测试和检查 Git 差异。上下文验证器跨三个进程完成记忆、自动摘要、流式工具调用和保存后的恢复，并核对随机目标标题。报告记录实际超时配置和 `model_retry` 事件；没有事件就表示该次真实运行未发生自动重试，不能用故障注入结果冒充真实服务行为。

报告位于 Git 忽略的 `.fast-agent/validation/`。每次启动这两个验证器会移除上一份同名报告，避免一次失败留下旧的成功结果。原始运行日志仍可单独保存。


## docs/tutorial/12-plan-execute.md

# 12：计划模式与执行模式

工程任务可以先理解代码、列出方案，再执行修改。这里把“当前交互模式”和“启动权限”分开：模式决定模型现在能做什么，启动权限决定执行阶段最多允许什么。

## 亲自操作

```bash
source .env
fast-agent --workspace /你的仓库 --plan
```

依次输入：

```text
分析这个问题，只读代码，给出修改文件、步骤和验证命令
/save repair-plan
/execute
按刚才的计划实施，先复现问题，再修复并验证
/plan
检查最终差异并总结
```

`/execute` 只切换状态，不请求模型，也不立即执行计划。下一条自然语言输入才启动新一轮 Agent 循环。计划是普通历史消息，不是可直接运行的脚本，也不是已经批准的补丁；实际修改仍展示差异并按现有权限确认。

## 两层约束如何配合

| 启动权限 | 计划模式 | 切换执行后 |
| --- | --- | --- |
| confirm | 仅只读工具 | 修改和命令继续逐次确认 |
| restricted | 仅只读工具 | 恢复原来的精确 argv 命令白名单及修改确认 |
| read-only | 仅只读工具 | `/execute` 拒绝提升权限 |

`workspace.system_prompt` 告诉模型当前模式，要求计划用中文说明目标、依据、涉及文件、步骤、验证方式和待确认问题。没有运行测试时必须说明只是推断。

提示词不是权限保障。`Agent.tool_schemas()` 在计划模式只发送 `effect='read'` 的工具定义；`ToolRegistry.execute()` 又在执行前检查真实工具的 effect。即使模型虚构写入调用，宿主也会拒绝。`ToolContext.authorize()` 同样检查当前模式，保护需要授权的内置处理函数。自定义工具默认按写操作处理，只有确实只读的工具才应标记为 read；插件实现仍属于可信宿主代码。

模型没有 `/execute` 工具。终端命令由 `session_commands` 在本地处理，历史消息中的“已经同意执行”不会改变权限。

## 切换和恢复为什么要重新读取

`Agent.set_mode()` 更新 system 消息，并清空文件与规则的读取指纹。切换执行后，模型必须重新读取目标文件和沿途 AGENTS.md，之后才能编辑；计划阶段读过的版本不能直接作为修改依据。现有外部修改检查和差异确认继续生效。

`/load`、`/resume`、`--resume` 都重新生成当前工作目录的系统消息并进入计划模式，即使保存的是执行中的历史也如此。恢复不重放旧工具。`/reset` 和 `/trim` 不会退出计划模式，`/execute` 也不会解除“操作结果未知”的阻止；未知结果仍要人工检查并通过原有处理命令记录结论。

Python 宿主应使用恢复 API，而不是直接赋值 history：

```python
agent = Agent(model, registry, context, plan=True)
agent.restore_history(store.load('repair-plan'))  # 校验并进入计划模式
agent.set_mode('execute')  # 可信宿主明确发起；不能交给模型调用
result = agent.run('重新读取文件，然后实施计划')
```

一次性 `--resume ID --prompt '检查进度'` 只会进行计划模式分析。需要执行修改时进入交互终端后输入 `/execute`。

## “只读”的准确范围

计划模式约束模型对项目的操作。会话和检查点仍可写入 `.fast-agent/`，已有后台任务也不会自动暂停。本地 `/cancel ID` 是用户明确发起的控制，仍可取消后台任务；模型的 `cancel_command` 工具在计划模式不可用。该机制没有提供操作系统沙箱，也不能约束其他进程或不可信的自定义 Python 代码。

## 用 MiniMax 验证完整链路

```bash
source .env
.venv/bin/python examples/real_plan_demo.py
```

演示创建临时 Git 仓库和两个失败测试。第一个独立进程让真实模型只读规划，并保存会话与检查点；父进程核对源文件、测试、规则文件的哈希与 Git 状态，并确认规划时没有授权回调。

第二个进程分别恢复会话和检查点，核对两次都进入计划模式，再通过本地 `/execute` 明确切换。模型重新读代码、运行失败测试、修改加法实现、重跑测试并检查 Git 差异。宿主仅允许目标源文件和精确测试命令，最后独立验证两个测试通过、测试文件未修改、差异仅涉及目标源文件。

结果写入 `.fast-agent/validation/plan-demo.json`，过程事件写在运行输出中。真实模型验收检查正常工作链路；伪造写入调用、只读权限不能提升、恢复不继承授权等拒绝路径由 `tests/test_plan_mode.py` 的确定性测试覆盖。

## docs/tutorial/13-multi-edit.md

# 13：批量精确编辑

同一文件里的多个相关修改，可以交给 `multi_edit_file` 一次处理。例如同时修复两个函数，避免第一处已写入、第二处匹配失败时留下半成品。

## 工具参数

先通过 `read_file` 读取目标文件和适用规则，再提交：

```json
{
  "path": "src/math_utils.py",
  "edits": [
    {"old": "return a - b", "new": "return a + b"},
    {"old": "def multiply(a, b):\n    return a + b", "new": "def multiply(a, b):\n    return a * b"}
  ]
}
```

数组包含 1 到 100 项，按顺序执行。每个 `old` 必须非空，并且在**前面替换完成后的内存文本**中唯一匹配。第一处替换可以生成第二处要匹配的文本；如果匹配多个位置，需要扩大 `old` 的上下文。不会模糊匹配，也不会默认替换所有匹配项。

## 从模型请求到磁盘写入

1. 注册表检查参数结构、类型和当前执行权限。计划模式不向模型提供此工具，也拒绝其伪造调用。
2. `checked_before` 检查读取记录、文件哈希和沿途 AGENTS.md，防止用过期计划覆盖当前内容。
3. `multi_edit_file` 在内存依次替换；任何一项失败，返回其序号，整个批次不写入、不请求确认。
4. 全部成功后，复用 `commit_text` 展示原文件与最终内容的整体 diff，只确认一次。
5. 确认后再次检查文件与规则，写入同目录临时文件，刷新后用 `os.replace` 替换目标文件。
6. 工具结果通过原有 `tool_call_id` 返回模型；模型继续读取、测试、检查 Git 差异。

每一步的内容仍受 1 MiB 文件上限约束，最终 diff 上限为 64 KiB。超出上限会拒绝，不会截断修改。最终内容与原文件相同时返回 `changed=false`，不请求写入确认。成功修改后更新读取指纹，后续编辑仍会检测外部变化。

## 边界与恢复

这是**单个文件**的批量原子替换，不是跨文件事务。它沿用既有确认策略，不增加自动批准权限；`/execute` 后仍需批准实际 diff。运行记录和 Git 内部文件仍禁止由编辑工具修改。

确认期间文件变化会导致拒绝，保留外部修改。若进程在写入与检查点记录之间中断，仍按第 10 章的“结果未知”处理：先检查实际文件，不能盲目重放整个批次。本机制也没有消除并发符号链接替换风险，不是操作系统沙箱。

## docs/tutorial/14-command-streaming.md

# 14：命令执行实时输出

模型的流式回复与命令的实时日志是两条独立通道。前者来自模型服务，后者来自本机子进程。运行测试时，即使模型还没收到结果，终端也可以先展示进度。

## 执行顺序

1. 模型提出 `run_command`，宿主仍先检查计划模式、权限和用户确认。
2. `execute_process` 使用管道合并 stdout/stderr，通过 selector 持续读取。
3. 每段保留下来的字节经 UTF-8 增量解码，通过 `command_output` 事件展示并刷新终端。
4. 命令退出或超时后，清理进程组，发出 `command_output_end`。
5. 最终 `tool_end` 携带输出、退出码、截断标志和错误。Agent 只把这一条配对的工具结果加入历史，之后继续请求模型。

CLI 不会在最终工具事件里重复打印已经流式展示的日志正文。Python 事件订阅者仍能从 `tool_end` 取得完整限额内结果。`--no-stream` 关闭模型文字流式回复，不关闭命令日志。

## 中文分块与输出上限

管道读取边界可能落在一个汉字的 UTF-8 字节中间。增量解码器暂存不完整字节，下一段到达后再输出，避免正常中文因分块变成乱码。结束时遇到确实不完整或无效的编码，使用替代字符。

实时展示与最终结果共享原有 64 KiB 字节上限。超过后继续排空管道，防止子进程卡住，但不继续显示或累计超量内容；结果中的 `truncated=true` 明确说明截断。截断恰好切断字符时，末尾可能出现替代字符。

终端展示转义控制字符，保留换行与制表符。程序自己的缓冲仍然有效：Python 命令可用 `-u`，或在输出时设置 `flush=True`。这不是伪终端，不支持交互式命令输入；日志也不会自动恢复被截断的部分。

## 中断和失败

非零退出与超时仍返回失败结果，并保留已收到的输出。Ctrl+C 会清理同组进程；Agent 按原有机制保存中断状态，对可能已经发生的修改标记结果未知。实时日志是观察证据，不代表命令成功，也不是自动授权。

事件回调在执行线程同步调用，应快速返回。宿主回调异常会停止执行并触发进程清理，不能把显示异常当作命令成功。后台命令继续使用第 10 章的日志轮询机制。

## 运行与验证


MiniMax 在临时仓库中完成只读规划、恢复后显式执行、复现失败测试、批量修复、重跑测试和检查差异。测试每次输出中文进度并稍作等待；宿主检查流式片段与最终工具结果一致、命令结束事件数量正确。第三个独立进程恢复执行后的会话，只读核验。

## docs/tutorial/15-command-logs.md

# 15：长日志保留与按需读取

测试或构建可能输出很多背景信息，真正的错误却在末尾。只保留前 64 KiB 会漏掉这些证据。本章在同步命令的实时输出之外，增加磁盘日志和只读分页工具。

## 三个独立上限

| 内容 | 上限 | 含义 |
| --- | --- | --- |
| 终端实时显示 | 64 KiB | `display_truncated=true` 表示实时展示不完整 |
| 最终工具结果的 output | 4 KiB | `truncated=true` 表示传回模型的正文不完整 |
| 磁盘日志 | 1 MiB | `storage_truncated=true` 表示磁盘也未保存后续输出 |

日志存入工作目录的 `.fast-agent/command-logs/`，使用随机 ID，文件权限为 600。`run_command` 的结果增加 `log_id`、`stored_bytes` 和 `storage_truncated`，原有退出码及失败原因保持不变。模型首先收到前缀输出和这些状态信息，不会自动收到全部日志，也没有额外调用模型生成摘要。

存储保留的是前 1 MiB，超过容量后继续排空进程管道但丢弃后续字节。因此，存储已截断时，读取尾部得到的是“已保存部分的尾部”，不能宣称看到了真实输出的最终错误。应缩小测试范围或调整命令输出后再次运行。

## 按需读取

模型可在执行模式和计划模式调用只读工具：

```json
{"log_id": "命令结果中的32位ID", "tail": true, "limit": 4096}
```

读取指定区间时改用：

```json
{"log_id": "命令结果中的32位ID", "offset": 0, "limit": 4096}
```

`offset` 和 `limit` 按字节计数，limit 最大 65536；tail 与 offset 不可同时指定。结果包含 `offset`、`next_offset`、`stored_bytes` 和 `eof`，继续读取时使用 next_offset。`eof` 只指当前保存文件的末尾，不代表命令成功。分页边界切开 UTF-8 字符时可能出现替代字符，可重叠读取附近字节确认原文。

## 保存与恢复

日志 ID 作为普通工具结果进入历史，会话或任务恢复后仍可访问同一工作目录中的日志。恢复只读模式不妨碍查日志，也不会重跑命令。不要删除日志文件后仍期待旧会话可读取它们。

日志正文在命令结束时刷新并 fsync，随后原子保存元数据。命令仍在执行、进程被强制结束或元数据写入失败时，可能只剩部分日志；读取工具此时返回 `finalized=false`、`storage_truncated=null`，不假定完整。日志写入故障导致工具失败时沿用“操作结果未知”处理，不能自动重试有副作用的命令。

工具只接受规范日志 ID，不接受任意文件路径，并检查运行目录及目标文件的符号链接。与其他文件工具一样，这不是完整的操作系统沙箱，也不防御所有并发文件系统替换。日志可能包含命令打印的敏感数据，应保持 `.fast-agent/` 不入 Git；本阶段没有自动清理策略，每条日志有容量上限，总目录仍需要用户管理。

## docs/tutorial/16-active-compaction.md

# 16：单次长任务的上下文压缩

第 9 章按用户轮次压缩历史，但一次用户任务里可能连续读取多个文件、运行多次测试。即使只有一轮对话，工具结果也会逐渐挤满上下文。本章允许在安全边界上摘要当前任务的较早部分。

## 什么是一个完整工具批次

一个 assistant 消息可以提出多个工具调用，后面必须有每个调用对应的 tool 结果。它们共同构成一个批次。不能只删除其中某个结果，也不能摘要还没有返回全部结果的批次。

Agent 每次请求下一步模型之前检查预算。这时前一批工具已经执行完，历史结构经过校验，才有机会压缩。

## 选择与保留规则

1. 先尝试原有的历史轮次压缩，保留 `keep_rounds` 指定的近期轮次。
2. 如果当前保留内容仍太大，或没有更早轮次可压缩，则检查当前任务是否至少存在两个完整工具批次。
3. 把当前任务较早的批次加入待摘要内容；当前用户原始消息、system 消息和最近一批工具调用及全部结果保留原文。此前近期轮次仍保留原文。
4. 若原文保留部分与工具定义本身已塞满预算，停止并要求缩小读取范围或调整预算，不拆散最后一批结果。

`keep_rounds` 继续控制较早轮次的保留；新机制允许在其中最新一轮内部摘要更早的工具批次。摘要只代表历史事实，不能成为新的权限授权。加载会话仍进入计划模式，未知操作结果的阻止仍然有效。

## 摘要如何进入历史

沿用 `SUMMARY_MARKER` 标记的一组摘要消息：system → 摘要标记 user → 摘要 assistant → 保留的近期轮次与当前任务。

当前任务的原始 user 消息再次出现在摘要之后，最近工具批次紧随其后。旧摘要参与新的摘要输入并被替换，不会无限堆积摘要标记。当前用户消息也提供给摘要模型作为整理背景，但它在最终历史中仍保留原文。

摘要请求没有工具定义。模型若返回工具调用、空白、过长或不完整内容，程序拒绝采用。候选历史必须通过配对校验、确实缩小且满足预算，原始历史备份成功后才替换内存历史。摘要失败或备份失败不修改原始消息，也不会重新执行工具。

## 能力边界

字符预算是请求 JSON 的估算体积，不是 tokenizer 的精确 token 数。摘要也可能遗漏事实，原始备份可供核查，重要修改仍应重新读取代码与验证结果。超大单文件输出、过长用户要求或工具定义本身超预算时，这个机制不能解决所有问题。

当前只保留最近一个完整工具批次作为当前轮的原文证据，不保证更早结果逐字保留。不同轮次的历史压缩仍可能摘要过去的用户消息。它不增加模型执行步数上限，也不等于无限长任务。

## 亲自验证


报告位于 `.fast-agent/validation/active-compaction-demo.json`；`compaction_end` 中 `scope=current_task` 和 `summarized_tool_batches` 标识本轮内部压缩。宿主核对实际测试、文件差异、摘要存在性和恢复模式；确定性测试覆盖多调用配对、重复压缩、无法压缩及备份失败。

## docs/tutorial/17-edit-undo.md

# 17 · 文件编辑记录与安全撤销

Agent 能修改代码，还需要让使用者看清改动，并在适当时恢复文件。本章在原有文件写入流程上增加持久收据和本地撤销命令。

## 使用方法

```text
/changes
/execute
/undo <编辑编号>
```

`/changes` 显示编号、路径、时间和状态，不输出完整文件内容。文件工具成功返回的 `edit_id` 也可以直接用于撤销。恢复会话默认进入计划模式，必须显式 `/execute` 后才能确认修改；启动时的只读权限不会被提升。

`/undo` 是本地命令，不发给模型。它展示反向差异，得到确认后才写入。会话消息保留原来的操作历史，下一轮应重新读取文件，以当前文件为准。

## 一次编辑的数据流

1. `read_file` 保存文件和沿途 AGENTS.md 的指纹。
2. 编辑工具在内存计算结果，展示完整差异并请求确认。
3. 确认后写入 `.fast-agent/edits/<编号>.json`，状态为 `pending`，包含修改前后文本。
4. 再次检查文件和规则，使用同目录临时文件及原子替换提交。
5. 将记录标记为 `completed`，向模型返回编辑编号。

记录文件权限为 0600，目录为 0700，复用有界、原子写入的 RuntimeStore。快照可能包含项目私有内容，应保留在被 Git 忽略的 `.fast-agent` 中。单个文本文件仍受 1 MiB 限制；当前没有历史总量自动清理。

## 撤销为什么不能直接覆盖

撤销先检查当前文件是否逐字节等于记录中的修改后版本。如果用户或其他工具后来改过文件，就拒绝覆盖。确认过程中再次发生变化，也会拒绝。

通过检查后，记录先进入 `undoing`，再复用原有差异确认、权限判断和原子文件替换，成功后标记为 `undone`。同一条记录不能重复撤销。多次编辑同一个文件，应从最新记录开始逆序撤销。

首版只撤销已有文本文件的编辑。新文件会留记录，但不会自动删除；命令产生的副作用、Git 操作和多文件事务不在撤销范围内。

## 中断与限制

文件和 JSON 记录是两次独立的磁盘操作，不能承诺一起提交。进程若在中途退出，可能留下 `pending` 或 `undoing`。这些记录不能直接撤销，需要人工查看当前文件核实，不自动猜测操作是否完成。哈希/内容检查也不是针对恶意并发进程的操作系统级事务隔离。

撤销共用工作区执行锁，拒绝与启用检查点的 Agent 任务同时运行。它遵守计划模式、启动只读权限及已知未核实操作的阻塞。


脚本在临时 Git 仓库中依次执行：失败测试 → MiniMax 规划 → 工具修复并测试通过 → 独立进程恢复会话并只读核验 → 外部修改冲突保护 → 独立进程通过本地命令撤销 → 原始失败测试重新出现。最终核对源文件完全恢复、测试文件未改和 Git 差异为空。

# 18 · 更精确的代码检索

仓库中可能同时存在正式实现、示例和测试里的同名函数。Agent 需要逐步缩小范围，找到正确代码，再读取和修改。本章扩展现有 `search_code` 工具，保持计划模式可用。

## 三个新参数

```json
{
  "query": "^def (add|multiply)",
  "regex": true,
  "glob": "src/**/*.py",
  "context_lines": 1,
  "limit": 20
}
```

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `regex` | `false` | 默认固定文本；为 true 时使用 ripgrep 的 Rust 正则语法 |
| `glob` | 不筛选 | 以工作区为根的路径模式；`*` 不跨目录，独立的 `**` 匹配零个或多个目录 |
| `context_lines` | `0` | 每个匹配前后各返回 0～5 行 |

`src/**/*.py` 同时匹配 `src/a.py` 和 `src/core/a.py`。`*.py` 只匹配工作区根目录的文件；任意层级使用 `**/*.py`。支持单段中的 `?` 和字符集合，不支持花括号展开、反斜杠或否定模式。模式不能包含绝对路径、空段、`.`、`..`。

`path` 仍然指定搜索目录；glob 始终相对于工作区，不会因为设置了 `path` 而改变基准。

默认查询 `a.b` 只匹配字面量 `a.b`。设置 `regex=true` 后，点号才表示任意字符。无效正则返回工具错误，模型可修改参数；没有匹配是成功的空列表。正则不启用 PCRE2，不支持其回溯引用和环视扩展。

## 模型收到什么

```json
{
  "matches": [{
    "path": "src/math_utils.py",
    "line": 2,
    "text": "def add(a, b):\n",
    "before": [{"line": 1, "text": "# 加法函数\n"}],
    "after": [{"line": 3, "text": "    return a - b\n"}]
  }],
  "truncated": false
}
```

`before`、`after` 只在请求上下文时出现。文件起止位置的上下文自然少于指定行数。相邻匹配的上下文可能重叠，每条结果都保留自己的行号。

搜索不会登记编辑所需的读取指纹。即使上下文已经显示目标代码，编辑前仍必须 `read_file`，以读取适用规则和校验文件版本。

## 忽略规则与输出预算

不能简单地给 ripgrep 添加正向 `--glob`：它可能覆盖忽略规则。当前实现先使用原有的忽略策略搜索，再对返回事件进行路径筛选。这样 `.gitignore`、运行目录和 `.env*` 的排除继续生效，也不跟随符号链接。

这个选择有明确限制：glob 是结果筛选，不保证减少底层扫描。底层输出超过 64 KiB 时，即使筛选后为空，`truncated` 仍为 true，不能解释为仓库中没有目标。此时先缩小 `path` 或增加查询精度。

结果最多 500 条，默认 100 条；每行最多 500 字符，截断行带 `text_truncated=true`。包含上下文后的结果数据也限制为 64 KiB。底层输出、匹配数量、行文本或结果数据被截断，都会设置顶层 `truncated=true`。读取不超过 1 MiB 的文件，并保留原有命令超时。

# 19 · 手动上下文压缩 /compact

自动压缩在请求超过预算时触发。一个阶段结束后，也可以主动整理旧资料，再继续工作。本章增加本地命令 `/compact`，复用已有的摘要校验与工具消息分组。

## 使用方法

```text
/compact
/compact 重点保留任务编号、禁止修改测试的约束和未完成事项
/save compacted
```

关注点可省略，最多 1000 字符；多个词按空格连接，含引号时遵循命令行 shlex 规则。它只影响摘要强调的信息，不授权执行工具，也不能提高权限。计划模式和启动只读权限下均可压缩。

手动压缩成功后显示请求字符数变化与完整备份路径。字符数包含工具定义，不是 token 数。恢复备份时用文件名去掉 `.json` 的名称：

```text
/load manual-<编号>
```

这会恢复原始消息并进入计划模式，不撤销文件、不重放工具。若要继续修改，仍需本地 `/execute` 和原有操作确认。

## 执行流程

1. 取得工作区执行锁，校验历史消息协议。
2. 先保存 `.fast-agent/sessions/manual-<编号>.json` 原始备份。
3. 根据 `keep_rounds` 保留最近轮次；必要时只摘要较早的完整工具批次，保留最近批次及当前用户目标。
4. 调用摘要模型，工具列表为空。关注点作为明确标注的摘要偏好加入提示。
5. 校验摘要非空、长度、无工具请求、消息配对完整，且请求字符数实际减少。
6. 全部通过后才替换内存历史；显式 `/save` 保存压缩后的会话。

原始历史未达到自动压缩阈值时也会处理。`--context-chars 0` 仅关闭自动触发：手动压缩仍可用，此时以原请求大小作为压缩结果上限。配置了非零预算时，结果还必须满足该预算。

空会话或没有足够较早完整消息时，不调用模型并提示无法安全压缩。非空但不能压缩的历史可能已经生成备份；不会为了缩短内容拆开工具调用和工具结果。

## 失败时发生什么

备份写入失败时不调用模型。模型失败、返回工具调用、摘要过长、摘要未缩小上下文或用户中断时，原历史不变。已保存的备份保留，失败消息包含其路径。该命令不更新旧任务检查点；`/resume` 恢复原检查点，需要恢复压缩结果时使用 `/save` 与 `/load`。

模型摘要仍可能遗漏或误述事实，格式检查不能证明语义完全正确。关键约束应核对摘要或备份；继续修改前重新读取当前文件。关注点不会被当作新的工程操作指令。

# 20 · 会话列表与启动时加载

保存的会话多了以后，不应依赖记忆或手动翻找 JSON 文件。本章补上命名会话的发现与启动入口，继续复用原有内容校验和恢复权限边界。

## 找到保存的会话

```text
/sessions
/sessions 2
/sessions --all
/sessions 2 --all
```

每页固定 20 条，按文件修改时间从新到旧排序；同一时间按名称排序。列表包含名称、字节大小、UTC 更新时间，以及总数、当前页和 `has_more`。页码从 1 开始，超出末页返回空列表。

默认隐藏 `auto-` 与 `manual-` 开头的压缩备份，`--all` 显示全部。分类依据名称前缀，因此自己命名时也应避免这两个前缀。普通 `/save 名称` 的文件会显示在默认列表中。

列表只读取文件元数据，不加载消息正文，也不请求模型。损坏 JSON 仍可能出现在列表中，只有 `/load` 或 `--load` 才校验内容。符号链接、目录和不合法名称会被跳过；会话存储目录本身若为符号链接则拒绝访问。

分页限制返回数量，当前仍会扫描目录中的全部候选文件元数据，不是数据库索引；数量特别大时仍有扫描成本。

## 启动时加载

```bash

```

进入后先处于计划模式，可以检查 `/history`、`/context`，再决定是否执行：

```text
/execute
请继续刚才保存的修复任务，重新读取源码后再修改。
```

也可以一次性只读核验：

```bash
fast-agent --workspace /path/to/repo --load 修复计划 --prompt '只读核对当前源码与此前计划'
```

`--load` 和 `--resume` 互斥：前者加载 `/save` 保存的命名会话，后者加载任务检查点。两者都不重放工具，也不从磁盘继承执行授权。启动权限为 `read-only` 时，`/execute` 仍不能提升权限。

会话不存在、JSON 损坏、消息协议无效或工作目录不一致时，启动报错退出。列表里的名称可直接用于 `--load`，但“列出成功”并不代表内容已通过校验。

## 代码流程

`SessionStore.list()` 读取元数据并排序分页 → 本地 `/sessions` 输出列表 → CLI 参数解析选择唯一恢复入口 → `SessionStore.load()` 校验文件 → `Agent.restore_history()` 刷新系统指令、清空旧读取指纹、进入计划模式 → 后续用户输入才可能发起模型调用。

元数据列表没有摘要字段，避免为了展示会话而额外向模型发送历史正文。更新时间来自文件系统，复制文件可能改变排序。

# 21 · 任务继续执行与步数控制

达到调用上限不等于任务失败，也不代表目标已经完成。本章让暂停原因、继续入口和恢复方式在终端中清楚可见。

## 常用命令

```text
/steps
/steps 15
/continue
/continue 请先核对测试结果，再处理剩余问题
```

`/steps` 查看当前上限，带整数时调整后续每轮模型调用次数，范围 1～1000。启动参数 `--max-steps` 使用相同范围，默认 10。设置只保存在当前进程，加载会话不会从文件继承该配置。

`/continue` 是显式发起模型调用的本地入口：附加一条继续任务的用户消息，携带当前历史进入现有 Agent 循环。补充说明可省略，最多 4000 字符。空会话无法继续，应先输入任务或加载历史。已完成的任务也可以用它发起后续检查，它不是“仅未完成任务”状态机。

## 达到上限时

Agent 完成当前模型回复中的工具批次，再检查是否还有下一次模型调用预算。达到上限时，返回未完成状态，保留工具结果，并保存 `incomplete` 检查点。终端提示 `/steps`、`/continue` 以及启用检查点时的任务编号。

一个模型回复可以包含多个工具调用，所以步数限制不是工具数量限制，也不是总耗时或费用上限；自动压缩的摘要请求和网络重试不计入这个循环步数。

```bash
fast-agent --workspace /path/to/repo --resume <检查点编号>
```

恢复后先处于计划模式。需要修改时显式切换：

```text
/steps 15
/execute
/continue 请继续修复并实际运行测试
```

也可以 `/save 名称`，下一进程通过 `--load 名称` 恢复。每次继续复用 `run()`，启用检查点时创建新的任务编号，旧检查点保留。

## 不重放意味着什么

宿主程序不会遍历历史重新执行旧工具调用。模型会看到已有结果和继续说明，然后生成新的决策；它仍可能主动提出再次读取或测试。继续提示要求先核对已完成事项，但这不是对所有副作用的去重保证。

计划模式保持只读，启动 `read-only` 权限不能被 `/continue` 或 `/steps` 提升。结果未知的旧操作仍由任务记录阻止写入，需要先人工核实；增加步数不能绕过这些检查。

最后一步若只完成工具调用，还没有模型最终总结，整轮仍属于未完成。继续后模型可以依据已有工具结果总结，无需自动重跑它们。

## docs/tutorial/22-repeated-failures.md

# 22 · 重复失败检测与暂停

模型可能反复读取不存在的文件，或不改变参数地重复失败操作。步数上限能限制总轮次，但无法区分探索与无进展重复。本章在工具结果返回后增加轻量检测。

## 什么时候暂停

同一轮任务中，连续三次工具执行同时满足以下条件，就暂停：

- 工具名称相同。
- 参数相同：合法 JSON 忽略空白和对象键顺序，数组顺序保留；不合法 JSON 按原始字符串比较。
- 失败结果相同：比较错误文本及结果数据。`run_command` 的随机 `log_id` 不参与比较，实际输出、退出码等仍参与。

工具成功，或者工具、参数、错误、结果数据发生变化，计数重置。检测按工具执行顺序进行，同一模型回复中的多个调用也计数。

前两次失败按常规记入历史，批次完成后返回模型，让它有机会纠错；如果同批已连续失败三次，则立即暂停，不发起下一次模型调用。它不撤销已经发生的操作，也不能保证前三次尝试没有副作用。

## 如何保存暂停现场

第三个失败结果正常加入历史。如果该回复还有其他工具调用，宿主不执行它们，而是补上“重复失败保护已暂停；此调用尚未执行”的工具结果。这保证每个调用 ID 都有对应结果，保存和恢复不破坏消息协议。

启用检查点时，任务状态为 `paused_repeated_failure`，终端显示失败原因、检查点编号和继续方式。它表示重复失败造成的暂停，不等同于副作用未知。

```text
/tasks
/continue 文件路径已确认，请先检索正确位置再继续
```

也可以新进程恢复：

```bash
fast-agent --workspace /path/to/repo --resume <检查点编号>
```

恢复仍是计划模式，修改前需要 `/execute`。每次用户发起新一轮，包括 `/continue`，计数重新开始；旧工具结果继续保留，不由宿主重放。

## 未知结果优先处理

工具返回 `uncertain=true` 时，原有逻辑立即停止并记录未核实操作，不会等到重复三次。即使 `/continue` 或调高步数，写操作仍被阻塞，必须先人工核实。

当前检测不是通用循环识别器：A/B 交替失败、每次输出不同时间戳、成功读取穿插失败等情况不会累计为连续相同失败，仍由总步数限制约束。模型输出相同文字但没有工具调用，也不属于此检测范围。

## 测试如何避免依赖模型随机行为

确定性测试让模型夹具连续调用真实只读工具，精确验证第三次暂停、同批剩余调用未执行、完整消息配对、成功和变化重置计数、继续后重新开始，以及未知写入结果优先停止。

真实验收采用两段流程：

```bash
source .env
FAST_AGENT_READ_TIMEOUT=120 FAST_AGENT_MAX_RETRIES=1 \
  .venv/bin/python examples/real_repeated_failure_demo.py
```

第一进程使用明确标注的确定性模型夹具，反复读取不存在的文件，触发暂停并保存会话。第二进程使用真实 MiniMax，通过 CLI 加载暂停历史并 `/continue`：依据失败历史检索并定位正确源码、读取测试、复现失败、修复、重跑测试及检查 Git 差异。

不把夹具输出冒充 MiniMax 决策，也不要求真实模型碰巧连续犯错才能证明检测有效。报告位于 `.fast-agent/validation/repeated-failure-demo.json`，其中区分准备阶段模型与真实继续阶段。

# 23 · 调用用量与请求预算

工程 Agent 的一步不等于一次计费请求：摘要会调用模型，网络故障后的重试也会再次请求服务。因此预算放在模型适配层，而不是只在 Agent 循环里数步数。

## 启动与查看

```bash
export FAST_AGENT_MAX_REQUESTS=30
fast-agent --workspace .
```

交互中输入 `/usage` 查看当前模型实例的累计统计：

- `requests`：实际准备发出的请求尝试次数，包含失败、重试与压缩摘要。
- `max_requests`：请求上限，默认 0 表示不限制。
- `prompt_tokens`、`completion_tokens`、`total_tokens`：服务已返回的有效用量之和。
- `unknown_requests`：没有有效用量记录的请求数。大于 0 时，token 合计并不完整。

上限在每次调用 SDK 前检查。耗尽后 Agent 返回未完成状态；已执行的工具不会回滚，历史仍可保存。用 `/save 名称` 保存，再以新预算启动并使用 `--load 名称`，加载后仍为计划模式，需要 `/execute` 后继续。

`/steps` 限制单轮循环步数；请求预算限制当前模型实例整个生命周期。`/reset`、`/load` 和 `/continue` 都不会清零它。退出进程后重新计数，这不是跨进程或账户级配额，也不是金额上限。

## 对照代码理解

[usage.py](../../src/fast_agent/usage.py) 在 `begin()` 检查并增加请求计数。请求失败也保留计数，因为客户端无法判断服务端是否已经处理或计费。

[providers.py](../../src/fast_agent/providers.py) 的每次重试都先调用 `begin()`。普通响应读取 `response.usage`；流式请求带 `stream_options.include_usage`，接收末尾可能没有候选文本的用量块。同一请求重复出现累计用量时覆盖原记录，避免重复相加。

缺失或格式异常的用量保留为未知。这里不根据字符数推算账单，不维护可能过时的模型价格；费用以供应商账单为准。不支持流式用量参数的兼容服务可使用 `--no-stream`，不会自动重新发送已失败的请求。

## 验证

单元测试覆盖：重试耗尽请求预算、未知用量、重复流式用量块、摘要共享预算、恢复与重置不清零，以及配置校验。

真实验证示例 [real_usage_demo.py](../../examples/real_usage_demo.py) 在临时目录中使用两个模型实例：第一个最多请求一次，执行工具后在下一次请求前暂停；保存并加载历史后，第二个实例继续修复函数、调用测试命令，并独立核对测试退出码和测试文件未被修改。该示例验证新模型实例的预算重建，两个实例运行于同一 Python 进程，不宣称跨进程账单持久化。

本次 MiniMax-M3 验证 8 项检查全部通过。第一实例 1 次请求报告 2144 tokens；恢复后第二实例 7 次请求，其中 1 次用量未知，已报告合计 23739 tokens。后者不是完整账单。全量本地测试 274 项通过，严格文档构建通过。

# 24 · 命令写入与网络隔离

确认命令只表示用户同意执行；`cwd` 只决定相对路径起点，都不能阻止程序访问工作区之外。现在可在 macOS 显式启用操作系统的命令限制：

```bash
fast-agent --workspace . --sandbox macos
```

## 范围与边界

`run_command` 与 `start_command` 使用同一策略：禁止网络操作，禁止工作区之外写入（仅允许写入 `/dev/null` 空设备以兼容 Git 等程序），额外禁止写入工作区根目录的 `.git`、`.fast-agent` 和 `.env`。子进程沿用 macOS 限制；后台记录持久保存所选沙箱模式，不因终端退出变为普通命令。

这是写入和网络约束，不是完整的不可信代码安全隔离：外部文件仍可读取，进程交互等系统能力没有全部封禁；不要用它执行恶意程序或保护机器上的读取机密。需要完整隔离时应使用独立受控运行环境。macOS 的 sandbox-exec 可用性以本机验证为准，Linux/Windows 目前不能使用这个后端。

沙箱模式只给命令基础环境变量：PATH、语言、时区和终端类型；HOME、TMPDIR 指向工作区，并关闭 Python 字节码写入。依赖环境变量中的构建配置、外部缓存、下载依赖、Git 写操作的命令可能失败。失败会作为真实工具结果反馈，不自动放宽策略。默认 `--sandbox none` 保持原行为，但同步和后台命令都不再自动继承 FAST_AGENT_API_KEY。

普通模式移除一个环境变量并不能防止命令读取磁盘凭据。文件工具本身也不是操作系统沙箱。当前选项仅作用于命令进程。

## 代码路径

[command_sandbox.py](../../src/fast_agent/command_sandbox.py) 将原始 argv 包装为 sandbox-exec 调用，并生成环境变量；调用方仍对原始命令进行审批。配置不支持时提前报错，运行时沙箱启动失败则返回失败，不会回退到无沙箱执行。

[jobs.py](../../src/fast_agent/jobs.py) 将模式写入任务记录；[job_worker.py](../../src/fast_agent/job_worker.py) 在真正创建命令子进程时应用同样策略。日志由沙箱外的 Agent 执行器写入，因此命令不需要获得 `.fast-agent` 写权限。

## 验证

默认测试校验参数构造、凭据移除、不支持平台拒绝执行。本机原生测试需显式启用：

```bash
FAST_AGENT_TEST_SANDBOX=1 .venv/bin/python -m pytest tests/test_sandbox.py -q
```

原生测试实际检查工作区文件可写，外部文件、指向外部文件的符号链接、`.env` 与运行记录不能写，网络绑定被拒绝，后台命令同样不能越界写入。不要把参数字符串检查当成操作系统隔离的证据。

MiniMax 验证复用 [real_usage_demo.py](../../examples/real_usage_demo.py)，设置 `FAST_AGENT_DEMO_SANDBOX=macos`：预算暂停并保存后恢复，模型修改示例函数，在沙箱内执行 unittest，独立核对退出码与测试文件未修改。

本次本机全量测试（包含原生沙箱测试）281 项通过，严格文档构建通过。MiniMax 第一次组合验证在复现失败测试后请求超时；第二次恢复后完成修改，沙箱内测试通过且测试文件未改。但第二次最初请求未达到预期预算暂停，原脚本仍为失败。按本章“沙箱修复与会话恢复”范围复核的 9 项检查通过；预算暂停另有第 23 章成功证据。没有把组合脚本报告改写为全项成功。

# 25 · 多文件修改批次与安全恢复

重构经常需要一起修改多个文件。逐次编辑会让用户难以看清整体变化；把所有内容放到一个工具请求里，也不会让文件系统自动拥有跨文件事务。本章提供整体预检、整体审批和可检查的恢复记录。

## 模型如何调用

先 `read_file` 读取全部目标及其规则，然后调用：

```json
{
  "files": [
    {"path": "add.py", "old": "return a-b", "new": "return a+b"},
    {"path": "multiply.py", "old": "return a+b", "new": "return a*b"}
  ]
}
```

工具名为 `edit_files`。每个已有文件执行一次非空且唯一的精确替换；路径不能重复，最多 20 个文件。复杂单文件多处替换仍可使用 `multi_edit_file`。这一版不在批次中创建、删除文件或目录。

所有目标先验证读取指纹、AGENTS.md、匹配唯一性和大小。整体差异不超过 64 KiB，每个文件不超过 1 MiB，前后快照总计不超过 8 MiB。任何预检失败都不会写入任何目标。审批展示整批差异，审批后再次检查整批文件，再逐文件原子替换。普通文件先写，AGENTS.md 按目录由深到浅最后写；恢复也使用这一顺序，防止批次自身修改规则导致后续文件校验失败。

## 为什么还需要批次记录

操作系统没有为这些独立文件提供全局原子替换：第一个文件成功后，第二个可能遇到磁盘错误。不能把这类情况说成“全部没发生”，也不应该悄悄重试。

[edit_batches.py](../../src/fast_agent/edit_batches.py) 在第一次写入前保存 `.fast-agent/batches` 记录，包括每个文件修改前后的完整文本和状态：

| 状态 | 含义 |
| --- | --- |
| pending | 修改可能尚未开始或只完成一部分，需要核实 |
| completed | 整批写入与完成记录均成功 |
| undoing | 恢复可能进行到一半，需要核实 |
| undone | 整批恢复完成 |

`pending`、`undoing` 会阻止新任务写入。任务检查点中的未知工具结果仍保持原有保护；批次记录不会自动消除它。

## 用户显式恢复

```text
/batches
/undo-batch 批次编号
```

撤销命令不开放为模型工具。用户可以先核对 `/tasks`、`/batches` 和磁盘内容；若任务检查点也标记未知结果，先按已有 `/resolve 任务编号 核实说明` 流程处理，然后恢复批次。

恢复持有工作区任务锁，逐个校验所有文件必须与批次的修改前或修改后快照完全相同。遇到任何不同内容、缺失文件、无效路径或规则读取失败，拒绝整批恢复，不覆盖外部修改。校验通过后展示整体恢复差异，再确认并执行。恢复本身也可能中断，此时保留 `undoing`；再次显式恢复仍会重新检查整批内容。

只排除正在恢复的自身批次阻塞，其它未核实任务、后台任务、其它中断批次、计划模式和启动只读权限仍阻止写入。会话历史不会随文件撤销而改写，继续任务前应重新读取磁盘。

文件快照属于本机运行数据，不提交 Git，也不自动发送给模型；`list_edit_batches` 只返回编号、路径和状态。它们不是版本控制或长期备份，仍应使用 Git 保存正式工作。

## 验证流程

测试覆盖完整审批/恢复、预检失败不写入、审批期间变化、部分写入故障、外部冲突拒绝恢复、中断批次阻塞与恢复。真实示例 [real_edit_batches_demo.py](../../examples/real_edit_batches_demo.py) 用 MiniMax 修复两个文件并执行测试，保存加载历史后人工撤销，核对原始文件完全恢复及测试重新失败，再让模型重新读取、修复并运行测试。测试文件始终保持不变。

本次 MiniMax-M3 完整验证 11 项检查全部通过；包含原生沙箱检查的本机全量回归 289 项通过，严格文档构建通过。规则文件依赖顺序由故障复现测试和独立代码审查覆盖。

# 26 · 持久任务计划与版本冲突

聊天里写出的计划容易被长对话压缩，也可能在恢复时与磁盘状态脱节。本章把计划作为独立的工作区记录保存，让模型显式查询，而不是依赖历史文本猜测。

## 读写协议

三个模型工具分别负责查询、列举和更新：

- `get_plan {"name":"repair"}`：读取最新计划，不存在时返回 `revision: 0`。
- `list_plans {}`：返回名称、标题、版本和步骤状态摘要。
- `update_plan`：提交完整计划和刚读取的 `expected_revision`，经用户确认后保存。

```json
{
  "name": "repair",
  "expected_revision": 0,
  "title": "修复计算错误",
  "steps": [
    {"id": "read", "title": "读取源码", "status": "in_progress", "note": ""},
    {"id": "test", "title": "运行测试", "status": "pending", "note": ""}
  ]
}
```

计划名称和步骤编号使用字母、数字、下划线或短横线，最长 64 字符。标题最长 200 字符，说明最长 2000 字符。每个计划有 1～50 个步骤，状态可选 `pending`、`in_progress`、`completed`、`blocked`，最多一个 `in_progress`。

## 旧计划不能覆盖新计划

[task_plans.py](../../src/fast_agent/task_plans.py) 通过私有 JSON、原子替换和进程锁保存计划。新计划从版本 1 开始，每次更新增加版本。提交版本与磁盘版本不一致时，工具失败，要求重新读取；确认期间记录发生任何变化，也拒绝覆盖。

这避免两个进程拿着同一份旧计划先后覆盖。版本号不提供分支合并功能；模型需读取新状态后重新组织更新。

计划更新仍是写操作，遵循原权限策略。计划模式、启动只读模式和未核实结果都会阻止更新；计划模式可以查询已有计划，切换执行后才能确认保存。这保留了本项目“计划模式不写入”的约定，没有把元数据写入伪装成只读工具。

## 保存恢复后的行为

```text
/plans
/show-plan repair
/save work
/load work
```

计划保存在 `.fast-agent/plans`，消息保存在 `.fast-agent/sessions`。加载旧会话不会回滚新计划，`/reset` 和上下文压缩也不会删除计划。恢复后应调用 `get_plan` 读取当前版本，再读取文件核对现状。

计划属于工作区，不随会话文件自动迁移到另一台机器。计划不会自动注入每次模型请求，只有显式查询返回工具结果，避免所有历史计划占用上下文。

`completed` 只表示模型或用户记录的状态，不是测试通过证明。完成说明应引用真实执行结果；后续质量检查功能会单独保存命令和退出码。

## 验证

测试覆盖创建后重新读取、版本递增、旧版本拒绝、确认期间外部变更、权限拒绝和字段约束。真实示例 [real_task_plan_demo.py](../../examples/real_task_plan_demo.py) 使用 MiniMax 建立修复计划，读取文件、修复并测试，再更新完成状态；创建新模型实例加载会话后重新查询同一计划、重跑测试，检查计划没有被旧会话覆盖。

本次 MiniMax-M3 真实验证 10 项检查全部通过，持久计划从版本 1 更新到版本 2，恢复后内容保持一致并再次运行测试。默认本地回归 296 项通过、2 项原生沙箱测试按开关跳过；严格文档构建通过，独立审查未发现阻止交付的问题。

# 27 · 配置质量检查与执行证据

任务计划里的“完成”不是测试证据。质量检查把用户选定的命令与实际退出码保存在独立记录中，便于恢复会话后复核。

## 显式加载配置

创建 `checks.json`：

```json
{
  "tests": {"argv": ["python", "-B", "-m", "unittest", "-v"], "timeout": 30},
  "diff": {"argv": ["git", "diff", "--check"], "timeout": 10}
}
```

```bash
fast-agent --workspace . --checks checks.json
```

加载配置不会运行命令，也不代表已授权执行。配置在启动时读取一次；模型修改磁盘配置不会改变当前进程已加载的命令。配置最多 64 KiB、32 个检查，每条 argv 最多 128 个参数、每个参数最多 4000 字符；超时大于 0 且不超过 60 秒。没有 shell 字段，不通过 shell 解释命令。

## 工具调用过程

1. `list_checks` 查询已加载的名称、argv 和超时。
2. `run_checks {"names":["tests","diff"]}` 按顺序执行指定检查。
3. 每项复用 `run_command` 的审批、权限、沙箱、流式输出和长日志保存。
4. 首个失败停止，未运行的检查不会被计为成功。全部指定检查成功才返回 `ok: true` 和 `status: passed`。

工具参数只有名称，不能注入另一条 argv 或改变超时。使用 restricted 精确命令白名单时，仍按实际 argv 检查授权；只读/计划模式不能运行检查。

## 持久证据

[quality_checks.py](../../src/fast_agent/quality_checks.py) 在执行前保存 `running` 记录，每项结束后保存名称、实际 argv、耗时和完整的有界工具结果；最终保存 `passed` 或 `failed`。命令输出预览之外的长日志仍通过原有日志工具按需读取。

```text
/check-runs
/check-run 运行编号
```

模型可使用 `get_check_run` 查询记录。记录位于 `.fast-agent/checks`，包含工作区、沙箱模式和执行时间。可捕获异常保存 `unknown`，Ctrl+C 保存 `interrupted` 后继续向上传递中断，不伪造退出码；进程被强杀或存储失败仍可能留下 `running`，不能当成通过；未知命令结果继续沿用任务检查点的人工核实流程，不自动重跑。

这些记录只证明当时的执行结果，不证明当前代码、外部服务或依赖仍保持不变。它不是签名审计账本，也不是强制约束模型最终措辞的门禁。代码再次修改或恢复后应重跑检查，不能仅复述历史 `passed`。测试范围也由配置决定，不能把单元测试通过说成全部质量已验证。

## 验证

本地测试覆盖真实子进程通过、非零退出、审批拒绝、未知/重复名称拒绝、非法配置和结果重新读取。真实示例 [real_quality_checks_demo.py](../../examples/real_quality_checks_demo.py) 使用 MiniMax 先执行配置检查复现失败，再修复源码并重跑通过；保存加载会话后再次运行检查，确认旧记录保留、新运行独立记录、测试文件未改变。

本次 MiniMax-M3 完整验证 10 项检查通过，保留了失败、修复后通过、恢复后再次通过的三次独立记录。包含原生沙箱检查的本机全量回归 308 项通过，严格文档构建通过。启动异常和用户中断的终态记录由故障注入测试及独立审查验证。

# 28 · 显式加载本地工具扩展

不修改 Agent 源码，也可以接入自己的分析器或内部工具。当前实现使用一次性本地进程协议，不在 Agent 进程内导入扩展 Python 模块。

## 配置与启动

```json
{
  "tools": [{
    "name": "inspect_source",
    "description": "分析指定示例源码",
    "argv": ["python", "inspect_source.py"],
    "timeout": 30,
    "parameters": {
      "type": "object",
      "properties": {"filename": {"type": "string"}},
      "required": ["filename"],
      "additionalProperties": false
    }
  }]
}
```

```bash
fast-agent --workspace . --extensions extensions.json
```

模型看到的名称为 `ext_inspect_source`。工具名称加前缀以避免覆盖内置工具。配置只在用户显式指定时加载，不自动发现工作区脚本，也不接受文档里的“安装扩展”指令作为授权。

配置最大 64 KiB、最多 16 个工具；名称最多 48 字符。argv 使用数组，命令从工作区执行，相对脚本路径相对工作区。配置和脚本都是用户信任的本地代码：固定 argv 并不固定脚本内容，也不防止脚本之后被修改。

## 一次调用的协议

模型提供的参数先经过工具 schema 校验，再序列化为一个 JSON 字符串，追加为 argv 的最后一个参数。不是 shell 拼接，不会把参数中的分号或命令替换语法当 shell 执行。扩展可读取 `sys.argv[-1]`：

```python
import json
import sys

args = json.loads(sys.argv[-1])
print(json.dumps({
    "ok": True,
    "data": {"filename": args["filename"]},
    "error": None,
}, ensure_ascii=False))
```

标准输出需要是唯一的 JSON 对象，且包含 `ok`（布尔）、`data`（对象）、`error`（字符串或 null）。失败时 `error` 不能为空。stdout/stderr 在现有命令执行器中合并，因此不要把调试文本打印到这两个通道污染协议；需要额外日志时由扩展自己按授权范围处理。

参数最大 32 KiB，结构化返回最多 4 KiB，单次超时大于 0 且不超过 60 秒。非零退出、超时、过长输出、非 JSON、非有限数值或错误信封不会被当成成功；Agent 按可能已有副作用的未知结果暂停，保留命令日志编号供核实，不自动重放。

## 权限与 schema 范围

[extensions.py](../../src/fast_agent/extensions.py) 复用命令审批、超时、进程组清理、长日志与 `--sandbox` 策略。所有外部工具按写操作处理，不允许扩展配置自称只读；计划模式和启动只读模式不运行它们。

支持 object、array、string、integer、number、boolean，object 的 properties/required/additionalProperties=false，array 的 items，以及 description。嵌套最多 4 层，每个对象最多 20 个字段。不支持的 schema 关键字会在加载时报错，避免向模型宣称某种约束却没有实际校验。它不是完整 JSON Schema 实现。

配置不等于执行授权。restricted 白名单比较包含 JSON 参数的完整实际 argv；动态参数通常需要交互确认。命令默认不继承模型 API 密钥；macOS 沙箱限制仍仅覆盖已说明的写入与网络范围，不提供完整机密读取保护。

此协议不是 MCP，不包含远端服务发现、子 Agent 委派或自动执行技能。它先提供可检查的本地扩展入口，后续协议可复用同一工具注册和权限边界。

## 验证

本地测试实际启动扩展进程，验证中文和 shell 特殊文本按字面参数传递、参数类型拒绝、计划模式拒绝、异常响应触发未知结果，以及非法配置拒绝。真实示例 [real_extensions_demo.py](../../examples/real_extensions_demo.py) 让 MiniMax 调用外部源码分析器，修复函数，调用配置质量检查；保存加载后再次执行扩展和检查，核对测试文件未变。

本次 MiniMax-M3 扩展验证 12 项检查通过。最终组合示例 [real_engineering_demo.py](../../examples/real_engineering_demo.py) 把六项工程能力串联，在临时 Git 仓库中完成修复、计划、扩展分析、沙箱质量检查、预算拒绝、保存加载和撤销后重新修复，首次组合的 16 项检查未覆盖每个配置检查，审查发现 Git 检查被 `/dev/null` 权限阻止；已补充精确空设备例外和两轮全部检查断言，加强后的 18 项组合验证全部通过：首次测试失败，修复后 tests/diff 均退出 0，恢复并重新修复后 tests/diff 再次退出 0。最终本机全量回归 321 项通过（含原生沙箱），严格文档构建通过。


## docs/tutorial/29-mcp-tools.md

# 29 · MCP 工具发现、调用与恢复

上一章的本地扩展由配置手工声明工具 schema，每次调用启动一次进程。本章加入 **MCP stdio 工具客户端**：服务启动后完成握手，主动查询它提供的工具，再把模型的工具调用转成 JSON-RPC 消息。连接可在多轮调用间复用。

## 先运行示例

在 `fast-agent` 项目目录安装官方 SDK 示例依赖：

```bash
.venv/bin/python -m pip install -e '.[mcp-test]'
```

客户端本身不依赖 SDK；示例服务使用官方 Python SDK 1.x（本轮实际互操作验证版本见下方验收）。创建显式配置 `mcp.json`，把两个绝对路径换成本机项目路径：

```json
{
  "servers": [
    {
      "name": "repo",
      "argv": ["/绝对路径/fast-agent/.venv/bin/python", "/绝对路径/fast-agent/examples/mcp_inspector_server.py"],
      "timeout": 15
    }
  ]
}
```

服务以 `--workspace` 指定的目录作为工作目录，示例只读取该目录下的 `math_utils.py`。准备包含 `add` 函数的文件，然后启动：

```bash
.venv/bin/fast-agent --workspace /你的测试仓库 --mcp /绝对路径/mcp.json
```

先确认启动服务，再提问“调用 MCP 检查 add 的实现”。模型可见名称是 `mcp_repo_inspect_source`。每次调用前会展示服务名、工具名和实际参数，等待确认。启动服务与调用工具是两次不同的授权。

`--prompt` 没有交互确认，不会自动执行 MCP。restricted 命令白名单也不替代 MCP 授权。`--plan`、只读权限或存在未核实操作时，CLI 仍可进入会话，但不启动服务。先核实操作并 `/execute`，再输入 `/mcp-connect`。只读启动策略不能通过 `/execute` 提升权限。连接失败或用户拒绝启动不会丢失交互入口。

## 一次调用经过哪些消息

```text
CLI --mcp → 用户确认启动 → 本地服务进程
  → initialize(protocolVersion, clientInfo, capabilities={})
  ← 服务协议版本与 tools 能力
  → notifications/initialized
  → tools/list（必要时携带 cursor 分页）
  ← 工具名、描述和 inputSchema
  → 注册到 ToolRegistry → 发送模型工具 schema

模型返回 tool_call(mcp_repo_inspect_source, {})
  → 参数校验、权限/模式检查、用户确认
  → tools/call(name=inspect_source, arguments={})
  ← content / structuredContent / isError
  → ToolResult → role=tool，关联模型的 tool_call_id
  → 下一轮模型读取结果并决定是否继续
```

JSON-RPC 的 `id` 由 MCP 客户端递增分配，用来匹配服务响应；模型的 `tool_call_id` 属于模型会话。两者用途不同，不能混用。Agent 原有循环无需知道 MCP 字节协议：它仍然执行注册工具，并把 ToolResult 交回模型。

## 保存会话并不保存执行授权

`/save 名称` 保存模型消息及工具结果。下次 `--load 名称 --mcp mcp.json` 先恢复成计划模式，不启动服务、不重放调用。用户 `/execute` 后用 `/mcp-connect` 重新确认启动、握手和发现工具，再要求模型重新检查。

同一进程内成功 `/load` 或 `/resume` 也会关闭旧服务并移除工具；切换执行后需要 `/mcp-connect` 重新授权发现。部分服务故障时，重连会先关闭整组旧连接，再重新授权，避免留下旧进程。配置更新只在显式新连接时读取，工具列表在连接期间固定，不自动响应 tools/list_changed 做权限变化。连接故障后需核实 uncertain 操作，才能显式重连。

## 失败为什么要暂停

服务超时、断线、非法 JSON、响应 ID 不符、超限响应或不支持的返回内容，可能发生在服务已经写入之后。因此结果标记 `uncertain=true`，关闭连接，不自动重试。服务返回 `isError=true` 也按可能有副作用处理。现有 Agent 检查点会暂停后续写入，用户核实后才能继续。

本地参数校验失败或调用被拒绝发生在发送前，不标成未知副作用。服务请求客户端 sampling、elicitation 等能力会得到 Method not found，不会触发额外模型请求或终端操作。

## 当前兼容范围与限制

- 本轮实现 MCP **2025-11-25** stdio 生命周期与工具子集，可接受服务协商到 2025-06-18 或 2024-11-05；其它版本拒绝。不是最新协议的完整实现。
- 支持最多 8 个本地服务、总计 64 个工具、每服务最多 16 页发现。服务名为 1～16 位字母/数字/连字符，工具名为 1～40 位字母/数字/下划线/连字符。
- 参数是严格 JSON Schema 子集：object、array、string、integer、number、boolean，required、properties、items、description；最多 4 层，每对象最多 20 个字段。未知字段禁止；省略 additionalProperties 时也收紧为 false。SDK 的 title 仅作为展示标注移除。`$ref`、enum、anyOf、default、nullable 等未实现字段会拒绝整个连接，绝不偷偷删除验证约束。
- 支持文本 content 和对象 structuredContent；图片、音频、资源内容暂不支持。服务 outputSchema 不作为本地验证器使用。
- 每个协议帧不超过 64 KiB，调用参数不超过 32 KiB，一次请求 stdout/stderr 累计读取不超过 1 MiB、消息不超过 100 条。请求超时最大 60 秒。stderr 在等待响应时排空并丢弃，不混入协议或直接打印终端。
- 本地服务执行使用 argv，不经过 shell。只传基础环境变量，不继承模型密钥或其它环境凭据。当前没有服务专用 env/secrets 配置。
- 外部工具统一标记 write，不信任 readOnlyHint 自动放行。`--sandbox macos` 对服务进程同样限制写入和网络，但仍允许外部读取；无法隔离恶意代码。服务脚本及配置必须可信，普通进程也可能读取磁盘敏感文件。
- 退出终止服务进程组；主动脱离进程组的程序不在此清理保证内。实现使用 POSIX 管道与进程组，面向 macOS/Linux，不支持 Windows。
- 本轮不支持 HTTP/SSE/OAuth、resources/prompts、动态工具列表、客户端 sampling/elicitation。需要这些能力时应独立扩展并测试，不能把 stdio 支持等同于全 MCP 支持。

# 30 · MCP 远程 HTTP 服务

上一章通过标准输入输出连接本地进程。本章增加 Streamable HTTP：Agent 可以连接一个已经运行的 MCP 服务，模型仍然使用相同的工具调用循环。

## 配置与启动

在显式传入的 MCP 配置中，`url` 与 `argv` 二选一：

```json
{
  "servers": [
    {
      "name": "repo",
      "url": "https://mcp.example.com/mcp",
      "bearer_env": "MY_MCP_TOKEN",
      "timeout": 15
    }
  ]
}
```

`bearer_env` 是环境变量名称，实际凭据由你在启动进程前注入；不要把 token 写进配置、提示词或会话。无认证服务可省略它。客户端不会借用 `FAST_AGENT_API_KEY`，也不允许将其指定为 MCP 凭据来源。

```bash
fast-agent --mcp /绝对路径/mcp.json
```

连接和每次工具调用分别确认；确认内容包含服务名、目标 URL 与调用参数。计划模式先不连接，切换 `/execute` 后使用 `/mcp-connect`。远程工具按有副作用的工具处理，服务声明只读也不会自动绕过确认。

## 一次请求如何走完

1. `MCPManager.start()` 取得连接授权，再读取独立凭据，创建 `HttpClient`。
2. 客户端 POST `initialize`，协商协议；服务返回的会话标识只保存在内存中。
3. 客户端发送 `notifications/initialized`，随后通过 `tools/list` 注册工具。
4. 模型选择 `mcp_repo_工具名`。现有权限层确认后，将参数封装为 `tools/call` 发给 HTTP 服务。
5. 客户端读取 JSON，或从 SSE 流中找到匹配请求 ID 的结果。结果转换成原有工具消息，再由 Agent 发回模型。

后续请求携带协商后的 `MCP-Protocol-Version`；服务提供会话标识时还携带 `MCP-Session-Id`。通知与反向请求响应使用独立 POST。服务要求客户端执行反向能力时，本实现返回“不支持的方法”，不会启动额外模型调用。

代码入口是 `src/fast_agent/mcp_http.py`。`SSEMessages` 负责跨网络分片拼接 UTF-8、CR/LF/CRLF 和多行 data；`HttpClient.exchange()` 处理 HTTP 状态与消息；`mcp_tools.py` 复用工具注册、授权和错误暂停。CLI 通过统一的 `is_alive` 判断连接状态，HTTP 的这个值表示本地连接对象尚未关闭，并非后台健康探测。

## 保存、恢复与失败处理

`/save 名称` 保存对话。`/load 名称` 或启动时 `--load 名称` 恢复时先关闭现有连接，并进入计划模式。确认工作区后 `/execute`、`/mcp-connect`，重新授权并创建 HTTP 会话；旧会话标识和 token 不随会话文件保存。

关闭时尽力发送 DELETE，清除本地凭据与会话标识；它不会停止远端服务。DELETE 最多等待两秒，网络失败或服务不支持删除时不能保证远端已清理，需要服务自己的会话过期机制。

401/403 提示检查认证；404 表示端点或会话不可用。超时、断线、格式错误等会关闭连接并保留执行结果不确定的暂停状态。客户端不会自动重试 POST，也不会在 404 后悄悄初始化并重放工具。先核实远端操作结果，再显式重连继续。

## 工程边界

- 默认验证 HTTPS 证书，不跟随重定向。回环 HTTP 可直接使用；非回环明文地址须显式设置 `allow_insecure_http: true`，意味着接受凭据和数据的明文传输。
- URL 不允许内嵌凭据、查询或片段。回环请求直连；其他地址沿用当前进程代理环境。
- 每次请求总超时包含持续心跳；请求和单条 JSON/事件上限 64 KiB，SSE 累计响应上限 1 MiB、最多 100 个事件。拒绝压缩响应，避免解压导致无界内存使用。
- 支持 2025-11-25、2025-06-18 的工具子集，沿用上一章有限参数 schema、文本和对象返回。暂不支持 OAuth、旧版 HTTP+SSE、后台 GET 通知流、Last-Event-ID 断点续传或完整 MCP 能力。
- 本机命令沙箱约束本地命令，不能隔离远端服务执行；Agent 自身的 HTTP 传输也不属于命令沙箱。远端结果属于不可信数据，仍需检查文件差异和测试证据。
- 客户端使用同步入口包装异步请求，适用于当前 CLI；不应直接嵌入已有的 asyncio 事件循环。

协议参考：[MCP Streamable HTTP 官方规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)。

# 31 · 上下文占用诊断

长任务变慢或频繁压缩时，需要知道请求空间花在哪里。已有 `/context` 只显示总量，本章增加分项和最大的工具定义，帮助决定缩小读取范围、减少加载工具，还是手动 `/compact`。

## 使用

在交互终端输入 `/context`，无需模型请求，也不会执行工具、修改历史或生成摘要。

输出包含：

| 字段 | 含义 |
| --- | --- |
| total_chars | 与自动压缩触发器同口径的请求 JSON 字符数 |
| system | 系统提示消息 |
| conversation | 用户、助手消息及助手发起的工具请求 |
| tool_results | 工具返回消息 |
| tool_definitions | 当前模式实际暴露的工具定义 |
| json_structure | 外层对象、数组和分隔符 |
| remaining_chars | 距离阈值的剩余字符；关闭自动压缩时为 null |
| over_budget_chars | 超出阈值的字符数 |
| compression_due | 当前快照是否超过压缩阈值 |
| largest_tools | 最大的五个工具定义，只列名称和大小 |

分项之和严格等于总量。统计保留 Unicode 字符，不把中文编码后的字节数当字符数。它不是模型 token 统计，也不能推断服务商实际上下文窗口；实际用量仍查看 `/usage`。

下一条输入尚未计入。`compression_due=true` 表示下一次预算检查需要尝试压缩，不保证一定能成功：系统提示、工具定义或必须保留的最新结果过大时，压缩可能无法解决。

## 为什么工具定义也要看

连接 MCP 后，每次请求会携带可用工具的 schema 和说明。即使尚未调用，定义也占空间。历史摘要不会缩小工具定义。计划模式会隐藏写工具，因此恢复后的统计可能比执行模式小；这是当前可用工具集合变化，并非丢失历史。

`largest_tools` 按字符数降序排列，同大小按名称排序，最多五项。诊断不打印消息正文、工具描述或历史参数，但工具名称仍属于项目元数据，不应随意公开。

## 结合代码理解

`compaction.py` 的 `context_diagnostics()` 是纯统计函数，使用和 `request_characters()` 相同的序列化方式。每条消息根据角色分组，工具定义单独累计，最后计算结构开销。`session_commands.py` 在 `/context` 分支展示报告，同时保留模式、权限、步数和原有会话轮数信息。

诊断不调用摘要模型。只有你运行 `/compact`，或后续任务请求触发自动压缩时，才进入原来的压缩流程。

# 32 · 本地 Skill 发现与资源读取

Skill 将一套任务步骤和参考材料放进目录，供 Agent 按需读取。它不会自动新增执行权限。

## 启用与使用

```bash
.venv/bin/python -m fast_agent --workspace . --skills examples/skills
```

输入“使用 review Skill 检查当前修改”。模型可以先发现 Skill，再读取说明和资源：

| 工具 | 用途 |
| --- | --- |
| list_skills | 列出目录中包含普通 SKILL.md 文件的子目录 |
| read_skill | 按目录名称读取 SKILL.md 全文 |
| list_skill_resources | 列出该 Skill 的资源目录，path 默认是 . |
| read_skill_resource | 读取相对路径文本，支持 start_line 和 max_lines |

示例目录：

```text
examples/skills/
└── review/
    ├── SKILL.md
    └── references/
        └── checklist.md
```

首次发现只返回名称、路径和文件大小，不把所有正文塞进上下文。目录名称是标识，限定为 1～64 位字母、数字、下划线或短横线，首位须是字母或数字。`SKILL.md` 可包含 YAML frontmatter，但当前版本将它作为原文，不解析或执行其中的配置。

## 权限和工作区

`--skills` 必须显式提供，并指向工作区内独立子目录。不扫描用户主目录，不自动安装、下载或执行 Skill。未提供参数时，不注册这四个工具。

四个工具均为只读，计划模式可用。Skill 内容不能覆盖用户约束、AGENTS.md 或工具权限。即使说明要求“忽略审批”，命令和编辑仍由已有权限层判断。这里保障的是工具的权限边界，不保证模型永远不会受文本误导。

资源路径只允许在该 Skill 内，拒绝绝对路径和 `..`。逐层目录描述符配合 `O_NOFOLLOW` 拒绝符号链接；只读取普通 UTF-8 文本文件，拒绝 FIFO 等特殊文件。当前实现面向本项目 macOS/POSIX 环境，未实现 Windows 兼容层。

单文件最多 64 KiB；资源每次最多 200 行，默认从第一行读取 200 行。每层目录最多 200 个条目，超限报错，需要拆分目录。读取脚本只返回文本；执行必须另走命令工具与审批，不能直接把目录外资源纳入 Skill。

## 保存和恢复

读取结果作为普通工具消息进入历史，会被保存，也会占用 `/context` 中的工具结果空间。加载会话不会恢复 Skill 目录授权或注册工具；新进程需要再次提供 `--skills`。恢复仍进入计划模式。历史中的内容可能过时，继续任务时应重新读取当前说明和资源；本版本没有自动版本固定或内容刷新。

## 与其他机制的区别

- AGENTS.md：适用于工作区及目标文件的开发规则。
- Skill：按任务读取的操作步骤和参考资源。
- 本地工具扩展 / MCP：提供可以调用的外部能力。

本版本不支持自动匹配 Skill、安装市场、脚本直执行、frontmatter 权限声明或完整第三方 Skill 运行环境。资源中的链接不会自动访问。

## docs/tutorial/33-skill-metadata.md

# 33 · Skill 名称与用途元数据

上一章通过目录名发现 Skill。本章让 `list_skills` 同时返回用途，使模型能先选择相关 Skill，再读取正文。

## 编写说明

```yaml
---
name: review
description: >
  检查 Python 修改的测试证据和 Git 差异。
  适用于小型代码审查。
---
```

在结束分隔符之后写 Markdown 操作说明。`name` 必须与目录名一致；`description` 最多 1024 字符。字段均可省略，无 frontmatter 的旧文件返回目录名和空用途。

只支持 name 和 description。暂不接受其他字段，包括 allowed-tools、模型选择和自动执行声明。不要把其他工具生态中的 Skill 配置直接当作本项目的权限授权。

## 发现和错误处理

`list_skills` 返回名称、用途、路径和大小，不返回正文。磁盘端会有界读取文件用于校验，因此这不是“从不读取正文文件”；节省的是发给模型的上下文。每个文件仍受 64 KiB 限制，头部受 8 KiB 限制。

一个文件格式错误时，它进入 errors 列表，其他合法 Skill 仍可发现。`read_skill` 也重新校验头部，错误时不返回正文。已有脚本、文件读取和命令审批边界保持生效。

用途描述仍是本地文件内容，不能覆盖用户要求或提升权限。本版本由模型根据描述选择，不实现自动评分或自动激活。

## 解析实现

`skill_metadata.py` 先限制 YAML 标记数量，并拒绝锚点、别名和显式标签，再使用 SafeLoader 生成语法节点。只接受顶层映射及字符串标量，显式拒绝重复键；不实例化 YAML 中的 Python 对象。普通文本、引号字符串和折叠多行描述均可使用。

参考 [PyYAML 官方文档](https://pyyaml.org/wiki/PyYAMLDocumentation)。运行依赖已声明 `PyYAML>=6,<7`，新环境通过项目安装命令获取。

测试覆盖多行中文描述、旧文件兼容、名称不一致、重复键、错误类型、别名/标签、未知权限字段、超限与错误邻居隔离。继续复用上一章权限及保存恢复测试。

## docs/tutorial/34-tool-output-retention.md

# 34 · 工具结果统一限额与落盘

文件检索、Skill 和 MCP 都可能产生长结果。单独限制命令日志不够，本章在 Agent 写入工具消息前增加统一处理。

## 数据流程

工具执行 → 判断未知结果 → 计算原始失败签名 → 结果限额与保存 → 写入历史 → 返回模型。

结果 JSON 不超过 16,000 字符时保留原样。超过后，只向模型提供最多 2,000 字符预览、原始长度和 output_ref。完整 JSON 最多保存 1 MiB，超过部分明确标记 storage_truncated。记录位于工作区私有 `.fast-agent/tool-outputs/`，沿用原子写入和文件权限设置。

模型使用 `read_tool_output(output_id, offset, limit)` 按字符读取；默认每页 4,000 字符，最大也是 4,000。next_offset 用于下一页。eof 仅表示已保存内容读完，不能证明原始结果完整；还必须看 storage_truncated。存储截断的 JSON 片段不保证能独立解析。

## 保持原有执行语义

裁剪不会改变 ok；保留有限长度的 error，以及 uncertain、returncode、status 等状态。重复失败检测使用裁剪前的结果，记录 ID 不影响连续失败判断。

落盘失败时返回 storage_error，保留预览和原操作状态，不把“保存日志失败”误报成“文件修改失败”。应重新核实，不得因此重放写操作。已处于结果未知状态的写工具仍走原来的暂停流程。

这限制的是进入模型历史的结果大小；工具在产生结果时仍需自身的内存和输出限制。磁盘记录可能含源码和敏感业务内容，保存会话不会将这些记录打包迁移。跨工作区复制会话后，旧引用不保证可读取。当前没有自动清理策略，清理前应确认相关会话不再需要这些证据。

## 验证

本地测试覆盖小结果不变、中文大结果分页还原、存储截断、落盘失败、长失败连续暂停，以及保存恢复后按引用读取。实现入口：`tool_outputs.py`、`agent.py`。


## docs/tutorial/35-user-questions.md

# 35 · 模型主动向用户提问

Agent 遇到需求歧义时，可以调用 `ask_user`，暂停当前同步循环等待终端回答，然后将回答作为工具结果交回模型。

## 调用与交互

参数 question 为问题，choices 是可选的选项列表。问题最多 2,000 字符，最多五个选项，每项最多 200 字符；回答最多 4,000 字符。

交互式终端显示问题后，可以输入文字或选项编号。空行和 EOF 表示未回答，不得视为同意。Ctrl+C 进入现有的任务中断流程。

只有真实交互式 CLI 入口绑定输入回调。`--prompt` 等非交互入口不会阻塞等待 stdin，会返回明确失败，要求模型说明待确认事项。嵌入式调用可显式提供 ToolContext.ask_user 回调。

## 澄清与授权不同

此工具在计划模式可用。回答“使用方案 A”不会改变计划模式、命令白名单或文件修改审批；真正执行时仍需通过现有权限层。

问题和回答会写入对话历史，可随会话保存。恢复只加载历史，不重放提问。这里没有异步消息队列或持久化待回答表单：进程退出后，未回答的问题应由新任务重新确认。不要在这个普通输入框输入密钥。

本地测试验证回答进入工具历史、恢复不重复询问、空回答、选项编号和不提升权限。真实 MiniMax 交互验证待服务恢复后补齐。


## docs/tutorial/36-skill-lifecycle.md

# 36 · Skill 显式使用与加载状态

输入 `/skills` 可以查看已配置目录里的 Skill、用途和本进程读取状态。输入 `/skill review 检查当前修改` 会先读取 review 的最新 SKILL.md，再将任务和参考材料交给模型；此命令会发起模型请求。

## 状态含义

- not_loaded：当前进程没有可用的读取标记。
- unchanged：说明文件指纹与上次读取时一致。
- changed：说明文件已经变化，应重新读取。

`read_skill` 计算 UTF-8 内容的 SHA-256。`list_skills` 比较当前内容与标记，不修改标记；查看状态不调用模型。模型通过工具读取和用户通过 `/skill` 读取使用同一套逻辑。

指纹仅覆盖 SKILL.md，不覆盖引用资源；资源使用前仍应重新读取。标记表示文件读取过，不保证模型每次请求都保有全文，也不保证说明正确。大结果仍可能被统一限额机制替换为预览和引用。

## 压缩、恢复和权限

成功压缩、裁剪历史、切换模式、重置或恢复会话会清空读取标记。压缩失败保留原标记。之后可以通过 `/skill 名称 任务` 或 read_skill 显式重新读取；当前不自动把全文重新注入摘要，以免重新撑满上下文。

保存会话会保存已进入历史的材料，但不保存读取标记或目录授权。新进程仍需提供 --skills，恢复默认计划模式。`/skill` 不会切换到执行模式，也不提供文件修改或命令授权。

未启用目录、名称不存在或说明格式错误时，命令报错且不调用模型。裸 `/skill review` 缺少任务，也不会发起请求。任务和 Skill 材料以当前用户发起的请求进入历史，参考材料明确注明不能覆盖用户约束及工作区规则。

## 验证

离线测试覆盖显式调用、文件变化、状态查询不调用模型、无效请求、压缩失效和恢复失效。真实 MiniMax 验证仍单独记录，不能以离线测试替代。

本轮验收：417 项本地测试通过；MiniMax 真实 Skill 调用与保存恢复 8/8 项断言通过，6 次请求，unknown_requests=0。复现脚本为 `examples/real_skill_lifecycle_demo.py`（凭据通过环境配置），报告位于 `.fast-agent/validation/skill-lifecycle-real.json`。这验证当前示例链路，不代表所有外部 Skill 都兼容。


## docs/tutorial/37-worktree-isolation.md

# 37 · Git worktree 独立任务目录

同一仓库的两个任务直接修改同一个目录，容易覆盖彼此的改动。本章提供本地命令 `/worktree-create 名称`，创建独立检出目录，再由用户启动新的 Agent 会话。

## 使用步骤

从主 Git 仓库根目录启动交互式 Fast Agent，保持执行模式，输入：

```text
/worktree-create fix-parser
```

程序先解析当前 HEAD，展示完整提交标识和目标路径，再请求确认。确认后创建 `.fast-agent/worktrees/fix-parser`，使用 detached HEAD；不创建分支，不复制工作区未提交修改。

复制返回的绝对目录，以 `fast-agent --workspace /绝对目录` 启动独立会话。在新会话里重新检查 AGENTS.md，显式配置 Skill、MCP 和质量检查。主会话不会自动切换目录，既有历史也不会自动迁移。

完成后使用新目录中的 git_status、git_diff 和原有测试工具检查结果。新文件需要结合 Git 状态检查，普通 diff 不自动展示未跟踪文件内容。首版不自动提交、合并、推送或删除 worktree；因此变更交付和安全清理仍需后续完善。

## 创建边界

- 只接受普通主仓库根目录，要求 .git 为真实目录；不从已有 linked worktree 或仓库子目录再次创建。
- 名称最多 48 位，仅允许字母、数字、下划线和短横线，首位须为字母或数字。目标必须不存在，拒绝覆盖及符号链接。
- 计划/只读模式或非交互入口不能授权创建；有未核实操作时沿用原来的阻塞规则。
- 当前 macOS 命令沙箱禁止写入 Git 元数据，因此开启该沙箱时本命令明确拒绝，不自动降级。
- 创建时禁用 Git hooks，不继承 GIT_DIR 等重定向环境和模型凭据。仓库自行配置的检出过滤器仍可能执行，确认提示会明确说明；只在信任的仓库使用。
- worktree 共享 Git 对象库，不是安全沙箱。父仓库中的 Agent 也并非无法读取其内部子目录；本功能提供任务文件隔离，不是恶意代码隔离。

建议主仓库将 `.fast-agent/` 加入忽略规则；本命令不自动修改 .gitignore。根目录未提交的规则或配置不会出现在新检出中，必须核对。

## 中断与验证

Git 创建失败或超时后，不会自动清理目录或重试覆盖。请用 `git worktree list` 核实 Git 实际登记和目标内容；残留结果需要人工判断。

实现位于 `worktrees.py` 和本地命令分发中，没有注册为模型工具。测试在临时真实 Git 仓库中验证：父目录脏文件保留、新工作区独立修改、Agent 文件工具在新目录工作、权限拒绝、链接拒绝和已存在目录拒绝。

新版创建时还保存固定基点，后续可以通过 [第 39 章的交付命令](39-worktree-delivery.md) 导出完整变更包；自动合并和清理仍未实现。


## docs/tutorial/38-readonly-delegation.md

# 38 · 只读子 Agent 委派

输入 `/delegate 阅读 src 中的调用流程，给出文件位置和依据`，主会话会同步启动一个探索子任务。

子任务拥有新的系统提示和对话历史，不复制主会话的消息、文件读取版本或 Skill 状态。它只能使用内置的文件读取、文件列表、代码搜索、规则读取、Git 状态与差异、工具结果分页读取。即使模型请求写入、执行命令或提问，也会因工具不存在而失败。本地扩展和 MCP 不会继承。

## 预算与结果

子任务最多调用模型 `min(5, 主会话步数)` 次，不做自动摘要；仍使用同一个模型客户端和请求预算，所以请求与 token 用量计入 `/usage`。网络重试也沿用已有总请求预算。这里是步数限额，不是时间或 token 硬上限。

结果保存到 `.fast-agent/delegations/<ID>.json`，包含 `completed`、步数、工具名称及成功状态、最多 16000 字符的报告。工具成功只说明调用结果，不能证明模型结论正确。达到步数、用户按 Ctrl+C、模型服务失败均保留未完成状态。Ctrl+C 的响应速度受同步网络调用影响。

报告仅打印并落盘，不自动注入主会话，也不被当作用户指令。主会话历史保持不变，保存和恢复主会话不会重放子任务。可根据报告继续给主 Agent 下达明确任务。

## 代码流程与边界

`delegation.py` 重新构建内置白名单注册表 → 创建只读 ToolContext → 使用相同模型启动新 Agent → 收集 tool_end 证据 → 恢复父事件回调 → 原子保存报告。

这里隔离的是对话和工具权限，文件系统仍是同一个工作区；运行记录可以写入 `.fast-agent`。它不是操作系统安全沙箱，也不是独立进程。首版不支持并行、后台恢复、写入子任务、递归委派或自动汇总进主会话。后续需要在共享模型回调和预算的并发语义明确后再扩展。

报告现支持 `/delegations [页码]` 和 `/delegation ID` 查看，详见 [整体架构中的执行与仓储分离](../architecture.md#_4)。


## docs/tutorial/39-worktree-delivery.md

# 39 · worktree 变更交付与真实修复验收

第 37 章创建独立目录；本章让修改成为可核对的交付包。先在主仓库 `/worktree-create repair`，再在返回的目录启动 Agent 修复和测试。回到主仓库的执行模式，输入 `/worktree-export repair`，确认后获得本地 JSON 交付记录路径。

## 交付的内容

创建时记录固定 `base_commit`。导出使用这个基点与当前工作目录比较，因此包含子工作区已经提交、暂存和未暂存的最终变化，而不是只执行普通 `git diff`。新文件需要由用户明确暂存。删除、文件模式及二进制变化通过 Git 的完整补丁表达。

交付记录位于 `.fast-agent/worktree-exports/<ID>.json`，保存基点、当前 HEAD、状态、补丁字节的 SHA-256 和 `patch_base64`。Base64 避免非 UTF-8 内容损坏；校验值用于核对字节一致性，不是签名或来源认证。补丁上限 2 MiB，超限拒绝；生成过程先暂存到临时文件再有界读取，临时磁盘使用不受此内存读取上限约束。

## 为什么拒绝交付

- 没有创建记录的旧 worktree：无法可靠知道最初基点，不能用当前 HEAD 猜测。
- 路径与记录不符、链接目标或共享 Git 目录不匹配。
- 存在未解决冲突、未跟踪文件（`.fast-agent` 运行记录除外）、被跟踪的运行记录或子模块。
- 两次补丁及前后状态不一致：采集期间发生修改，应停止其他写入者后重试。
- 计划/只读模式或未批准导出。导出会写本地运行记录，沿用现有授权规则。

忽略文件不会进入补丁，确认需要交付的内容没有被忽略。重复采集是并发变化检测，不是对任意编辑器或 Git 进程的强制锁；请在静止的工作区导出。此功能不是安全沙箱。

## 接收与复测

先查看记录并核对基点；在这个精确基点的**干净检出**中，将 `patch_base64` 解码为补丁，核对 SHA-256，运行 `git apply --check`。检查通过后才应用，再运行项目测试和检查 Git diff。检查成功不等于测试通过，也不代表补丁可以安全应用到有脏修改的主目录。

本功能不自动应用、合并、提交、删除 worktree，也不清理父目录。自动合并和安全清理需要单独的冲突与丢失保护流程。

## MiniMax 验收流程

`examples/real_worktree_delivery_demo.py` 创建带失败加法测试的临时仓库，让 MiniMax 实际读文件、运行测试复现、编辑源码、重跑测试并查看 Git 状态与差异。宿主程序另外运行测试，核实测试文件和父目录脏修改保持不变。随后导出补丁，在精确基点的第二份干净检出中检查、应用并再次测试。模型的文字结论不作为通过依据。

实现入口：`worktrees.py` 的 `create_worktree` 和 `export_worktree`。离线测试还覆盖二进制补丁、冲突、未跟踪文件、错误记录以及采集期间的文件变化。

2026-10-20 验收：MiniMax 12/12 项通过，6 次请求；本地全量 436 项通过。真实报告保存在 `.fast-agent/validation/worktree-delivery-real.json`，记录为本次运行结果，不代表未来服务一直可用。


## docs/tutorial/40-skill-resource-versions.md

# 40 · Skill 资源版本与变更失效

Skill 的说明没变，配套检查表或示例可能已经变化。只记录 SKILL.md 的摘要不足以判断本轮依据是否仍有效。本章在原有只读权限和路径约束内，为**实际读取过的资源**记录内容版本。

## 分页时固定版本

首次调用 `read_skill_resource` 得到 `sha256`。读取后续页时，把这个值作为 `expected_sha256` 传回。如果文件已变化，工具返回失败及当前摘要，不返回新页正文，并提示从第一页重新读取，避免把两个版本拼成一份材料。

不传版本参数时仍允许读取当前版本，保持已有调用方式兼容。结果提供 `previous_sha256` 和 `changed`；如果 changed 为 true，旧内容不能作为当前依据，应重新读取说明和资源。SHA-256 描述本次读取的完整文本，而不是所返回的某一页。摘要不是签名，也不证明内容可信。

## 加载状态如何失效

- `/skills` 或 `list_skills` 会重新检查已读资源，返回 `resource_changes` 路径列表；内容变化、删除、链接替换或无法读取都按失效处理，清除该 Skill 的说明加载标记。
- 直接读取已读资源时发现变化或无法读取，同样使说明加载标记失效。旧资源摘要保留用于比较，只有成功读取当前内容才更新。
- `/reset`、`/trim`、模式切换、会话恢复，以及成功的手动或自动压缩，都会清除资源版本标记。恢复历史不代表资源仍是旧版本，需要再次读取。

这些操作不会删除历史中的旧文本或自动运行 Skill。历史仍是当时的记录，模型应以新读取结果作为当前依据。重新加载说明不会悄悄把旧资源标记为新版本。

## 检测范围和限制

每个 ToolContext 最多保存 64 个已读资源标记，单文件继续限制 64 KiB，目录和路径沿用此前的限制。发现时最多重读这 64 个文件，不递归扫描所有配套资源。未读取过的新增文件、资源树整体版本固定、文件监控和自动重新注入仍未实现。

这是调用时的内容检测，不是文件系统快照。外部程序应完成写入后再读取；运行中的原地写入不受此机制锁定。后续页传入 expected_sha256 可以检测与此前版本不一致，但不会阻止其他程序改文件。

## 代码与验收

`ToolContext.skill_resource_reads` 按 Skill 名称和规范化相对路径保存摘要；`skills.py` 在发现和读取时比较内容。Agent 和本地会话命令统一清理这组标记。

`examples/real_skill_versions_demo.py` 让 MiniMax 读取旧代号，由宿主更新资源，核对发现失效和旧版本分页拒绝，再让模型实际重读新代号。保存恢复后再次调用工具读取，而不是只复述已有历史。离线测试覆盖未变化分页、变化读取、删除、链接替换、标记数量限制和恢复清理。

2026-10-20 验收：本地全量 442 项通过。MiniMax 首次未完整通过并保留失败报告；一次有限重跑后 12/12 项通过，9 次请求。成功报告位于 `.fast-agent/validation/skill-versions-real.json`。


## docs/tutorial/41-worktree-archive.md

# 41 · worktree 安全归档与恢复

交付补丁不包含所有本地内容。未跟踪笔记、忽略文件、命令日志和任务检查点都可能仍有价值。为了先保证不丢失数据，本章的“清理”是把整个 worktree 移出活动目录，**不删除工作区，也不释放磁盘空间**。

## 使用流程

先停止目标目录里的 Agent、后台命令和编辑器写入。从普通主仓库根目录的执行模式输入：

```text
/worktree-archive repair
/worktree-restore repair
```

每次都要经过既有权限确认。归档通过 `git worktree move` 把 `.fast-agent/worktrees/repair` 移到 `.fast-agent/archived-worktrees/repair-<随机 ID>`，保留 Git 登记、独立提交、暂存区、脏文件、未跟踪文件、忽略文件和全部运行记录。恢复时移回原路径，目标存在则拒绝覆盖。

归档目录仍是 Git worktree，不能当作可以随意删除的压缩备份。已有任务记录包含绝对路径，归档期间不要直接在新路径恢复旧任务；先恢复到原位置。证据内容不会被程序批量改写。归档使用过的名称不会分配给另一个新工作区。

## 拒绝条件

- 路径不是本程序记录的工作区，或不属于当前主仓库；链接路径和含子模块的工作区也拒绝。
- 计划/只读模式、未授权、启用了当前命令沙箱。
- 无法获得目标任务锁，或发现活动/未知/格式无效的任务、后台命令、编辑批次记录。
- 任一类任务记录超过 1000 项，无法在约定范围内核查。
- 存在未确认的移动记录或恢复目标已占用。

已完成的任务证据原样保留。未知结果即使已有人工说明，首版仍采取保守拒绝，不通过删除记录来绕过。请先核对原因，再等待专门的异常恢复流程。

## 中断与并发边界

移动前写入 `worktree-archives/<名称>.json`，状态为 `moving_archive` 或 `moving_restore`；Git 移动成功且路径和 HEAD 核对通过后，才写入 `archived` 或 `restored`。

如果移动完成但状态写入失败，程序也不声称成功，不自动反向移动。请检查 `git worktree list`、记录中的两端路径与文件内容。保留不确定记录以阻止盲目重试；本版不提供自动修复这些记录的命令。

任务锁能阻止遵循同一锁的操作，但不能锁住所有外部编辑器、无检查点 Agent 或独立进程。确认提示要求先停止这些写入者；不要在活动目录仍被使用时归档。归档操作不是文件系统快照、磁盘备份或操作系统安全沙箱。

## 实现与验收

`worktree_lifecycle.py` 专注归档与恢复，复用 RuntimeStore 和 worktrees.py 的 Git 调用。执行顺序为：校验归属 → 获取任务锁 → 检查任务状态 → 授权 → 再次检查 → 写移动记录 → Git 移动 → 核实路径/HEAD → 更新状态。

本地测试核对脏修改、独立提交、忽略的二进制文件、运行证据在归档/恢复前后字节一致，并验证活动任务、锁冲突、目标冲突和移动后中断。

真实验收扩展 `examples/real_worktree_delivery_demo.py`：MiniMax 修复失败测试并完成交付，宿主再添加未交付笔记和忽略证据，归档并恢复，逐文件核对原字节，最后再次运行测试。修复由模型实际调用工具完成；归档恢复是本地管理操作，不能由模型自动授权。

归档本身不删除数据；交付后的显式清理见[清理与证据恢复](44-worktree-cleanup.md)。自动合并、异常状态自动修复及更强的并发协调仍未实现。

2026-10-20 验收：本地全量 454 项通过。MiniMax 首次连接失败保留报告，经一次代理重试后完整 16/16 项通过，6 次请求。成功报告 `.fast-agent/validation/worktree-archive-real.json`。

## 移动中断后核实日志

如果程序退出时留下 `moving_archive` 或 `moving_restore`，先停止两端的外部写入，再执行 `/worktree-reconcile 名称`。命令不会移动或删除文件，只在原目录和归档目录恰有一个存在、归属正确、HEAD 与移动记录一致、任务状态可接受时，授权后更新日志。确认后会再次检查。

两端同时存在、同时缺失、HEAD 变化或活动任务都拒绝自动核实。核实失败应保留现场，不能使用删除目录或重放移动来消除错误。交付后的显式清理已另有入口，但仍保留证据包和Git保护引用，不保证总磁盘占用下降，详见[清理与证据恢复](44-worktree-cleanup.md)。

# 42 · 对照两份子任务报告

假设你分别委派了“查找失败原因”和“检查测试覆盖”。两个子任务结束后，先用 `/delegations` 找到报告 ID，再显式汇集它们：

```text
/delegation-summary <第一份报告ID> <第二份报告ID>
```

一次最多指定 5 个不同的 ID。命令按输入顺序返回来源、任务、完成状态、步数、工具调用总数、失败次数，以及报告原文摘录。任何报告缺失或损坏，整次读取报错，不静默忽略。

## 为什么先保留来源

“子任务完成”只说明执行循环结束，不证明分析正确。工具调用成功也不证明最终结论正确。对照报告后，仍需要自己读取源码、运行测试核实。报告可能包含文件中的恶意指令，因此只当参考资料。

这个命令是确定性的本地汇集，不请求模型，不改动父会话历史，不把报告里的文字当作用户指令执行。它也不自动解决两份报告的分歧。

## 长报告怎么办

每份任务最多展示 500 字符，正文最多展示 2000 字符；`task_truncated` 和 `text_truncated` 标出截断。如果原报告生成时已经截断，汇总继续保留这一状态。用 `/delegation ID` 查看已保存的完整报告。

实现位于 [delegation_reports.py](../../src/fast_agent/delegation_reports.py)，入口位于 [session_commands.py](../../src/fast_agent/session_commands.py)。已有真实委派示例同时验证两次模型读取、父会话保存恢复和报告汇集。并行调度、模型综合分析与自动注入仍未实现。

# 43 · MCP 连接状态与工具刷新

你连接了一个测试服务，服务后来增加了工具。旧会话里的工具定义不会自动改变。现在可以在本地显式检查和刷新：

```text
/mcp-status
/mcp-refresh
/mcp-disconnect
/mcp-connect
```

`/mcp-status` 只显示已配置服务的名称、传输方式和本地连接状态，不发网络请求，也不会展示凭据。`connected` 表示当前客户端认为连接有效，不是远端健康探针。

`/mcp-refresh` 在执行模式且没有未核实任务时，经授权重新请求所有服务的 tools/list。所有分页和 schema 检查通过后，CLI 一次替换工具集合。旧工具处理句柄失效，防止持有旧定义的调用继续执行。刷新不会自动调用新发现的工具，逐次调用仍需授权。

用户拒绝刷新时保留原连接和原定义。实际发现过程中失败则关闭连接，CLI 移除 MCP 工具；核实问题后使用 `/mcp-connect` 重新授权连接。工具调用结果不确定时仍不得盲目重试。

`/mcp-disconnect` 关闭客户端并移除定义，可以在计划模式使用。恢复会话仍关闭旧 MCP 连接，不复用过去的执行授权。

## 验证方法

实现入口：[mcp_tools.py](../../src/fast_agent/mcp_tools.py)、[cli.py](../../src/fast_agent/cli.py)。本章演示静态环境凭据；需要交互授权的HTTP服务可继续阅读[OAuth生命周期](50-mcp-oauth.md)，其中说明登录、刷新和撤销。自动通知刷新和持续健康检查也未实现。

## docs/tutorial/44-worktree-cleanup.md

# 44 · 清理工作区，同时保留证据

归档只移动目录，不释放空间。任务交付后，可以先预览再显式清理已归档的工作区：

```text
/worktree-cleanup-preview 名称
/worktree-cleanup 名称
```

清理要求工作区归属和归档状态一致、没有活动或未知任务、没有未提交的跟踪文件变化，而且归档 HEAD 必须已经位于主仓库 HEAD 的祖先链。仅导出补丁不等于完成这个交付条件；独立提交仍会拒绝清理。

## 先保留什么

程序把除 `.git` 管理指针外的全部文件保存在私有证据包，包括未跟踪、忽略文件、二进制、权限和空目录。最多 8 MiB、4000 项，超限直接拒绝，不截断。链接、特殊文件和特殊权限也拒绝。每个文件都有校验值，包落盘后重新读取验证。

确认前必须停止外部编辑器和进程写入。内部任务锁并不能阻止所有外部程序。确认后再次采集对照，变化时拒绝清理；提交另存 Git 引用。随后才移除工作区。证据包继续占用空间，因此不保证总磁盘占用下降。

## 恢复与中断

返回的证据 ID 可用于 `/worktree-evidence ID`。恢复只写入全新的证据目录，不覆盖路径，不执行其中脚本；这是文件恢复，不会自动重新注册 Git worktree。

若删除中断，使用 `/worktree-cleanup-reconcile ID`。它核对证据、受保护提交、目录及 Git 注册，只更新状态，不重试删除。目录仍存在但内容变化、目录与注册不一致等情况需人工核实。

清理证据包与Git保护引用当前采用无自动到期策略，不提供删除这两类证据的命令；其他运行记录的隔离、恢复和到期清除见[存储回收](46-storage-retention.md)。源码入口：[worktree_cleanup.py](../../src/fast_agent/worktree_cleanup.py)、[worktree_snapshot.py](../../src/fast_agent/worktree_snapshot.py)。

# 45 · 问题没回答，退出后怎样继续

```text
/answer 问题ID 只修复 A
```

## docs/tutorial/46-storage-retention.md

# 46 · 先看引用，再决定回收

长时间使用后，工具大结果、委派报告和问题记录会逐渐积累。旧文件不一定没用了：保存的会话可能还持有它的 ID。

```text
/storage-preview 30
```

命令只做预览，不删除文件。候选范围是问题、委派和工具大结果的 JSON 记录；默认保留 30 天，按文件修改时间估算。输出包括候选、受保护记录、引用来源和阻塞项。

出现以下情况时保留：未满保留期；问题未回答；其他运行记录包含该 ID。活动或未知状态会阻塞回收。存在损坏记录、链接、扫描超限时直接报错，不能把没读到的引用当作不存在。

当前引用识别采用保守的 ID 文本匹配，可能多保留，不是语义引用图。扫描包含主工作区以及 worktrees、archived-worktrees、restored-evidence 下独立工作区的 `.fast-agent` 记录；全局最多 32 个工作区、1000 条记录、32 MiB。隔离 `.record` 和清理证据包中的快照内容也参与引用匹配。子工作区记录只作为引用依据，不成为主工作区回收候选。清理证据包、Git 保护引用和工作区本身不在自动候选范围。

可恢复隔离与恢复已接入下方命令，永久回收需按下方保留期和确认流程执行，不应手工按候选列表直接删除。实现入口：[retention.py](../../src/fast_agent/retention.py)。

## 从预览到可恢复隔离

使用 `/storage-preview 30` 查看候选和 fingerprint 后，执行 `/storage-quarantine 指纹 30`。这一步需要现有权限控制的确认：再次扫描全部记录、比对引用和内容指纹，变化则拒绝。确认前应停止其他写入运行记录的进程；任务锁只能约束遵守本项目锁协议的进程，不能冻结外部编辑器。

候选通过独占创建硬链接、核对哈希与文件身份，再移除原名字的方式移入私有隔离目录，原始字节保留；目标已存在则拒绝。读取哈希时不跟随符号链接，并拒绝特殊文件。返回批次 ID 后可用 `/storage-restore ID` 恢复原路径。恢复拒绝内容变化、缺失和已有目标冲突，绝不覆盖冲突文件。崩溃后可对部分移动/恢复状态重新恢复；如果同一记录两个位置同时存在，则保守报错，保留两份供人工核实。移动/恢复中状态也会阻止工作区归档。

这只是可恢复隔离，不释放全部磁盘空间。永久清除仅适用于下方已到保留期的隔离记录；worktree 清理证据包和 Git 保护引用仍不属于回收候选。


## 永久回收隔离记录

```text
/storage-purge-preview 批次ID 30
/storage-purge 批次ID 预览指纹 30
```

隔离保留期默认 30 天，最短 7 天。以成功隔离时记录的时间为准，不使用隔离文件的 mtime。旧版本缺少时间记录的批次不能直接永久删除，需先恢复再隔离。

预览重新检查当前及独立工作区引用、内容哈希、活动状态与原路径冲突。仅忽略本批次清单和本批次待一起删除的隔离内容；其他批次、会话、归档工作区或清理快照中的引用都会拒绝删除。执行还需不可逆确认，并再次扫描。计划模式与非交互无授权时拒绝。

每项在删除前保存 `deleting` 意图，删除后保存 `deleted`，全部完成后标记 `purged`。中断时可以重新预览同一批次；只有已有删除意图的缺失文件才能被接受，仍需再次确认才继续，不会后台自动重放删除。清单、哈希和时间记录保留，内容永久删除后不能再恢复。工作区、清理证据包、Git 保护引用不在此接口的删除范围。

运行回收期间应停止外部写入进程；内部任务锁不能冻结其他程序。测试使用临时目录，覆盖保留期、引用保护、确认期间新增引用、删除中断及再次授权。

## 清理证据与 Git 保护引用保留多久

普通内容和恢复证据使用不同保留规则。预览输出中的 `retention_policy` 明确列出以下三类记录，`automatic_expiry: null` 表示没有自动到期时间：

| 对象 | 保留原因 | 普通回收行为 |
| --- | --- | --- |
| `worktree-cleanups` 证据包 | 保存被清理工作区的文件快照与任务证据 | 不隔离、不永久删除 |
| `refs/fast-agent/cleanups/…` Git 引用 | 防止被清理工作区所指提交被 Git 垃圾回收 | 不修改、不删除 |
| `retention` 审计清单 | 永久删除后仍能核对原路径、哈希、时间与状态 | 始终保留清单 |

`retained_evidence` 列出扫描到的证据包和回收清单的路径、字节数及哈希，便于核对空间来源。该列表不是恢复成功证明；它也没有检查 Git 引用是否实际存在。验证具体工作区时仍需使用清理核实/恢复接口，它们会核对受保护提交。

这意味着永久回收普通工具结果后，证据包仍可能占用空间。这是明确的保留策略，而不是后台遗漏清理。当前不提供删除唯一恢复证据或 Git 保护引用的命令；不能为了腾空间手工删除它们，然后仍宣称可恢复。备份或迁移主仓库时，应一起保存 `.fast-agent` 记录和这些本地 Git 引用。

## 完整流程验收

已有真实模型配置后，可运行：

```sh

```

脚本只操作自己创建的临时工作区。模型先实际分页读取长工具结果，宿主保存含该 ID 的会话，检查结果受到引用保护。移除该临时会话后，宿主走预览、确认隔离和恢复，逐字节核对原记录，并再次通过读取工具访问它。

## docs/tutorial/47-skill-tree.md

# 47 · 整套 Skill 材料变了怎么办

只记录读过的文件，会漏掉新加入的规则或尚未读取的资源。`inspect_skill_tree` 对指定 Skill 的全部资源计算版本：路径、内容、文件权限均进入指纹，包含空目录，不执行任何脚本。

```text
先调用 inspect_skill_tree(name="review")，再 read_skill 与 read_skill_resource。
```

检查后，读取说明或资源都会在读取前后核对资源树。发生变化就拒绝正文，并清除已读说明和资源标记；重新调用 inspect_skill_tree 接受新版本，再从说明和资源第一页重新读取。也可传 `expected_tree_sha256` 要求特定版本，不匹配时拒绝。

检查最多 1000 项、4 MiB、16 层；链接和特殊文件拒绝，超限不做部分指纹。资源版本检查可以覆盖二进制，但正文读取仍只支持现有的 UTF-8 文本接口。会话恢复、压缩和重置清除树标记，需要重新检查。

这不是文件系统快照：外部进程仍可修改文件；也没有后台监控。它提供有界、按需的乐观版本校验，执行脚本前仍需权限和现有规则检查。

## docs/tutorial/48-window-recovery.md

# 服务窗口超限后如何继续

字符预算只是本地提示。模型服务仍可能因自己的 tokenizer、窗口限制或工具定义大小拒绝请求。这里学习如何在服务明确拒绝时恢复，而不是无限增加重试次数。

## 一次请求经历什么

1. `OpenAIModel._request` 识别 HTTP 400/413/422 且错误码为 `context_length_exceeded` 或 `context_window_exceeded` 的响应；另兼容实测 MiniMax HTTP 400、`bad_request_error`、精确文本 `invalid params, context window exceeds limit (2013)`。普通 400 或仅含相似词句不会触发压缩。
2. 若还没收到任何响应片段，抛出 `ContextWindowError`；已经收到角色、推理、文本或工具参数片段后，仍按普通失败停止，避免重放。
3. `Agent._run` 每次任务最多恢复一次。使用现有压缩器保留当前目标和完整工具配对，摘要有效后保存 `overflow-…` 原始会话，再采用摘要并重新请求。
4. 第二次窗口超限、摘要失败或没有可压缩历史时停止，保留可检查的会话。摘要请求本身超限也不会递归调用恢复。

例如旧对话很长、当前目标很短时，第一次请求被拒绝，第二次请求生成旧对话摘要，第三次请求使用摘要继续处理当前目标。三个请求都会进入已有请求预算与用量记录；不是免费重试。

## 为什么不直接删消息

工具结果必须与 assistant 的工具调用 ID 成对。只删除长工具结果会破坏协议，也会让模型误判哪些操作已经执行。这里复用 `compact_history` 的完整轮次/工具批次边界，保留备份，并使 Skill 已读版本标记失效。

## 当前边界

恢复路径由明确错误码驱动；下文另有显式窗口估算，但没有精确 tokenizer 或供应商窗口自动发现。不认识的服务错误仍会停止。单条用户输入或工具定义已经太大时，压缩旧历史也无法解决，需要缩小输入或工具集合。自动字符压缩设为 0 时，服务明确超限仍允许这一次恢复。

本地测试覆盖分类、错误信息脱敏、备份、二次拒绝停止、无旧历史和流式部分输出不重放。下文另记录真实 MiniMax 拒绝后分段摘要并继续工具调用的 8/8 验收；该记录只覆盖指定场景，不代表所有服务与任意输入都可恢复。

## 在服务拒绝之前预留窗口

可以显式设置当前服务支持的窗口大小，不能根据模型名字猜测：

```sh
fast-agent --context-window 32768 --output-tokens 4096
```

这里的 32768 是演示配置，使用前要确认自己的模型窗口。扣除 4096 输出 token 和 1024 安全余量后，以每个序列化 Unicode 字符估算 4 token，得到 6912 字符的输入阈值，再与 `--context-chars` 取更小值。中文、代码、消息结构和工具定义都计入；压缩后也必须满足这个阈值。

这是刻意保守的跨 tokenizer 估算，不是实际 token 上界的供应商保证；可能造成提前压缩。安全余量覆盖服务额外包装的不确定性，但不能保证任意接口都足够。已有一次性超限恢复仍作为补救。

输出预留同时以 `max_tokens` 发送给兼容服务，流式与非流式一致。不支持该字段的服务会明确失败，不会静默删掉上限重试。返回被截断仍视为未完成。窗口参数为 0 时保持原有字符预算；字符预算为 0 但窗口非零时，窗口阈值仍生效。`/context` 会显示两种预算、有效字符阈值、预留值和估算方法。

## 真实模型验收记录

`examples/real_window_budget_demo.py` 在临时工作区以一个只读工具进行验收：预置长历史触发真实摘要，读取验收代号，保存后加载并再次读取。MiniMax 10/10 项通过，6 次请求，11714 个已报告 token，1 次请求用量未知。恢复保持计划模式、源文件未变，历史配对校验通过。

## 大段历史如何分段摘要

先按原有规则选出完整旧轮次或已完成工具批次；当前目标和保留的工具消息仍保持配对。序列化待摘要历史超过10万字符时，按顺序切成最多32段，每段最多10万字符。分段只是提供给摘要器的引用材料，可能从一条消息中间切开，不作为可执行会话恢复。

每段最多返回2000字符摘要，再合并成最终摘要。所有调用都沿用同一个请求预算。任何一段为空、过长、请求工具、服务失败或预算耗尽，都保留原会话；不会把已完成的部分摘要冒充完整历史。最终摘要通过大小与消息配对检查、原历史备份成功后才采用。

超过320万待摘要字符仍明确拒绝，避免无界请求。分段汇总可能丢失细节，关键文件和结论应再次读取核实；完整原文可从备份找回。`compaction_end` 记录 `summary_chunks` 与 `summary_requests`，单段历史仍只需一次摘要调用。

完整真实验收入口：

```sh

```

它发送合成超大历史，关闭预压缩以实际触发服务拒绝，再检查分段摘要、原文备份和实际工具读取。最多24次请求，不使用用户历史；长输入会产生费用，不应在普通测试或周期监控中无条件重复运行。

## docs/tutorial/50-mcp-oauth.md

# MCP OAuth：授权、刷新与登出

OAuth 让 Fast Agent 代表用户访问受保护的 HTTP MCP 服务。授权码与令牌只经过本地控制层和 HTTP 传输层，不进入模型消息。stdio 继续使用环境凭据。

## 配置与操作

在 MCP 配置中为 HTTP 服务添加 OAuth，不能同时配置 `bearer_env`：

```json
{
  "servers": [
    {
      "name": "secured",
      "url": "https://mcp.example/mcp",
      "oauth": {
        "issuer": "https://auth.example",
        "client_id": "your-registered-public-client",
        "scope": "read",
        "port": 9000
      }
    }
  ]
}
```

这些是示例地址，需换成实际服务及预注册公共客户端信息。回调为 `http://127.0.0.1:9000/callback`，必须与注册信息一致；端口 0 可动态分配，但需授权服务支持。凭据默认保存在 `~/.local/share/fast-agent/oauth`，可配置绝对路径 `directory`，但不能位于当前工作区内。

使用私有 CA 的 HTTPS 服务，可在服务配置顶层添加 `"ca_file": "/绝对路径/company-ca.pem"`。该文件必须是最多 1 MiB 的普通 PEM 文件，不能是符号链接；证书添加到默认信任集合，仍校验服务主机名。OAuth 元数据/令牌请求和 MCP 传输共用这项显式信任配置；不要把服务证书错误改成关闭 TLS 校验。启动确认会显示 CA 文件路径。

```text
/mcp-login secured
/mcp-auth-status secured
/mcp-connect
/mcp-logout secured
```

登录需执行模式和交互确认。终端展示授权 URL，由用户在浏览器完成授权；本机回调收到匹配的 state 后交换授权码并保存凭据。登录不自动执行工具。状态仅显示有效期、scope 等脱敏信息。登出关闭现有 MCP 连接并移除工具定义，清除本地凭据；需要时重新 `/mcp-connect`。

`/mcp-revoke secured` 另请求远端撤销。本地删除和远端撤销是两个结果：服务未声明撤销端点或网络失败时，本地仍已删除，不能声称远端成功撤销。仅本地登出无需先完成在线发现。

## 执行链路与代码

1. `oauth_discovery.py` 无凭据读取资源元数据，支持 challenge 和 well-known；按 OAuth/OIDC 顺序发现授权方。资源/issuer 必须匹配，跨来源需批准，拒绝重定向和超过 64 KiB 的响应，不发送 Cookie。
2. `oauth_flow.py` 生成 PKCE S256 与随机 state；事务五分钟有效。授权码只能消费一次，交换表单绑定目标 resource。
3. `oauth_callback.py` 先绑定回环端口再生成授权 URL。校验 Host/path/state，不记录 URL 或授权码；超时、取消、成功后关闭端口。
4. `oauth_tokens.py` 交换/刷新/撤销不自动重试，检查 Bearer、有效期和 scope 不扩张，错误不包含服务原文。
5. `oauth_store.py` 按 resource/issuer/client ID 绑定，要求当前用户拥有的 0700 目录、0600 文件，拒绝链接，原子替换并使用凭据锁。它是文件权限隔离，不是钥匙串加密；当前用户权限的其他进程仍可能读取。
6. `oauth_session.py` 串联上述组件。MCP 每次请求通过令牌提供器检查凭据，到期前 30 秒刷新；连接关闭只使用已有令牌尝试结束远端会话，不刷新。

## 失败如何处理

刷新前移除旧凭据。若服务已经轮换刷新令牌，但响应丢失或新令牌保存失败，旧令牌不会被重复尝试；需要重新登录。这牺牲部分便利性，保留明确的未知状态边界。

错误 Host/state 不消费有效授权事务；用户取消则结束等待。401 或工具响应失败不会自动重放工具。凭据不可用时请求停止，先检查状态，再显式登录。未授权的计划模式不能自动提升权限。

## 验收与限制

已通过受控元数据/令牌 HTTP transport 测试、本机真实回调到令牌交换和保存的控制层测试、请求头更新与静态凭据互斥测试。完整本地 HTTPS 授权/MCP 链路也已通过（临时受信证书，未关闭 TLS）；本次验收不接入外部用户账户；受控服务结果不代表外部用户授权成功。

目前支持预注册公共客户端，要求授权服务明确支持授权码、PKCE S256 和 `none` 客户端认证；不支持动态注册或客户端密钥认证。发现和令牌客户端沿用 HTTP 库的环境代理配置；受控 CONNECT 代理转发已通过下方本地验收；日常回环场景应确保 NO_PROXY 包含 localhost、127.0.0.1。

协议依据：[MCP 2025-11-25 Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)。


## 超时边界不要混淆

授权交互和令牌刷新在 MCP 网络事件循环之外完成。MCP 的总截止时间覆盖真正的 POST、响应和 SSE，不涵盖用户确认时间或前置 OAuth 请求。OAuth 元数据与令牌请求分别使用自身网络超时；回调等待有五分钟上限。不能把这些阶段加起来的耗时宣传成单个 MCP timeout。

本地受保护 HTTP MCP 验证覆盖 initialize、tools/list、tools/call 与关闭：每个普通请求之前获取凭据，初始化通知和关闭使用当前凭据，不再触发授权或刷新。后续 `tests/test_oauth_https.py` 进一步验证完整本地 HTTPS 授权服务链路。

### 附加 CA 文件的读取边界

`ca_file` 是宿主显式配置的信任材料。读取时以禁止末级符号链接、非阻塞方式打开，随后对已打开的描述符检查普通文件类型与1 MiB大小限制，并且实际最多读取1 MiB加1字节。这样文件在检查后增长也不能引起无界读取，替换成管道也不会等待写入者。超过上限直接拒绝；证书仍由SSL解析，保留系统根证书和主机名校验。

# LSP：从文本检索走向符号与诊断

**通信层、Agent 工具与 CLI 配置已接入，真实 clangd 本地验证及 MiniMax 三工具/保存恢复验证通过。** 这不是编辑器插件，也不等同完整 IDE 集成；当前支持范围与权限边界见下文。

## 配置后交给 Agent 查询

创建 `lsp.json`，使用本机已安装语言服务的命令：

```json
{
  "argv": ["clangd", "--background-index=0"],
  "language_id": "cpp",
  "extensions": [".cpp"],
  "timeout": 10
}
```

```sh
fast-agent --workspace /你的项目目录 --lsp lsp.json
```

配置只加载工具，不自动启动进程。可请 Agent“查询 main.cpp 的函数符号，再定位 answer 调用的定义，并检查诊断”。注册的工具是 `lsp_symbols`、`lsp_definition`、`lsp_diagnostics`，都要求 `path`；定义查询另需从 1 开始的 `line` 和 `column`，输入列按 Unicode 字符计数，客户端转换成 UTF-16。返回的服务位置仍是 LSP 零基 UTF-16，不应直接当成编辑工具行列。

每次调用独立启动服务、打开文件、查询并关闭，避免恢复会话时复用旧诊断。代价是项目分析需要重新预热。执行模式每次确认启动；计划模式及未获批准时拒绝，不因名字带“查询”就把启动任意程序当作无副作用读取。

文件限定在当前工作区及配置的扩展名内，确认前后与分析结束后核对正文，变化则拒绝旧结果。语言服务本身可读取其他项目资料，启动沿用 `--sandbox` 设置；这不是读取隔离。定义可能指向外部库，返回 URI 是来源数据，不会自动读取该文件或扩大文件工具权限。

## 为什么搜索之外还需要语言服务

搜索 `answer` 能找到文本，但不能可靠地区分函数定义、调用和同名变量。语言服务分析代码语法与项目配置，可以回答“这个调用指向哪个定义”，也能返回错误位置和说明。

Fast Agent 作为 LSP 客户端，clangd 等程序作为语言服务。模型不直接操作语言服务进程。客户端需要限制消息大小、等待时间和允许的服务端请求，再把结果交给上层工具。

## 一次可运行的流程

本地安装 clangd 后，在项目目录运行：

```sh
python -m pytest tests/test_lsp_transport.py tests/test_lsp_tools.py -q
```

测试找不到 clangd 时会跳过真实语言服务部分，跳过不能算真实验收。其他边界测试仍运行。

真实测试使用临时 C++ 文件，依次完成：

1. 启动独立进程，发送 `initialize`，声明 UTF-16 位置编码。
2. 发送 `initialized` 和 `textDocument/didOpen`，带上文件 URI、正文和版本号。
3. 请求 `textDocument/documentSymbol`，获取函数符号；请求 `textDocument/definition`，核对调用的定义位置。
4. 对包含未定义名称的文件等待 `textDocument/publishDiagnostics`，核对当前版本的错误。
5. 关闭进程与管道，检查进程确实退出。

源码：[lsp_transport.py](../../src/fast_agent/lsp_transport.py)。它复用 stdio 进程管理，但使用 LSP 的 `Content-Length` 帧，不能把 MCP 的逐行 JSON 协议直接套过来。

## 为什么诊断必须关联版本

文件更新为版本 2 时，服务可能仍在发送版本 1 的诊断。把旧诊断当成当前错误会误导下一次编辑。`wait_diagnostics(uri, version)` 只接受 URI 与版本匹配的通知；无版本或旧版本不能证明当前文件已完成检查。等待超时也不等于“没有错误”。

目前该接口要求服务发送诊断版本。后续接入其他语言服务时，必须处理其能力差异，不能偷偷放宽版本检查。

## 通信边界

单帧正文最多 1 MiB，头部最多 8 KiB；一次请求或诊断等待累计输出最多 2 MiB、最多 100 条消息，并受截止时间限制。标准错误输出也计入总量，但不会当成协议消息。

服务端请求返回不支持；即使服务请求修改文件，客户端也不会执行。正常结束先发送 `shutdown`，收到空结果后发送 `exit`，短暂等待服务退出；协议等待与退出等待分别最多半秒。无响应、错误或超时仍清理进程组与管道，不能为了优雅关闭而无限等待。

源码入口：[lsp_tools.py](../../src/fast_agent/lsp_tools.py)负责配置、授权、文件版本与位置转换；[cli.py](../../src/fast_agent/cli.py)负责显式注册。结果是语言服务提供的数据，不是可信指令，也不能代替编译和测试。

## 真实模型验收

本地 clangd 测试证明语言服务能工作，不能证明模型实际会调用工具。已有模型环境变量后运行：

```sh
python examples/real_lsp_demo.py
```

脚本只在临时目录创建 C++ 样例，注册三个 LSP 工具，授权仅允许该样例的语言服务启动。独立检查函数名称、定义位置、当前版本错误诊断、源文件不变，以及保存恢复后的计划模式和消息一致性。通过与否取决于工具记录与磁盘事实，而非模型总结。它会消耗真实模型请求；输出用量中的未知值应保留。

此前的脚本序列化、系统消息比较和临时目录别名问题均保留失败记录，没有覆盖为成功。该次通过证明的是这套临时 C++ 场景，不代表所有语言服务都兼容。

协议反例测试已覆盖超大帧、重复长度头、不匹配的请求 ID、无效诊断参数，以及服务端 `workspace/applyEdit` 请求。后者收到“不支持”响应，测试核对本地文件未被修改。测试使用真实子进程管道，异常后检查进程退出，而不仅是模拟一个错误返回值。

## docs/tutorial/52-engineering-evals.md

# 工程评测：用独立断言核对 Agent

Agent 的总结可以很流畅，但评测要回答的是：它是否实际读取了文件，修改是否满足任务要求，有没有改动不该动的内容？

## 先固定任务，再运行模型

`examples/engineering_eval.py` 当前定义 `engineering-v2`，含两个临时工作区任务：

| 任务 | 目标 | 独立判定 |
| --- | --- | --- |
| locate | 找到并读取有缺陷的加法函数 | 实际搜索和读取工具成功，源文件不变 |
| repair | 修复加法函数，保留签名 | 实际读写工具成功；宿主 AST 检查参数相加与函数形状 |

每个任务有独立模型客户端、最多 8 次请求、最多 8 轮。只注册任务需要的检索/文件工具，确认仅允许修改临时目录内的 `maths.py`；不会自动运行模型生成的 Python。断言在宿主脚本里，不允许模型改写。

这套微型任务集用于反复回归，不代表大型仓库基准。修复判定目前限定代码形状：只接受指定签名、单个返回语句及 `a + b`。其他等价实现可能不通过，这是版本化任务约定，而不是通用语义证明。复杂修复仍需独立测试套件与隔离执行。

## 运行与比较

已有模型环境变量后，在项目目录运行：

```sh
python examples/engineering_eval.py > engineering-report.json
```

这会真实调用模型并产生费用。报告包括任务集版本、模型名、时间、每项断言、耗时、请求和 token 用量。改变提示词或判定规则时应更新任务集版本，不把不同规则的分数直接比较。

源码：[evaluation.py](../../src/fast_agent/evaluation.py)、[engineering_eval.py](../../examples/engineering_eval.py)。

2026-10-20，MiniMax-M3 的 `engineering-v1` 运行通过 2/2 个任务、10 项独立断言，6 次请求、8156 个服务报告 token、未知用量请求数 0。报告为 `.fast-agent/validation/engineering-v1.json`，费用仍为 `null`。这是一次运行证据，不代表多次重复运行的稳定成功率。

v2 将修复断言收紧为整棵 AST 与指定加法函数一致，忽略位置、空白和注释，但拒绝装饰器、默认参数、额外参数、注解及额外语句。v1 只检查局部形状，可能漏掉这些额外行为；因此不能把 v1 的通过记录直接当作 v2 的通过。测试覆盖这些反例，且判定期间不执行待测源码。

同日 v2 独立重跑通过 2/2 个任务、9 项断言；7 次请求、9892 个报告 token、未知用量请求数 0。证据为 `.fast-agent/validation/engineering-v2.json`。断言数量减少源于完整 AST 判定替换多个局部判定，不是放宽通过标准。

## 怎样算通过

模型循环完成，并且全部非空布尔断言为真，任务才通过。空断言、字符串 `"true"`、运行异常都不能算成功。单个任务异常不阻止后续任务；记录异常类型，不保存可能带凭据的异常正文。

任务出错时，真实任务 runner 会在关闭客户端前通过 `EvaluationFailure` 保留已有用量；仍无法取得完整用量时，总用量为 `null`，不把缺失任务算作零。服务未报告 token 时保留 `unknown_requests`。当前没有可核验价格配置，费用固定为 `null`，不会凭空估价。

## 当前边界

此汇总器运行受信任的本地任务函数，不加载模型生成的评测插件，也不提供恶意任务的执行沙箱。没有外部强制总超时；真实模型仍受自身请求超时与预算约束。后续扩充任务集、超时与质量边界后再做整体验收，不能用这两个场景宣称全面工程能力。

## 把失败与会话恢复纳入评测

只测一次成功修复容易遗漏状态恢复问题。`engineering-recovery-v1` 增加一个独立任务：先读取不存在的 `answer.txt`，要求模型如实停止；保存这段包含失败工具结果的会话，再由宿主在临时工作区补齐文件。创建新的 Agent 并从磁盘加载历史后，只提示它继续原目标。

```sh
python examples/engineering_recovery_eval.py
```

随机代号只写入文件，不出现在第二轮提示中。宿主检查实际失败读取、实际成功读取结果中的代号、恢复历史一致、恢复后计划模式、文件未变和没有额外文件。模型说“已恢复”不能代替工具事件。全程只注册 `read_file`，不授予写权限，最多8次模型请求，每轮最多4步，失败仍保留用量报告。

这里模拟的是外部修复缺失文件后的恢复；不是 Agent 自行修复环境，也不是进程崩溃恢复。新 Agent 复用同一个模型客户端以共享请求预算，恢复数据实际经过 SessionStore 落盘与加载。进程级保存恢复另见会话章节。错误与成功同时进入同一评测，使“正确报告失败”和“恢复后真正读取”都成为可核对行为。

2026-10-23 MiniMax-M3 实际验收通过7项断言，4次请求、4639个报告token，用量未知请求为0；报告为 `.fast-agent/validation/engineering-recovery-v1-retry.json`。首轮未产生工具调用的失败报告 `engineering-recovery-v1.json` 保留，不计为通过。此入口关闭自动模型重试，避免环境失败时扩大请求量。
