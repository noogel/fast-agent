FAST AGENT / 任务执行与权限

持久任务计划与版本冲突

聊天里写出的计划容易被长对话压缩，也可能在恢复时与磁盘状态脱节。本章把计划作为独立的工作区记录保存，让模型显式查询，而不是依赖历史文本猜测。

读写协议

三个模型工具分别负责查询、列举和更新：

  • get_plan {"name":"repair"}：读取最新计划，不存在时返回 revision: 0。
  • list_plans {}：返回名称、标题、版本和步骤状态摘要。
  • update_plan：提交完整计划和刚读取的 expected_revision，经用户确认后保存。
{
  "name": "repair",
  "expected_revision": 0,
  "title": "修复计算错误",
  "steps": [
    {"id": "read", "title": "读取源码", "status": "in_progress", "note": ""},
    {"id": "test", "title": "运行测试", "status": "pending", "note": ""}
  ]
}

计划名称和步骤编号使用字母、数字、下划线或短横线，最长 64 字符。标题最长 200 字符，说明最长 2000 字符。每个计划有 1～50 个步骤，状态可选 pending、in_progress、completed、blocked，最多一个 in_progress。

旧计划不能覆盖新计划

task_plans.py 通过私有 JSON、原子替换和进程锁保存计划。新计划从版本 1 开始，每次更新增加版本。提交版本与磁盘版本不一致时，工具失败，要求重新读取；确认期间记录发生任何变化，也拒绝覆盖。

这避免两个进程拿着同一份旧计划先后覆盖。版本号不提供分支合并功能；模型需读取新状态后重新组织更新。

计划更新仍是写操作，遵循原权限策略。计划模式、启动只读模式和未核实结果都会阻止更新；计划模式可以查询已有计划，切换执行后才能确认保存。这保留了本项目“计划模式不写入”的约定，没有把元数据写入伪装成只读工具。

保存恢复后的行为

/plans
/show-plan repair
/save work
/load work

计划保存在 .fast-agent/plans，消息保存在 .fast-agent/sessions。加载旧会话不会回滚新计划，/reset 和上下文压缩也不会删除计划。恢复后应调用 get_plan 读取当前版本，再读取文件核对现状。

计划属于工作区，不随会话文件自动迁移到另一台机器。计划不会自动注入每次模型请求，只有显式查询返回工具结果，避免所有历史计划占用上下文。

completed 只表示模型或用户记录的状态，不是测试通过证明。完成说明应引用真实执行结果；后续质量检查功能会单独保存命令和退出码。

验证

测试覆盖创建后重新读取、版本递增、旧版本拒绝、确认期间外部变更、权限拒绝和字段约束。真实示例 real_task_plan_demo.py 使用 MiniMax 建立修复计划，读取文件、修复并测试，再更新完成状态；创建新模型实例加载会话后重新查询同一计划、重跑测试，检查计划没有被旧会话覆盖。

示例中 MiniMax-M3 真实验证 10 项检查全部通过，持久计划从版本 1 更新到版本 2，恢复后内容保持一致并再次运行测试。默认本地回归 296 项通过、2 项原生沙箱测试按开关跳过；严格文档构建通过，独立审查未发现阻止交付的问题。
