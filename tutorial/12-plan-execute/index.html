    计划模式与执行模式

    工程任务可以先理解代码、列出方案，再执行修改。这里把“当前交互模式”和“启动权限”分开：模式决定模型现在能做什么，启动权限决定执行阶段最多允许什么。

    亲自操作

    source .env
fast-agent --workspace /你的仓库 --plan

    依次输入：

    分析这个问题，只读代码，给出修改文件、步骤和验证命令
/save repair-plan
/execute
按刚才的计划实施，先复现问题，再修复并验证
/plan
检查最终差异并总结

    /execute 只切换状态，不请求模型，也不立即执行计划。下一条自然语言输入才启动新一轮 Agent 循环。计划是普通历史消息，不是可直接运行的脚本，也不是已经批准的补丁；实际修改仍展示差异并按现有权限确认。

    两层约束如何配合

    启动权限 计划模式 切换执行后
    confirm 仅只读工具 修改和命令继续逐次确认
    restricted 仅只读工具 恢复原来的精确 argv 命令白名单及修改确认
    read-only 仅只读工具 /execute 拒绝提升权限

    workspace.system_prompt 告诉模型当前模式，要求计划用中文说明目标、依据、涉及文件、步骤、验证方式和待确认问题。没有运行测试时必须说明只是推断。

    提示词不是权限保障。Agent.tool_schemas() 在计划模式只发送 effect='read' 的工具定义；ToolRegistry.execute() 又在执行前检查真实工具的 effect。即使模型虚构写入调用，宿主也会拒绝。ToolContext.authorize() 同样检查当前模式，保护需要授权的内置处理函数。自定义工具默认按写操作处理，只有确实只读的工具才应标记为 read；插件实现仍属于可信宿主代码。

    模型没有 /execute 工具。终端命令由 session_commands 在本地处理，历史消息中的“已经同意执行”不会改变权限。

    切换和恢复为什么要重新读取

    Agent.set_mode() 更新 system 消息，并清空文件与规则的读取指纹。切换执行后，模型必须重新读取目标文件和沿途 AGENTS.md，之后才能编辑；计划阶段读过的版本不能直接作为修改依据。现有外部修改检查和差异确认继续生效。

    /load、/resume、--resume 都重新生成当前工作目录的系统消息并进入计划模式，即使保存的是执行中的历史也如此。恢复不重放旧工具。/reset 和 /trim 不会退出计划模式，/execute 也不会解除“操作结果未知”的阻止；未知结果仍要人工检查并通过原有处理命令记录结论。

    Python 宿主应使用恢复 API，而不是直接赋值 history：

    agent = Agent(model, registry, context, plan=True)
agent.restore_history(store.load('repair-plan'))  # 校验并进入计划模式
agent.set_mode('execute')  # 可信宿主明确发起；不能交给模型调用
result = agent.run('重新读取文件，然后实施计划')

    一次性 --resume ID --prompt '检查进度' 只会进行计划模式分析。需要执行修改时进入交互终端后输入 /execute。

    “只读”的准确范围

    计划模式约束模型对项目的操作。会话和检查点仍可写入 .fast-agent/，已有后台任务也不会自动暂停。本地 /cancel ID 是用户明确发起的控制，仍可取消后台任务；模型的 cancel_command 工具在计划模式不可用。该机制没有提供操作系统沙箱，也不能约束其他进程或不可信的自定义 Python 代码。

    用 MiniMax 验证完整链路

    source .env
.venv/bin/python examples/real_plan_demo.py

    演示创建临时 Git 仓库和两个失败测试。第一个独立进程让真实模型只读规划，并保存会话与检查点；父进程核对源文件、测试、规则文件的哈希与 Git 状态，并确认规划时没有授权回调。

    第二个进程分别恢复会话和检查点，核对两次都进入计划模式，再通过本地 /execute 明确切换。模型重新读代码、运行失败测试、修改加法实现、重跑测试并检查 Git 差异。宿主仅允许目标源文件和精确测试命令，最后独立验证两个测试通过、测试文件未修改、差异仅涉及目标源文件。

    结果写入 .fast-agent/validation/plan-demo.json，过程事件写在运行输出中。真实模型验收检查正常工作链路；伪造写入调用、只读权限不能提升、恢复不继承授权等拒绝路径由 tests/test_plan_mode.py 的确定性测试覆盖。

    示例中 MiniMax-M3 实测：规划阶段 3 次模型调用、6 次只读工具调用；执行阶段 4 次模型调用、7 次工具调用。规划阶段 Git 状态及文件哈希不变，两种恢复入口均返回 plan，测试从 2 个失败变为全部通过，最终仅修改 src/math_utils.py。两阶段均观察到流式文本事件，完整流程约 137 秒。这是一次临时仓库验收，不代表任意复杂仓库的成功率。
