FAST AGENT / 代码检索、编辑与验证

多文件修改批次与安全恢复

重构经常需要一起修改多个文件。逐次编辑会让用户难以看清整体变化；把所有内容放到一个工具请求里，也不会让文件系统自动拥有跨文件事务。本章提供整体预检、整体审批和可检查的恢复记录。

模型如何调用

先 read_file 读取全部目标及其规则，然后调用：

{
  "files": [
    {"path": "add.py", "old": "return a-b", "new": "return a+b"},
    {"path": "multiply.py", "old": "return a+b", "new": "return a*b"}
  ]
}

工具名为 edit_files。每个已有文件执行一次非空且唯一的精确替换；路径不能重复，最多 20 个文件。复杂单文件多处替换仍可使用 multi_edit_file。这一版不在批次中创建、删除文件或目录。

所有目标先验证读取指纹、AGENTS.md、匹配唯一性和大小。整体差异不超过 64 KiB，每个文件不超过 1 MiB，前后快照总计不超过 8 MiB。任何预检失败都不会写入任何目标。审批展示整批差异，审批后再次检查整批文件，再逐文件原子替换。普通文件先写，AGENTS.md 按目录由深到浅最后写；恢复也使用这一顺序，防止批次自身修改规则导致后续文件校验失败。

为什么还需要批次记录

操作系统没有为这些独立文件提供全局原子替换：第一个文件成功后，第二个可能遇到磁盘错误。不能把这类情况说成“全部没发生”，也不应该悄悄重试。

edit_batches.py 在第一次写入前保存 .fast-agent/batches 记录，包括每个文件修改前后的完整文本和状态：

状态 含义
pending 修改可能尚未开始或只完成一部分，需要核实
completed 整批写入与完成记录均成功
undoing 恢复可能进行到一半，需要核实
undone 整批恢复完成

pending、undoing 会阻止新任务写入。任务检查点中的未知工具结果仍保持原有保护；批次记录不会自动消除它。

用户显式恢复

/batches
/undo-batch 批次编号

撤销命令不开放为模型工具。用户可以先核对 /tasks、/batches 和磁盘内容；若任务检查点也标记未知结果，先按已有 /resolve 任务编号 核实说明 流程处理，然后恢复批次。

恢复持有工作区任务锁，逐个校验所有文件必须与批次的修改前或修改后快照完全相同。遇到任何不同内容、缺失文件、无效路径或规则读取失败，拒绝整批恢复，不覆盖外部修改。校验通过后展示整体恢复差异，再确认并执行。恢复本身也可能中断，此时保留 undoing；再次显式恢复仍会重新检查整批内容。

只排除正在恢复的自身批次阻塞，其它未核实任务、后台任务、其它中断批次、计划模式和启动只读权限仍阻止写入。会话历史不会随文件撤销而改写，继续任务前应重新读取磁盘。

文件快照属于本机运行数据，不提交 Git，也不自动发送给模型；list_edit_batches 只返回编号、路径和状态。它们不是版本控制或长期备份，仍应使用 Git 保存正式工作。

验证流程

测试覆盖完整审批/恢复、预检失败不写入、审批期间变化、部分写入故障、外部冲突拒绝恢复、中断批次阻塞与恢复。真实示例 real_edit_batches_demo.py 用 MiniMax 修复两个文件并执行测试，保存加载历史后人工撤销，核对原始文件完全恢复及测试重新失败，再让模型重新读取、修复并运行测试。测试文件始终保持不变。

示例中 MiniMax-M3 完整验证 11 项检查全部通过；规则文件依赖顺序由故障复现测试和独立代码审查覆盖。
