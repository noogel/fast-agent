FAST AGENT / 会话与上下文

自动压缩上下文与流式交互

Agent 的历史随着工具执行增长，等待完整回复也会让终端显得没有反应。本章分别解决历史体积和输出延迟，核心循环仍然是“请求模型 → 执行完整工具调用 → 回传结果”。

开始使用

source .env
.venv/bin/fast-agent --workspace /你的仓库 --max-steps 20

真实模型默认流式输出；模拟模型没有流式接口时自动回退普通输出。自动压缩默认阈值为 60000 个请求 JSON 字符，保留最近 2 轮原始对话。这不是模型的精确 token 数或服务端上下文上限。

# 更早触发压缩，并保留最近一轮（包括当前用户任务）
.venv/bin/fast-agent --context-chars 20000 --keep-rounds 1
# 关闭流式输出
.venv/bin/fast-agent --no-stream
# 关闭自动压缩，仍可使用 /trim
.venv/bin/fast-agent --context-chars 0

自动压缩发生在哪里

agent.py 在每次任务模型调用前检查消息和工具定义的序列化字符数。超过预算时调用 compaction.py：

  1. 按 user 消息划分轮次，保留最近 N 轮的所有消息，工具请求和结果不拆开。
  2. 把更早的消息作为数据交给同一个真实模型，要求总结目标、约束、路径、关键数值、已完成验证和未完成事项。摘要调用不提供工具。
  3. 检查摘要有内容、没有工具请求、长度合适，而且替换后确实缩小并满足预算。
  4. 将原始完整会话备份到 .fast-agent/sessions/auto-<随机编号>.json。
  5. 备份成功后才替换内存历史，显示压缩前后字符数和备份路径。

摘要以一组明确标注的 user/assistant 历史记录放在 system 之后。它不替换当前的系统规则；重复压缩时旧摘要一起参与重新整理，不无限堆叠。最近原始轮次仍按协议原样保留。/history 可以查看摘要，/save 和 /load 继续使用原有格式，不需要新会话格式。

摘要是有损信息整理，不保证逐字保留所有细节。需要找回原始事实时可用 /load auto-编号 恢复备份（加载不重放工具）；也可提高预算或关闭自动压缩。摘要可能遗漏信息，因此关键修改仍要重新读文件并验证结果。

为什么有时会停止而不是强行压缩

摘要调用失败、超长、请求工具、无效或备份失败时，当前轮次明确报错，原历史不被覆盖。不会无上限重试，也不会默默删除对话。

待摘要输入最多 100000 字符，摘要最多为预算的四分之一且不超过 8000 字符。如果最近保留轮次、系统规则或工具定义本身已经很大，仍可能无法满足预算；单个正在执行的轮次不会从中间拆开。这时需要更小的文件读取范围、提高预算、调整 --keep-rounds 或手动 /trim。

自动摘要会额外调用一次模型，增加耗时和费用；它不计入任务模型循环的 max-steps。每次任务模型调用前至多尝试一次压缩，失败会停止本轮。字符预算用于可理解的教学策略，不是对任意模型上下文大小的保证。

流式输出如何工作

providers.py 的 complete_stream 给 Chat Completions 请求增加 stream=True。SDK 返回增量事件，交给 streaming.py 处理。

文本片段通过 text_delta 事件立即交给终端显示。一段可能是几个字或标点，不等于一个 token。最终回答不再重复打印。程序仅处理 content 文本字段；供应商把额外标签混入 content 时，它们也可能显示。

工具调用参数也可能分多段到达，例如：

片段 1：index=0，id=call_A，name=read_file，arguments={"pa
片段 2：index=0，arguments=th":"note.txt"}
结束标记：finish_reason=tool_calls

程序按照 index 合并 id、名称和 arguments，等到正常完成标记，再校验调用 ID 和 JSON 参数。只有这些检查通过后，Agent 才执行工具。

连接中断、缺少结束标记、length/content_filter、无效参数等情况都会拒绝执行本次回复中的工具。已显示的部分文本可能不完整，终端会同时显示失败信息；不把半截回复加入历史。已经完成的前几次工具操作不会回滚。

Ctrl+C 会关闭当前流；如果发生在工具执行阶段，仍按原有机制补齐中断结果，保留可继续使用的消息结构。流式回复总量最多 1 MiB、最多 128 个工具调用，避免无界累积。

一次完整的真实模型验证

source .env
.venv/bin/python examples/real_context_stream_demo.py

演示使用三个独立进程：

  1. 第一进程告诉模型一个随机目标标题及较长背景，保存会话。
  2. 第二进程加载历史，不直接获得随机标题；较低预算触发真实模型摘要，随后以流式工具调用读取、修改、复读 note.txt，并保存压缩后的会话。
  3. 第三进程加载压缩后的会话，要求只回答之前的标题，验证跨进程保留了关键信息。

父进程检查磁盘内容、工具顺序、多个真实文本增量、摘要事件、原始备份、不同 PID 和恢复后的标题。临时目录随后清理，报告留在 .fast-agent/validation/context-stream-demo.json。

这验证的是一次可重复的小型端到端场景，不代表摘要对所有长任务都无损。大型仓库仍应结合分段读取、测试和差异审查。

真实模型验证

MiniMax-M3 在三个独立进程中完成验证，总耗时 56.55 秒。请求字符数由 19475 降到 3722，备份原始会话 1 份；压缩后执行 read_file → edit_file → read_file，磁盘随机标题正确且正文未变。第三个进程恢复压缩后的会话，准确回答同一个随机标题。

三个阶段分别收到 40、111、12 个真实 content 增量，共 163 个；任务模型调用共 6 次，另有 1 次摘要调用。临时文件已清理，JSON 报告保留在项目 Git 忽略目录。自动化测试共 111 项通过，包含缺少结束标记、断流、截断、参数无效、摘要失败、重复压缩和 CLI 不重复输出。

后续 单次长任务的上下文压缩 扩展了单次任务内部的压缩：在完整工具批次边界摘要较早结果，保留当前用户要求和最近一批原始证据。
