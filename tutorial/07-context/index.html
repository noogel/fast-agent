FAST AGENT / 会话与上下文

保存、恢复与裁剪上下文

模型每次收到的请求都包含消息历史。本章先讲解 Python API 的内存历史和手动会话保存；当前 CLI 还会自动保存任务检查点，关闭终端后可恢复，详见任务恢复、后台命令与权限。会话保存把消息写到磁盘；恢复把它们重新加载到新的 Agent。这里没有训练模型，也没有自动重放工具。

亲自操作

fast-agent --mock --workspace /你的练习目录

依次输入：

你好
/history
/context
/save first
/reset
/load first
/context
/trim 0
/exit

文件保存在工作目录的 .fast-agent/sessions/first.json。只保存版本、工作目录和消息，不保存 API 配置或密钥。消息本身可能包含用户输入和代码，因此文件权限为 600，本项目的该目录已加入 Git 忽略（在其他仓库使用时也应忽略 .fast-agent/）；不要把敏感内容随意发给模型或分享会话文件。

恢复后默认进入计划模式，历史中的执行同意不会成为当前授权。需要修改时在终端输入 /execute；启动权限为 read-only 时不能提升。详见 第十二章。

为什么不能直接删除前 N 条消息

一轮 user 消息后可能有多个 assistant 工具调用与 tool 结果。只保留最后几条可能让结果失去对应调用 ID，导致下次模型请求失败。

sessions.py 的 trim_history 按 user 开始的一整组消息裁剪，保留开头的 system 消息。/trim 2 保留最近两组，包括组内所有工具请求及结果；/trim 0 只保留系统消息。中断或请求失败的轮次可能尚未获得最终回复，但只要工具结果配对完整，也允许保存和恢复。

/context 分别显示轮数和完整回复轮数。JSON 字符数是可理解的粗略体积指标，不是模型 tokenizer 的精确 token 数，也没有计入工具定义。现在也支持自动摘要，详见 第九章。手动裁剪会遗忘早期目标；重要需求应重新告诉模型。文件中的既有保存不会随内存裁剪自动改变，需要再次 /save。

保存与恢复的正确性

保存先写同目录临时文件，flush 和 fsync 后再原子替换，写入失败不会破坏原会话。加载检查版本、工作目录、字段类型和每个工具调用的配对；所有检查通过才替换当前 history。工作目录不同则拒绝，防止恢复后把工具用于另一个项目。

同名 /save 会原子覆盖原会话。会话目录和文件拒绝符号链接；这仍不是抵御恶意并发文件系统修改的完整沙箱。

用真实模型验证跨进程恢复

配置好真实模型后，在项目根运行：

source .env
.venv/bin/python examples/real_session_demo.py

父进程生成一个随机目标标题。第一个独立进程把标题告诉模型，只读取 note.txt，然后保存会话并退出。第二个独立进程只收到工作目录，不收到目标标题；它通过 restore_history 加载历史进入计划模式，再由演示宿主显式 set_mode("execute")，重新读取文件建立当前修改指纹，再继续上一轮任务，编辑并复读文件。确认回调仅批准临时 note.txt 的修改。最后父进程核对随机标题、正文与工具顺序。

这个演示复用真正的 SessionStore、Agent 和模型接口；完成后清理临时文件。它同时证明：消息跨进程持久化、上下文恢复、工具调用 ID 的序列结构有效，以及恢复后的真实修改结果正确。
