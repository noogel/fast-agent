    模型请求的超时、重试与执行边界

    真实模型请求会遇到连接失败、限流和服务端临时故障。工程化 Agent 需要有界恢复，同时保证恢复网络请求时不会重新执行已经完成的文件修改或命令。本章在模型适配层实现这条边界。

    配置与默认值

    配置从当前进程环境读取，不扫描其他项目的凭据，也不自动加载 .env。

    export FAST_AGENT_CONNECT_TIMEOUT=10
export FAST_AGENT_READ_TIMEOUT=60
export FAST_AGENT_MAX_RETRIES=2
fast-agent --workspace /你的仓库
    变量 默认值 允许范围 含义
    FAST_AGENT_CONNECT_TIMEOUT 10 秒 大于 0，最多 120 秒 连接超时，也用于写入和连接池等待
    FAST_AGENT_READ_TIMEOUT 60 秒 大于 0，最多 600 秒 等待响应数据的读取超时
    FAST_AGENT_MAX_RETRIES 2 0～5 的整数 初次请求之外的重试次数；0 表示禁用

    读取超时不是整个任务的总时长限制。流式响应持续收到数据时，可以运行超过这个时长；--max-steps 仍限制 Agent 的决策步数。配置为 2 次重试意味着一次决策最多发出 3 次 HTTP 请求。非有限数、负数、零超时和超限配置会在启动时被拒绝。

    Python API 也可以使用 Config(..., connect_timeout=10, read_timeout=90, max_retries=1)。正常构造模型时会把这些值传给 SDK；若显式注入已有 SDK client，则连接参数由该 client 的创建者负责。

    哪些情况可以重试

    request_policy.py 只接受明确的临时故障：

    • SDK 连接失败、超时，以及流读取过程中尚未收到任何片段时的网络/远端协议传输异常。
    • HTTP 429、500、502、503、504。

    401/403、请求参数错误、其他 HTTP 状态、工具参数不合法、模型回复缺少结束标记等情况不自动重试。程序异常也不会因为碰巧有一个 status_code 字段就被当成网络故障。

    默认按约 1、2、4、8、16 秒指数退避，并加入 0.8～1.2 倍随机抖动；单次等待不超过 30 秒。有效的 Retry-After 秒数或 HTTP 日期优先；服务要求等待超过 30 秒时直接结束本次请求，不提前请求。无效头部回退到有界退避。

    终端会显示：

    [重试] 请求受限，请检查配额或稍后重试。 等待 2.0 秒，准备第 2/3 次请求

    日志只包含本地生成的中文原因、次数和等待时间，不展示供应商原始错误、请求头或密钥。重试用尽时说明实际尝试次数。等待期间 Ctrl+C 可以中断。

    SDK 自带重试被设为 0，由 Fast Agent 统一管理；否则两层重试可能相乘，次数和等待就难以理解。

    流式回复一旦开始，就不能悄悄重来

    假设屏幕已经显示“正在修改”，随后连接断开。重新生成可能输出另一段文本，甚至提出不同的工具参数。因此采用保守边界：收到任何流式片段后，停止自动重试。

    “任何片段”包括文本、工具参数、角色、推理或用量片段，即使它尚未显示给用户。这也意味着某些看似没有文字的请求仍然不能自动重试。失败提示会说明已收到响应内容，当前响应中的工具没有执行。

    只有完整、正常结束并通过校验的工具调用才会交给 Agent。失败流会关闭，部分文本不会作为完整 assistant 消息加入历史，部分工具调用不会执行。用户可检查状态后发起新的任务；程序不会拼接两次生成的工具参数。

    为什么重试不会重放工具

    看 agent.py 和 providers.py 的分工：

    Agent 请求模型
    ↓
模型适配器尝试 HTTP 请求，必要时重试同一份 messages/tools
    ↓
收到完整 ModelReply
    ↓
Agent 执行工具一次，保存 tool_call_id 对应结果和检查点
    ↓
下一次模型请求把工具结果一并发送

    重试循环包围的是 chat.completions.create 和响应读取，不包围 Agent.run，也不调用 ToolRegistry.execute。如果工具已完成、下一次模型请求遇到 503，重发的是包含既有工具结果的消息，之前的工具不会再次执行。

    重试模型请求仍可能重复产生服务端生成费用，因为客户端超时不能证明服务端没有处理请求。这里保证宿主程序不因重试而重放工具，不承诺模型服务端恰好处理一次，也不能阻止模型在后续完整回复中主动提出新的重复操作。

    自动上下文摘要同样使用这个模型适配器，因此也遵循超时和重试策略。摘要失败时仍保留原历史；成功后的原始会话备份机制不变。

    如何验证

    离线故障注入与真实服务验证分开完成：

    python -m pytest -q
source .env
python examples/real_repository_demo.py
python examples/real_context_stream_demo.py

    自动测试使用真实 SDK 的内存 HTTP 传输，模拟首次 503、第二次正常 SSE，检查请求内容一致且文字只输出一次。其他用例覆盖认证拒绝、重试耗尽、连接失败、Retry-After、等待中断、流式片段后的失败，以及工具副作用只发生一次。

    MiniMax 验证器不伪造服务故障。仓库验证器让模型检索代码、复现失败测试、修改源码、重跑测试和检查 Git 差异。上下文验证器跨三个进程完成记忆、自动摘要、流式工具调用和保存后的恢复，并核对随机目标标题。报告记录实际超时配置和 model_retry 事件；没有事件就表示该次真实运行未发生自动重试，不能用故障注入结果冒充真实服务行为。

    报告位于 Git 忽略的 .fast-agent/validation/。每次启动这两个验证器会移除上一份同名报告，避免一次失败留下旧的成功结果。原始运行日志仍可单独保存。
