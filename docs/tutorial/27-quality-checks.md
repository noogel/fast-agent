# 配置质量检查与执行证据

任务计划里的“完成”不是测试证据。质量检查把用户选定的命令与实际退出码保存在独立记录中，便于恢复会话后复核。

## 显式加载配置

创建 `checks.json`：

```json
{
  "tests": {"argv": ["python", "-B", "-m", "unittest", "-v"], "timeout": 30},
  "diff": {"argv": ["git", "diff", "--check"], "timeout": 10}
}
```

```bash
fast-agent --workspace . --checks checks.json
```

加载配置不会运行命令，也不代表已授权执行。配置在启动时读取一次；模型修改磁盘配置不会改变当前进程已加载的命令。配置最多 64 KiB、32 个检查，每条 argv 最多 128 个参数、每个参数最多 4000 字符；超时大于 0 且不超过 60 秒。没有 shell 字段，不通过 shell 解释命令。

## 工具调用过程

1. `list_checks` 查询已加载的名称、argv 和超时。
2. `run_checks {"names":["tests","diff"]}` 按顺序执行指定检查。
3. 每项复用 `run_command` 的审批、权限、沙箱、流式输出和长日志保存。
4. 首个失败停止，未运行的检查不会被计为成功。全部指定检查成功才返回 `ok: true` 和 `status: passed`。

工具参数只有名称，不能注入另一条 argv 或改变超时。使用 restricted 精确命令白名单时，仍按实际 argv 检查授权；只读/计划模式不能运行检查。

## 持久证据

[quality_checks.py](../../src/fast_agent/quality_checks.py) 在执行前保存 `running` 记录，每项结束后保存名称、实际 argv、耗时和完整的有界工具结果；最终保存 `passed` 或 `failed`。命令输出预览之外的长日志仍通过原有日志工具按需读取。

```text
/check-runs
/check-run 运行编号
```

模型可使用 `get_check_run` 查询记录。记录位于 `.fast-agent/checks`，包含工作区、沙箱模式和执行时间。可捕获异常保存 `unknown`，Ctrl+C 保存 `interrupted` 后继续向上传递中断，不伪造退出码；进程被强杀或存储失败仍可能留下 `running`，不能当成通过；未知命令结果继续沿用任务检查点的人工核实流程，不自动重跑。

这些记录只证明当时的执行结果，不证明当前代码、外部服务或依赖仍保持不变。它不是签名审计账本，也不是强制约束模型最终措辞的门禁。代码再次修改或恢复后应重跑检查，不能仅复述历史 `passed`。测试范围也由配置决定，不能把单元测试通过说成全部质量已验证。

## 验证

本地测试覆盖真实子进程通过、非零退出、审批拒绝、未知/重复名称拒绝、非法配置和结果重新读取。真实示例 [real_quality_checks_demo.py](../../examples/real_quality_checks_demo.py) 使用 MiniMax 先执行配置检查复现失败，再修复源码并重跑通过；保存加载会话后再次运行检查，确认旧记录保留、新运行独立记录、测试文件未改变。

示例中 MiniMax-M3 完整验证 10 项检查通过，保留了失败、修复后通过、恢复后再次通过的三次独立记录。启动异常和用户中断的终态记录由故障注入测试及独立审查验证。
