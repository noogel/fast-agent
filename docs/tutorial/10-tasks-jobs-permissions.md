# 任务恢复、后台命令与权限

这一章把 Agent 循环扩展成可以中断、检查和继续的本地工作流程。模型负责提出下一步，宿主程序负责保存证据、执行权限和进程生命周期。

## 从会话到任务检查点

`/save` 保存的是会话。任务检查点额外记录本轮状态、操作结果是否确定，以及权限决策。CLI 默认启用，每次输入任务会显示一个 ID，并将检查点原子写入 `.fast-agent/tasks/`。Python API 通过 `Agent(..., checkpoints=True)` 开启。

一次调用的顺序是：

1. 将用户消息保存，然后请求模型。
2. 收到完整的工具调用，执行前保存检查点。
3. 执行工具，将带 `tool_call_id` 的结果追加到历史。
4. 再次保存，然后请求模型决定下一步。

磁盘快照始终是一组完整配对的消息：尚未执行的调用使用“未执行”结果占位，正在执行的修改使用“结果未知”占位。内存中的正常执行历史使用实际结果。这样即使进程直接退出，恢复后的消息仍符合模型协议。

```text
/tasks
/resume <任务ID>
/execute
继续检查结果并完成任务
```

也可以重新启动：

```bash
fast-agent --workspace /你的仓库 --resume <任务ID>
```

恢复只加载历史，不执行历史里的工具，并进入计划模式。可继续只读检查；需要修改时由用户输入 `/execute`，仍遵循启动权限。重新读取文件后才能编辑，之前的读取指纹不会恢复。已完成的操作结果告诉模型哪些步骤已经做过；程序不会自动重放旧调用，但不能保证模型永远不会提出新的重复操作，修改仍受权限控制。

## 为什么“结果未知”不能等同于失败

考虑：文件已经替换成功，但程序在保存工具结果之前退出。再次执行同一条追加命令可能重复写入。跨进程保存和外部副作用不在同一个事务里，所以这里不承诺“恰好执行一次”。

有未知结果时，整个工作目录的后续修改与命令都会被阻止；读取和检查仍可使用。新建任务、`/reset` 或 `/load` 不会解除阻止。人检查实际文件、Git 差异、命令日志后，显式记录处理结论：

```text
/resolve <任务ID> 已检查文件和测试日志，修改已完成，不需要重放
```

`/resolve` 是终端命令，不是模型工具。它不会撤销修改或执行命令，也不验证用户说明是否真实。工作目录内同时只允许一个启用检查点的 Agent 主循环；后台命令可以继续并发运行，因此仍要注意外部文件变化。

## 后台命令如何工作

`run_command` 保留原有同步语义，最大 60 秒。新工具为：

| 工具 | 作用 |
| --- | --- |
| `start_command(argv, timeout?)` | 启动独立执行器，立即返回 `job_id`；默认 300 秒，最多 3600 秒 |
| `poll_command(job_id, offset?, wait_seconds?)` | 返回状态、退出码、日志；单次最多 64 KiB，可等待最多 10 秒 |
| `cancel_command(job_id)` | 经确认写入取消请求，执行器终止命令进程组 |

终端查询不消耗模型请求：

```text
/jobs
/job <任务ID>
/job <任务ID> <next_offset>
/cancel <任务ID>
```

日志偏移以字节为单位；分块 UTF-8 边界可能显示替代字符。每个命令最多保存 1 MiB 日志，多余输出继续读取但不保存，`truncated=true` 表示丢弃发生。状态 `succeeded` 且 `returncode=0` 才表示命令成功；查询接口的 `ok=true` 仅表示查询成功。

关闭终端后独立执行器继续工作。它每半秒保存心跳；超过 10 秒无心跳会显示 `unknown`，不能据此重新启动命令。失联任务同样阻止后续修改；人工检查后使用 `/resolve-job <任务ID> <核实说明>` 解除阻止。核实记录不启动或终止命令。取消通过文件请求完成，不使用历史 PID 直接杀进程，避免误杀复用 PID 的其他程序。若执行器被强制杀死或机器重启，无法保证清理已脱离其控制的子进程，需人工检查。主动退出进程组的程序也不受普通进程组清理保证。

## 权限是本地决策

```bash
fast-agent --workspace /你的仓库 --permissions read-only
fast-agent --workspace /你的仓库 --permissions confirm
fast-agent --workspace /你的仓库 --permissions restricted --allow-commands /可信位置/commands.json
```

- `read-only`：允许内置读取、检索、Git 状态与后台查询；拒绝编辑、启动和模型发起的取消。用户输入 `/cancel` 是独立的显式取消请求。
- `confirm`：默认策略，文件修改展示差异后确认，命令逐次确认。非交互输入默认拒绝这些操作。
- `restricted`：精确匹配 `argv` 数组的命令自动获准，其余修改仍需交互确认；无交互时拒绝。不是命令前缀匹配。

白名单文件示例：

```json
{"commands": [["/绝对路径/python", "-m", "unittest", "discover", "-s", "tests"]]}
```

白名单在启动时由用户指定并读取，模型不能通过工具参数更改它。测试本身也能执行代码；精确参数匹配并不限制程序内部的行为。文件编辑仍保留原有差异确认和外部变化检查。注册自定义工具时默认按修改类处理，只有真正无副作用的工具才应声明 `effect='read'`。自定义修改工具也应在副作用之前调用 `context.authorize()`；只有能确定尚无副作用的校验错误才使用 `ToolInputError`，其余异常保守视为未知结果。文件编辑工具禁止修改 `.fast-agent` 运行记录和 `.git` 内部数据。

检查点内的 `audit` 保存批准/拒绝与目标，消息保存工具参数和结果；不复制 API 密钥或整个环境，但用户输入与工具输出本身仍可能含敏感内容。运行目录已被 Git 忽略，文件默认 0600。后台执行器不继承 `FAST_AGENT_API_KEY`，其他环境继承；同步命令仍继承环境。这些功能不是操作系统沙箱，也不防御同一用户恶意修改运行记录或并发替换符号链接。

## 对照代码阅读与验证

从 `agent.py` 的 `checkpoint()` 看写前记录，再看 `tasks.py` 的未知结果占位和 `resolve()`；`tools.py` 先检查只读/未知结果限制，具体编辑与命令通过 `ToolContext.authorize()` 作权限决策。`jobs.py` 创建句柄和查询记录，`job_worker.py` 独立管理命令生命周期。

```bash
source .env
python examples/real_reliability_demo.py
```

验证器只操作临时目录：真实模型读取并编辑文件、启动后台测试；宿主在启动结果已保存后模拟中断；第二个进程恢复并查询原任务，核对命令只执行一次；第三个进程启动并取消另一个任务。最终断言检查文件、退出码、测试日志、执行次数和进程 ID，不依赖模型的“完成”措辞。未知副作用和进程直接退出的路径另由离线自动测试覆盖。
