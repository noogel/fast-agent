# worktree 变更交付与真实修复验收

[Git worktree 独立任务目录](37-worktree-isolation.md)创建独立目录；本章让修改成为可核对的交付包。先在主仓库 `/worktree-create repair`，再在返回的目录启动 Agent 修复和测试。回到主仓库的执行模式，输入 `/worktree-export repair`，确认后获得本地 JSON 交付记录路径。

## 交付的内容

创建时记录固定 `base_commit`。导出使用这个基点与当前工作目录比较，因此包含子工作区已经提交、暂存和未暂存的最终变化，而不是只执行普通 `git diff`。新文件需要由用户明确暂存。删除、文件模式及二进制变化通过 Git 的完整补丁表达。

交付记录位于 `.fast-agent/worktree-exports/<ID>.json`，保存基点、当前 HEAD、状态、补丁字节的 SHA-256 和 `patch_base64`。Base64 避免非 UTF-8 内容损坏；校验值用于核对字节一致性，不是签名或来源认证。补丁上限 2 MiB，超限拒绝；生成过程先暂存到临时文件再有界读取，临时磁盘使用不受此内存读取上限约束。

## 为什么拒绝交付

- 没有创建记录的旧 worktree：无法可靠知道最初基点，不能用当前 HEAD 猜测。
- 路径与记录不符、链接目标或共享 Git 目录不匹配。
- 存在未解决冲突、未跟踪文件（`.fast-agent` 运行记录除外）、被跟踪的运行记录或子模块。
- 两次补丁及前后状态不一致：采集期间发生修改，应停止其他写入者后重试。
- 计划/只读模式或未批准导出。导出会写本地运行记录，沿用现有授权规则。

忽略文件不会进入补丁，确认需要交付的内容没有被忽略。重复采集是并发变化检测，不是对任意编辑器或 Git 进程的强制锁；请在静止的工作区导出。此功能不是安全沙箱。

## 接收与复测

先查看记录并核对基点；在这个精确基点的**干净检出**中，将 `patch_base64` 解码为补丁，核对 SHA-256，运行 `git apply --check`。检查通过后才应用，再运行项目测试和检查 Git diff。检查成功不等于测试通过，也不代表补丁可以安全应用到有脏修改的主目录。

本功能不自动应用、合并、提交、删除 worktree，也不清理父目录。自动合并和安全清理需要单独的冲突与丢失保护流程。

## MiniMax 验收流程

`examples/real_worktree_delivery_demo.py` 创建带失败加法测试的临时仓库，让 MiniMax 实际读文件、运行测试复现、编辑源码、重跑测试并查看 Git 状态与差异。宿主程序另外运行测试，核实测试文件和父目录脏修改保持不变。随后导出补丁，在精确基点的第二份干净检出中检查、应用并再次测试。模型的文字结论不作为通过依据。

实现入口：`worktrees.py` 的 `create_worktree` 和 `export_worktree`。离线测试还覆盖二进制补丁、冲突、未跟踪文件、错误记录以及采集期间的文件变化。

验收：MiniMax 12/12 项通过，6 次请求；真实报告保存在 `.fast-agent/validation/worktree-delivery-real.json`，记录为指定场景的运行结果，不代表未来服务一直可用。
