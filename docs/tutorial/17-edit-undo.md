# 文件编辑记录与安全撤销

Agent 能修改代码，还需要让使用者看清改动，并在适当时恢复文件。本章在原有文件写入流程上增加持久收据和本地撤销命令。

## 使用方法

```text
/changes
/execute
/undo <编辑编号>
```

`/changes` 显示编号、路径、时间和状态，不输出完整文件内容。文件工具成功返回的 `edit_id` 也可以直接用于撤销。恢复会话默认进入计划模式，必须显式 `/execute` 后才能确认修改；启动时的只读权限不会被提升。

`/undo` 是本地命令，不发给模型。它展示反向差异，得到确认后才写入。会话消息保留原来的操作历史，下一轮应重新读取文件，以当前文件为准。

## 一次编辑的数据流

1. `read_file` 保存文件和沿途 AGENTS.md 的指纹。
2. 编辑工具在内存计算结果，展示完整差异并请求确认。
3. 确认后写入 `.fast-agent/edits/<编号>.json`，状态为 `pending`，包含修改前后文本。
4. 再次检查文件和规则，使用同目录临时文件及原子替换提交。
5. 将记录标记为 `completed`，向模型返回编辑编号。

记录文件权限为 0600，目录为 0700，复用有界、原子写入的 RuntimeStore。快照可能包含项目私有内容，应保留在被 Git 忽略的 `.fast-agent` 中。单个文本文件仍受 1 MiB 限制；当前没有历史总量自动清理。

## 撤销为什么不能直接覆盖

撤销先检查当前文件是否逐字节等于记录中的修改后版本。如果用户或其他工具后来改过文件，就拒绝覆盖。确认过程中再次发生变化，也会拒绝。

通过检查后，记录先进入 `undoing`，再复用原有差异确认、权限判断和原子文件替换，成功后标记为 `undone`。同一条记录不能重复撤销。多次编辑同一个文件，应从最新记录开始逆序撤销。

首版只撤销已有文本文件的编辑。新文件会留记录，但不会自动删除；命令产生的副作用、Git 操作和多文件事务不在撤销范围内。

## 中断与限制

文件和 JSON 记录是两次独立的磁盘操作，不能承诺一起提交。进程若在中途退出，可能留下 `pending` 或 `undoing`。这些记录不能直接撤销，需要人工查看当前文件核实，不自动猜测操作是否完成。哈希/内容检查也不是针对恶意并发进程的操作系统级事务隔离。

撤销共用工作区执行锁，拒绝与启用检查点的 Agent 任务同时运行。它遵守计划模式、启动只读权限及已知未核实操作的阻塞。

## 真实模型验证

```bash
source .env
.venv/bin/python examples/real_edit_undo_demo.py
```

脚本在临时 Git 仓库中依次执行：失败测试 → MiniMax 规划 → 工具修复并测试通过 → 独立进程恢复会话并只读核验 → 外部修改冲突保护 → 独立进程通过本地命令撤销 → 原始失败测试重新出现。最终核对源文件完全恢复、测试文件未改和 Git 差异为空。

报告保存到 `.fast-agent/validation/edit-undo-demo.json`。撤销由宿主程序显式发起，不把模型文字中的“已撤销”当作证据。
