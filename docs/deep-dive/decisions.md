# 01 · 从一个失败测试认识 Agent

假设测试说 `add(2, 3)` 应该得到 5，实际得到 -1。最短的修复脚本可以写成：读取已知文件、把减号替换为加号、执行测试。既然脚本能做，为什么还需要 Agent？

如果还没看过完整例子，先读[修复失败测试的五个角色](../start-with-a-task.md)：模型提出操作，工具接触文件，上下文保存记录，权限约束执行，循环组织下一轮。下面解释为什么需要这样的分工。

## 差别出现在不知道答案的时候

如果你已经知道文件位置、错误原因和修改方式，固定脚本通常更直接。实际仓库里，你可能只知道“某个用例失败了”，还不知道是实现错误、测试数据错误还是依赖环境出问题。

Agent 的价值在于根据新证据选择下一步：搜索函数、读取调用方、复现失败，或者暂时停止询问用户。模型提出这些选择；宿主程序决定能否执行，并保存执行结果。动态探索增加了模型请求成本和出错机会，因此不应把本来确定的一步操作都变成模型决策。

## 模型提议与程序执行

模型可能提出先读源码，再运行测试。程序处理工具请求、检查参数与权限，执行后把结果加入消息。模型据此继续判断。下一章会拆开工具接口，第三章再逐轮展开消息列表。

## 为什么循环需要停止条件

想象模型不断尝试同一个不存在的路径。没有限制的循环会反复花费请求预算，却没有增加信息。Fast Agent 的步数上限和重复失败暂停就是为这类情况设置的边界。

这几个条件回答不同的问题：

| 条件 | 它限制什么 | 它不证明什么 |
| --- | --- | --- |
| 模型返回最终文本 | 本轮不再请求工具 | 任务一定正确完成 |
| 步数达到上限 | 当前运行的模型调用轮数 | 任务不可继续 |
| 重复失败暂停 | 连续重复的失败尝试 | 所有其他方案都无效 |
| 请求预算耗尽 | 客户端可继续消耗的请求量 | 当前代码已经安全交付 |

## 去代码里核对

从 [Agent._run](../reference/src/fast_agent/agent.py.md) 阅读模型回复、工具结果与历史追加的关系，再看 [ToolRegistry](../reference/src/fast_agent/tools.py.md) 的参数校验。模型协议数据类型在 [models.py](../reference/src/fast_agent/models.py.md)。

## 自测

**问题：模型已经输出合法 JSON，为什么还要做权限检查？**

答案：JSON 合法只说明请求形式符合约定，不说明路径、命令或副作用已得到授权。模型负责提议，宿主负责执行边界。
